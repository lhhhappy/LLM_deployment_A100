## 计时方案

`scripts/pod/verify/timed_run.py` 保留原 runner 的 preflight、首次 warmup 和严格 flush；
仅测量的 loadgen 使用 `timed_loadgen.py`。从第一条请求实际发出计时，70 分钟到点停止准入、唤醒 gap 等待，
已发请求继续完成。原 rendering、输出预算、gap、N 个链槽、引擎调用和时间戳口径保留。
发送台账与完成 raw 必须逐条闭合；不能通过截掉超时请求取得好看的分位数。回放自然排空，不需要正常路径 stopjob。

`timed_score.py` 核对冻结链前缀、逐请求元数据、发送/完成集合及 flush，用原评分统计生成 **diagnostic** 报告。
候选完成的请求集合可以不同，故同时报告完成量、工作量及共有请求比较；不冒充整档 VALID 或正式 N。
若全部链早于截止耗尽，保留真实结束时间，不补空等待凑时长。

原 scorer 除了稳态区间 `[10,70)`，还要求最后到达 `t_last >= W1`。严格在第70分钟停止发送不能满足该条件；
保留其原始无效标记。另列客户端 `[10,70)` 发出请求的诊断 TPM，分母60分钟，含这些请求排空后的完整输出；
不能把它称为原评分器稳态 TPM。未满70分钟也不改变这一固定分母。
