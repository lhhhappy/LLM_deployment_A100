# 咨询：长链本地回放与正式成绩的偏差，以及下一步数据和引擎工作的优先级

上下文截至 2026-09-24：058 已完成，059 引擎已在 8 卡上启动并处理请求，处于测量前的预检/预热阶段、尚无测量结果。文中样本和数字均属于指定运行，后续新数据不覆盖这些冻结版本。

我们在 8×A100-SXM4-80GB 上部署 GLM-5.3-Flash 推理服务。希望请熟悉长上下文推理、前缀缓存、混合注意力和在线调度的专家，审阅下面的实测与证据边界，帮助判断：为什么相同的正式 A 配置在合成长链 lite 集 N14 上比原开发集更接近线上 N14，却仍有系统性偏差？下一轮应先补哪类数据证据，再按什么顺序验证缓存、计算和调度优化？

请把“已实测”“由源码/静态账本推断”“待验证假设”分开。我们最需要可证伪的机制判断、对照实验和决策阈值，不需要仅凭合成集推算正式 N@SLO。

## 一、比赛目标与评分口径

- 先过 AIME26、GPQA Diamond 两项能力门，均需严格高于 90 分。压测采用隐藏多轮会话链的依赖感知回放，固定轨迹和输出预算；正式规模为 341 链、5150 请求，一轮约 8–10 小时。不能关 thinking、压低输出、截历史或删 tools。
- 并发档位从 N10 开始，过档加 4、失败减 4，首次在已通过档位之上失败即停止；N 是同时在场的逻辑会话数，不等于在途 HTTP 数。正式排名按主办方后续确认：已通过的最大 `n_at_slo` 越大越好，之后 `tpot_mean` 越小越好，再看 TPM、提交先后（题面旧版 TPM 不排名的表述已由该确认更新）。单档必须满足 11 道硬门：coverage=100%、harness_data=0、harness_render=0、engine_error<1%、infra_error<1%、四道 TTFT、所有必需桶有样本、TPOT p95。我们接受 TPOT 均值适度变慢以换取更高的有效 N，前提是全部硬门通过。
- 四个 TTFT 桶：链中且冻结未命中输入 ≤4096 token 的 `fast_intra` 目标 3 s；全部链中请求的 `overall_intra` 目标 5 s；非链首的用户轮首 `turn_start` 目标 15 s；链首或上下文重建的 `chain_start` 目标 30 s。TTFT 用服务端实际接收请求至首 token 的时间，包含准入、排队、调度与执行。
- 四道 TTFT 门有题面规定的统计余量：只有超标率的 95% 单侧下界仍高于 5%，该门才失败。下表“超标/允许”按此判定，不能仅以 p95 是否略过目标判断。`tpot_p95 ≤100 ms/token` 无此余量。
- TPOT 对每个请求计算“客户端收到末个 SSE token 与首个 SSE token 的时间差 /（输出 token 数−1）”，再按请求取均值或 p95。它包含流式传输与服务影响，不是 decode kernel 的纯耗时；排名用均值，硬门用 p95。TPM 用固定稳态窗口，不能用全程平均代替。
- 本地判分用原 harness 加赛规补充门；每个请求恰好一次，否则 INVALID。`/flush_cache` 必须真实清空前缀缓存，时间戳与 token 计数如实。用户已取消“生成 token 逐字一致”前置门及“同配置自动全档重跑”，但完整性、真 flush、正式评分和质量要求仍保留。

## 二、正式 A 与三类本地/线上数据

正式 A 是 attempt 45979。能力门已过，线上 **N14 通过**；线上 N18 失败，但平台没有返回失败分项和逐请求记录，不能断言 N18 是缓存驻留、prefill 或某一 TTFT 门所致。用户提供过其他选手 N30 的历史快照，仅是外部背景，不是我们可核实的当前对照。

A 的部署为 SGLang 路线、TP8、MTP/NEXTN（3 steps、top-k 1、draft tokens 4）、BF16 KV、64-token 物理页、LPM 调度、TileLang DSA prefill/decode、最大运行请求 32、CUDA graph 最大 batch 32、`prefill-decode-interval=2`。13 个已打补丁为 `000/101/106/110/111/114/120/121/130/140/150/160/170`。其中“在补丁栈里”不等于机制已开启：101/140 受 160 的 MTP 守卫关闭；130 的异步 tokenization 开关为 0；150 的启动预热在 MTP 下跳过；170 的 prefill graph 未开启；121 没有独立单变量评测。120 保护链首，调度 cold cap 为 4096、short tokens 为 8192；运行时 chunk 为 8192、max_prefill 为 16384。A 的 KV 池为 1,036,288 token、Mamba/KDA 状态槽约 321。044r 与 058 的 13 补丁、环境变量、启动参数与 A 一致，服务本地端口不同。两次本地对照是**负载变更**，不是引擎优化收益。

这三类请求集来源不同：

静态工作量也有缺口：完整集合计 prompt 393.887M，源链摘要 485.059M；总输出 4.108M，源摘要 4.105M。缺失请求的“源冻结新增预算”18.936M 与生成部分的“实际 LCP 新增”5.109M 属于**不同账本**，差额说明链长与输出对齐没有恢复新增算量分布，不能把差额当作真实 GPU 节省率。此前 CPU 驻留模拟在原 dev 上估计 prefill 17.3M，而 8 卡实测 9.92M，约高估 74%；它没有正确覆盖跨 session 共享和页级淘汰，因此当前不能用来选 N 或断言 N18 驻留瓶颈。

## 四、058 内部的两类偏差：开场拥塞和后段变轻

**唯一失败门是开场 chain。** 12 条超时均为被选链首条请求、均来自原始正文，在测量开始约 39 秒内到达。首 40 秒 15 个 chain 样本有 12 个超时；之后 71 个 chain 样本全过。这 12 条的“接收→首次执行”中位约 39.19 秒，“首次执行→首 token”中位 4.33 秒；11 条在第一次执行前已等待超 30 秒。前者不是纯调度耗时，后者也不是纯 GPU kernel 耗时。首 40 秒这 15 条合计实测新算 750,344 token。开始约第 5 秒时，仍有 1,002,240 个 KV token 槽、301 个 Mamba 槽空闲，队列已有 10 请求；可观测淘汰计数在开场约 95 秒未增加。证据支持集中冷 prefill 的积压，**不支持把这 12 条归因于测量期缓存容量不足或淘汰**。被抽中链的首请求即使源标签预期有前缀，flush 后也不能假设未纳入的前驱仍在缓存。

按冻结 cohort 独立复核前 14 条链首：lite 总输入 743,616 token，完整合成集 750,953 token，差约 1%，不支持仅凭总量断言 lite 抽到了特别重的开场。两者最大单请求分别为 251,916、194,991 token，都在队列第 4 个位置；长度分配、前缀共享和实际交错仍可能不同。这里统计的是原始 prompt 总量，不能当作去重后 GPU 新算量；这些前 14 条也不同于上文按实际接收时间选出的首 40 秒 15 个 chain 请求。更换随机种子会改变开场结构，但不能据此解决后续合成工作量和低并发尾段的代表性问题。

058 的 10 秒采样中，KV 锁定使用峰值约 774,976/1,036,288（74.8%），Mamba 活动槽峰值 52/321（16.2%）。`free` 接近零时还须看 `evictable`，单独的 free 不能证明不足。这些观察也不能排除更高 N 或更长全量回放中的驻留压力。相比之下，044r 首 40 秒 18 个 chain 请求有 9 条失败，之后还有 23 条失败，压力持续方式不同。

## 五、等待时间和生成机制仍未校准

新增链内 gap 采用 Phoenix 观测到的相邻调用 end-to-start 间隔，单次截到 300 秒；工具执行、用户停顿、模型服务耗时的分解未知。正式 runner 按每链 3600 秒限幅；现有三集均未触及该上限。以下均剔除每条链首请求，按相同 nearest-rank 口径计算：

|---|---:|---:|---:|
| 样本数 | 411 | 5290 | 1059 |
| p50 / p95 / p99，秒 | 2.639 / 22.110 / 33.210 | 3.024 / 28.249 / 95.846 | 3.082 / 28.705 / 119.918 |
| >30 秒；>60 秒 | 1.46%；0.49% | 4.76%；1.87% | 4.63%；1.89% |

171/172 早期数值门任务因**基线自身重复生成不逐字相同**而提前退出，不能称候选实现错误。用户已取消这项逐字一致性前置门；056/057 已按真实服务全量指标运行。122 的结果也说明短请求 TTFT、链首等待、缓存缺口混在一起，不能把每项局部收益简单相加。

**180 HiCache 当前设计。** A 原配置不启用主机二级缓存。底包直接为 GLM 开启 HiCache 时，混合 KDA/DSA 栈没有把 DSA indexer 键行加入主机池；主机恢复仅有 MLA KV 与 KDA 状态，会选错稀疏注意力历史行。kpool=4 时 256 token 组的 64 个 indexer 行集中写在该组第一张 64-token 页；若树在组内 64/128/192 处分叉，可能覆盖其他分支，或让已写穿主机的组头页成为过时副本。180 为 KV、indexer、KDA 状态与 MTP 草稿层建立完整主机池声明，并在 HiCache 打开时让树节点/检查点按 256 token 组确定所有权；未写满的尾组留在请求私有空间。关闭 HiCache 时不改变 A 的运行路径。

据实现方 Claude 的报告，180 在正式 A 全栈的真实缓存控制器与树路径上通过 52/52 项 CPU 测试；去掉 180 时 30 项失败、1 项报错，能检出 indexer 缺失、陈旧组头、分叉覆盖和 flush 问题。主会话已核对交付文档、补丁哈希及上线配置，本轮未独立重跑这 52 项测试。测试用 torch 拷贝替代 CUDA 搬运，因此只证明搬哪些字节、状态归属和 CPU 控制流程，**未证明 GPU DMA、流并发、8 卡一致性、真实模型数值或性能**。按配置公式，MTP 下主机镜像约 13,872 B/token/卡，KDA 检查点约 17.6 MiB/槽/卡。`--hicache-size 32` 是每卡 32 GB，八卡预算总计 256 GB；补丁说明里的约 180 万主机 token、约 380 个 KDA 状态是使用设备端 200 个状态槽的算例，不能套到 A 的 321 槽；059 启动日志已实测每卡主机 KV 容量 1,394,368 token：KV+indexer 预算约 19.34 GB（其中 KV 约 17.13 GB，目标 11 层+草稿 1 层），Mamba 主机预算约 12.67 GB；设备 KV 仍为 1,036,288 token。Mamba 主机状态槽数尚未独立核验，不能由上述算例替代。6 万 token 约 0.83 GB/卡、独占 PCIe 搬回约 0.05–0.1 秒也只是估算；最慢卡就绪时间、写回干扰和 decode 竞争须实测，不能把它当 p95 保证。256 对齐比原 64 对齐最多多重算 192 token。
