5. Consequences (INFERRED from 1-4, to be measured on the dev box)
   a. Whenever a virtual loc >= per-rank rows (818,112 in 025) is read/written: out-of-bounds -> illegal memory access.
      The allocator hands out the lowest free pages first, so this only happens once the virtual high-water mark passes
      1/W of the logical space. 025 crashed at "full token usage 0.07-0.10" of 6.54M logical = 0.46-0.65M live tokens,
      plus fragmentation from freed pages -> high-water mark over 818k is plausible. The crash is NOT specific to prefix hits;
      prefix hits (long retained trees) just push the high-water mark up. Cold probes (013b) never got there.
   b. Below that threshold, DCP runs WITHOUT crashing but the DSA layers read the wrong KV rows (row v holds virtual token
      v*W+rank) in both prefill and decode -> DSA attention output is wrong. 11 of 45 GLM layers are DSA, so the capability
      smoke (12/12 in F78) could still pass. Any DCP numbers so far (F78 −19% cold prefill, 025 N10) were measured on
      wrong attention.
6. None of 110/112/113/114/115 introduced the bug; they inherited the base's non-DCP addressing. 115 only made the
   64-head decode kernel fit A100 smem, which is what let DCP start at all.
