## 发现与修复

旧版开启 HiCache 后，120 的 `_ax_sched_protect_enabled()` 返回 false，121 的冷块限制也失效。
如果与 122 组合，其 `_ax_pace()` 同样不启用。因此不能把 059/060 写成保留正式 A 调度行为的 HiCache 对照，
也不能把此前单独调用预算方法的 CPU 测试写成组合已实际启用。

新版把该条件改为 `not enable_hicache_storage`。独立构建 A+180、A+122+180，零 fuzz 应用；
与旧组合相比，所有 Python 文件中仅 scheduler.py 有变化，见 [源码差分](source-diff.patch)。
实测真实方法初始化：旧版 protect/pace=false/false；新版 true/true；打开 L3 后 protect=false。

3 项 HiCacheTierTests 通过；12 项 pace 测试显式开启主机层，比较 A+新180 与 A+122+新180，全部通过。
第一次扩展测试错误地给未修复的 A 控制组也打开 HiCache，导致“pace 关闭时等价”测试失败；
因为控制组关闭了 120、候选保留 120，两个配置本就不同。错误控制组记录单独保留，修正控制组后通过。
这些是 CPU 真实决策方法加假请求/资源池，不是 GPU 恢复或性能证据。

120 的 `_ax_should_decode` 只在 interval=0 使用；正式 A 的 interval=2 已让该特定分支返回 false。
因此不能把 059 的变化说成所有 decode 让轮机制都被移除；已证实受影响的是保护总开关、冷块限制和短命中共享，
以及假定组合时 122 的初始化。主机待恢复请求仍不参与短命中预留；搬回成本仍未进入 122 模型。
