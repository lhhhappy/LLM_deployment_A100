# 115 — decode context parallel (DCP) on A100

One patch for DCP on sm80 (T57 folded the former 115 and 116 into this file; source tree byte-identical, evidence/T57). Status:
**Ordinary forward and the three NextN graph phases have TP2+DCP2 numerical evidence; full-capacity/HiCache integration is under validation (2026-09-26), with no TP8 result.** Off unless `--dcp-size N` is given. DCP-off execution retains the fixed baseline, including its original indexer relocation; topk=1 NextN does not call accepted-path compaction.

## 2026-09-26 integration contracts

- The 041 real/padded row mismatch is separate from 025 virtual-address overflow. Extend copies the planner's real token count from padded K tensors, and rejects missing rows. Both 33/40 and 33/34 are covered by the actual-function contract probe.
- Target and DSA NextN latent pools use the same owner rule (`loc % W`, `loc // W`). Draft allocation and accounting now match this layout; the indexer stays replicated in virtual address space. The former replicated-draft allocation comment did not describe the write kernel.
- Indexer capacity is enforced inside `DSATokenToKVPool`, including hybrid-target and draft construction. The hybrid target bypasses `KVCacheConfigurator._create_dsa_pool`; a fix confined to that factory misses this model. Low-address numerical passes alone do not validate capacity.
- DECODE, TARGET_VERIFY and DRAFT_EXTEND_V2 all use Q gather and partial-attention/LSE merge. Ordinary prefix extend still gathers the prefix into a full buffer. All three MTP graph phases require separate replay evidence.
- Current topk=1 NextN does not compact accepted KV. The relocation primitive nevertheless supports changing owners: snapshot source bytes, reduce contributions from their single owner, then write on destination owners. All ranks must call with identical virtual descriptors, including ranks with no local writes. Per-layer temporary memory is moved tokens × latent row bytes. Compressed indexer/tail relocation under DCP is rejected before modifying any cache; this is not tree-MTP support.
- HiCache uses physical latent rows and logical indexer rows, including the packed NextN layer; see [180](180-hicache-glm-dsa.md). The engineering plan and validation boundaries are in [the DCP plan](../../notes/plan-dcp-8card.md), and call-site review in [the review record](../../notes/reports/dcp-code-review-20260926.md).

## Part 1 — 32/64-head sparse attention kernel on sm80 (`kernels/ops/attention/dsa/tilelang_kernel.py`)
- 问题：`--dcp-size 8` 时每卡持有全部 64 个注意力头，`sparse_attention_fwd_kernel_v1` 需要 Q 64×512 + 双缓冲 KV + O_shared > 256KB 共享内存，A100 上限约 164KB → 启动失败（pod 探针 012e：`Failed to set the allowed dynamic shared memory size to 262144`）。
- 改动（`kernels/ops/attention/dsa/tilelang_kernel.py`，仅 v1 kernel + 分发）：
  - 新增 `stage_output` 参数：DCP 分支传 False，去掉 `O_shared`（写入后从未读取）；默认 True，与底包内核逐字相同（2026-09-24 迁移核查后改，原先无条件删除会改变正式 A 用的内核）。新增 `max_heads_per_block` 参数（原硬编码 64）。
  - sm80 且头数 ≥64 时用 `block_I=64, num_stages=1`（开发机扫描 7 种组合中最快且能编译：T=512 2.33–2.87ms；其余布局冲突或超限）。
  - 2026-09-26：TP8/DCP4 的32头默认布局也超限，实测请求196608 B共享内存。DCP开启且头数≥32时使用同一单stage布局；DCP关闭的32头路径保留固定基线。生产wrapper的eager/graph对显式单stage参考逐位一致，见[原始检查](../../evidence/dcp-mtp-20260926/phase2/sparse10.json)。
- 验证（开发机 A100，`build/p115_test.py`、`build/p115_sweep.py`）：H=8 与原版**逐位相同**、速度不变；H=64 相对误差 ≤3.4e-3、CUDA graph 正常；原版 H=64 按预期失败。
- 观察：64 头一起算（2.3–2.9ms/512 token）远快于 8 次 8 头（≈7.4ms）→ 同一 KV 读一次供 64 头用，印证 TP 按头切分的重复读 KV 问题。

### 可选：去掉确定不属于本rank的KPool列

`SGLANG_AX_DCP_COMPACT_TOPK=1`，默认关闭。仅DCP、KPool=4、页按4对齐且prefill/decode均TileLang时启用；其他DCP组合启动报错。普通prefix extend保持原路径。

KPool输出按每组的token偏移依次展开，尾段也从完整组边界开始。虚拟页对齐使列号与虚拟loc在`gcd(W,4)`下同余，所以先取`rank % gcd(W,4) :: gcd(W,4)`列，再执行原owner判断与loc/W换算，可以保留本rank的全部key。W2减少约一半候选列；W4/W8减少约四分之三。W8仍需屏蔽剩余的不属本rank的列。该推导不适用于任意top-k列表，不能用于不满足布局的模型。

单卡验证使用真实KPool CUDA输出、随机高位页映射、21个长度边界，检查拥有的索引多重集完全一致；18组attention/LSE/独立FP32参考及图重放检查通过。T=136/152对应N34/N38验证阶段每路4行；头数模拟TP8每卡形状。每组交替次序计时16对×10次，保存全部样本。数据见[原始记录](../../evidence/dcp-mtp-20260926/phase2/sparse10.json)，脚本为`scripts/analysis/dcp_sparse_probe.py`。它不包含Q gather/LSE通信、模型其余层或服务排队，不能当作N34/N38收益。32头两条测速路径均使用可运行的单stage布局，不能把无法启动的旧布局计为加速参考。

## Part 2 — DSA address protocol under DCP (`mla_buffer.py`, `dsa_backend.py`, `kv_cache_configurator.py`, `pool_configurator.py`)
Code comments are tagged `[ax] 116`. Task T50/T50b; root-cause evidence `evidence/T50/address_protocol.txt`.

### 问题（8 卡 025 崩溃的真正原因）

DCP 下调度器与分配器使用**虚拟 loc**（`[0,(rows+64)·W)`，页 64·W，容量按 ×W 计，`scheduler.py:2249,2423`、`kv_cache_configurator.py:1995`），而 DSA 池（latent 与 indexer K）是**每卡大小**。

- **latent 写入没分片**：GLM `qk_rope_head_dim=0`，写入走 `set_mla_kv_buffer_kernel_norope`（`kernels/ops/kvcache/mla_buffer.py:87-114`）。这个 kernel 没有 DCP 规则，每卡都把每个 token 写到虚拟 loc。只有带 rope 的 kernel（:42-44）按 `loc%W==rank → loc//W` 分片。
- 读路径（tilelang 稀疏 prefill/decode 的 `page_table_1`、indexer 的 `real_page_table`、112 的 `_paged` 不设上界）和 indexer K 写入也全用虚拟 loc。
- 结果：原栈 DCP 实际上是“每卡复制全部 KV，按虚拟 loc 访问一个每卡大小的缓冲区”。
  - 所有活跃 loc 都小于每卡行数时，结果正确（开发机实测 orig_dcp 与 orig_ref 一致），但容量没有增加（F78 的“逻辑 ×7.8”并不存在），decode 还在每卡对全部 token 算 64 头（W 倍冗余）。
  - 分配器高水位一旦超过每卡行数（025 为 818,112），读写就越界 → illegal memory access（推断；025 当时活跃约 0.46–0.65M token，加上碎片）。
- 与前缀命中无直接关系：长前缀树只是把高水位推高。冷探针从没到达这个区间。
- 110–115 都没有引入这个问题。

### 改动（4 个文件）

1. `kernels/ops/kvcache/mla_buffer.py`：`set_mla_kv_buffer_kernel_norope` 加 `DCP_RANK/DCP_WORLD_SIZE`（默认 0/1），规则与 rope 版相同：只存 `loc%W==rank`，写到本卡行 `loc//W`。发射处传入 `get_parallel()` 的值。**latent 从此真分片**。
2. `srt/layers/attention/dsa_backend.py`（仅 tilelang 分支）：
   - **extend（含前缀命中、chunked prefill）**：底包 forward_mla 在 DCP extend 时已把本批每个请求的前缀从各卡分片 all-gather 进 `attn_dcp_metadata.dcp_kv_buffer`，并拼接新 token（`dcp/comm.py:267`，布局见 `dcp/planner.py:48`），但原来只有 FlashInfer-MLA 读它。116 让 DSA 也读这块缓冲区：
     - 每批建一次“虚拟 loc → 缓冲区行”的 int32 表（每卡 `(rows+64)·W+1` 项；无效项进垃圾槽，置 -1）；
     - 把 top-k 转出的 `page_table_1` 查表换成行号；
     - 每卡用本卡的头对完整 KV 做注意力，不需要 LSE 合并。
     - DCP extend 若缺少 `attn_dcp_metadata`（例如将来被图捕获的 prefill 跳过了 planner），直接报错，不静默读错行。
   - **decode / target-verify / draft-extend-v2**：`page_table_1` 只保留本卡拥有的 loc，换成 `loc//W`，其余置 -1（kernel 按 `>=0` 掩码）；输出 partial + LSE，由底包的 LSE 合并完成。
     - 某行本卡没有 key 时 kernel 得 0/0=NaN，而 NaN×0 会穿过合并，所以用 `nan_to_num` 清零（这一行的 LSE 为 -inf/NaN，合并时权重为 0）。
     - 全部是张量运算，可以录进 CUDA graph。
3. `srt/mem_cache/memory_pool.py:DSATokenToKVPool`：DCP目标和DSA草稿的indexer构造容量下界是`(rows+64)·W−64`；`IndexKeyCache`再加64行padding，实际覆盖`(rows+64)·W`行。复制式indexer仍按虚拟loc寻址，latent物理行数不乘W。容量约束移入构造器，覆盖绕过`_create_dsa_pool`的`HybridLinearKVPool`路径；显式传入过小容量会报错。
4. `srt/model_executor/pool_configurator.py`：目标与草稿indexer计费均恰好乘一次W，草稿latent不乘W，显存核算与真实分配一致。

### 容量（算术，未在 8 卡实测）
每层每个逻辑 token：latent 1024 B（bf16 512）+ index 132 B。非 DCP 每卡存 1156 B。DCP8+116 每卡存 1024/8+132=260 B，所以逻辑容量约 **×4.4**（不是原来宣称的 ×7.8）。025 同配置（mem 0.75）下每卡行数估计从 818k 降到约 450k，逻辑约 3.6M token。开发机 TP2 实测 pool_rows 从 9,224,896 降到 8,279,488（W=2 时与算术一致）。
要再往 ×8 靠：indexer K 也分片（本卡算 logits + 本卡 top-k → all-gather 候选再取全局 top-k），并处理 kpool 压缩跨卡的问题。另立任务。

### 验证（历史开发机 2×A100，TP2）

## 风险
- 只修了 tilelang DSA 路径（A100 唯一可用的路径）。flashmla/fa3/trtllm/aiter 在 DCP 下仍按原样（Hopper 路径，这里不用）。
- MTP/NEXTN + DCP：草稿latent分片与三阶段路由已修，完整MTP、三类图和真实接受分布仍须按本轮证据验收；历史r7不覆盖这些路径。
- `SGLANG_DSA_FUSE_TOPK` 的 v2 plan（`SGLANG_OPT_USE_TOPK_V2=1`）未测；A100 强制 v2=0。
- extend 每层做一次前缀 all-gather（底包原本就做，原来白做），外加一张 `(rows+64)·W` 的 int32 表（8 卡约 15 MB）。extend 批次会临时分配 `seq_lens_sum×1 KB` 的 `dcp_kv_buffer`（22 万前缀约 230 MB），占激活余量。
- 底包 planner 假定每个请求的前缀长度是 W 的倍数（前缀按页对齐，101 切点按 64 向下取整，W≤8 时成立）；非对齐的前缀会让 gather 错位（静默错，不崩）。
- `offload_kv_cache`（PD decode / 优先级抢占的 CPU 备份）按虚拟 loc 拷贝 latent，DCP 下不对；我们的配置不走这条路。
- 容量只有约 ×4.4，而且 decode 仍要对 64 头 all-gather Q。性能与 TPOT 要看 8 卡梯子。
