## 2. 卡点

1. **还没有 N30 的基线。** 060、061 没有同负载对照就说不清好坏。A 原样 lite N30 是现在最缺的一次运行。
2. **复用容量（活变少）是正式区间的主杠杆，但还没兑现。**
   - 长链数据里 95% 以上的 prompt token 预期可复用（数据集算术）。
   - 状态留在卡上，一条追问只算几百到几千新 token。状态丢了，就要重算 6–13 万 token，按 10.75k tok/s 约 6–12 秒（推算），直接击穿 3 s / 5 s 门。
   - 180 把丢掉的状态存到主机内存（pod 实测有 2 TB）。还有三项没验证：
     - GPU 上从主机恢复后数值是否正确（开发机探针进行中）；
     - 恢复要多久，按最慢那张卡计；
     - 恢复对 decode 有多大干扰。
3. **开场冷启动潮。** 058 的 chain 失败全在开场：N 条冷链首同时进来，排队超过 30 秒。N30 时这股潮翻一倍。122（按 decode 余量给 prefill 预算、短命中优先）与链首准入正对这里。
4. **prefill 本身贵（活变便宜）。** R25 实测 16k token 时 Marlin 84.5 TF、Triton BF16 82 TF，说明 MoE 慢在 TP8 切出的窄形状，换 kernel 本身没用。正式 A 配置在 TP8 上的单块成本曲线还没有。
5. **MTP 关掉了 101/140 的 KDA 快照**（160 的守卫）。140 与 MTP 是否真冲突没有证实，原生路径实际保留了什么也还没量。
6. **必做 kernel 还没开工**：FP8 latent KV 进 sm80 TileLang DSA，整缓存约 1.75×（推算）。DCP 在 TP8 仍有 33/40 行不匹配的故障。

## 3. 接下来的顺序

所有候选都是"A + 一处改动"，在 lite N30 上与 A 基线比。单项有效后才测组合。

1. **按 059 → 060 → A 基线 → 061 的顺序读结果**。入队的人盯到结果，Claude 做失败归因：
   - 各门、超标条数与余量、TTFT p95、TPOT；
   - 主机命中与搬回次数、每条追问的 cached_tokens 与预期命中之差、重算 token、KV/状态槽用量；
   - 按请求类型拆：冷链首还是追问，失败发生在等待还是重算。
2. **把 N30 的失败归到机制上**，再决定下一个单变量：
   - 追问状态丢失、要重算 → 180 及后续补丁 181（恢复计时与回退原因埋点、恢复/备份优先级）；NUMA 绑定另外单测。
   - 开场冷启动排队 → 122、链首准入。
   - 显存不够 → 先做显存预算审计（按最坏形状实测峰值，把余量还给 KV），再上 FP8 latent KV。
   - prefill 太慢 → 先测 TP8 单块成本曲线；再试 MoE 放置（EP8 不需要 all-to-all；TP2×EP4），并削减 MoE 里非 GEMM 的显存搬运。
3. **MTP 下恢复 prompt 末尾的 KDA 快照**：快照只读、发布后不可变，与 verify/rollback 的工作状态分开。
4. **组合**：A+122+180 等组合，等两者各自在 N30 上有单测结果后再测。
5. **N34**：N30 上最好的候选再加压确认。

## 4. 做这些时必须守住的技术约束

- **完整检查点契约**：一个位置要能复用，KV、索引键/KPool、KDA 与卷积状态、MTP 草稿状态必须在同一位置同时有效。HiCache 开启时，树只在 256 token 分组边界分裂，KDA 检查点只在精确位置发布（180 已实现）。
- **HiCache 首版只做两级**（显卡 ↔ 主机）：
  - 异步、增量、write-through；
  - 源页等 D2H 完成后才回收；
  - `--hicache-size` 按每卡计，从 32 GB 起；
  - flush 必须清掉所有层级。
- **恢复预算按最慢那张卡计**。"0.05–0.1 s 搬回一个会话"只是少竞争时的估计，不能当 p95。
- **FP8 KV**：
  - 行格式：带 scale 的紧凑行，512 B FP8 加 4 个 FP32 scale，共 528 B。
  - 容量：latent 行约 1.94×，整缓存按 12,716/7,260 ≈ 1.75× 计。
  - A100 上先软件解码成 BF16 再做 MMA；上游 raw 512B / SM89+ 的路径不能照搬。
  - 验收：对照参考路径，判据要能检出已知错误变体；覆盖高位地址、池满和 CUDA graph；TP8 真机确认。
- **DCP 放在 FP8 之后**。两者容量不能相乘（推算 DCP4+FP8 约 4.4×、DCP8+FP8 约 5.8×）。33/40 按行身份契约修，不针对个别形状打补丁。
- 驻留账本（`scripts/analysis/residency_ledger.py`）在开发集上校准失败（prefill 多算 74%）。用真实长链运行校准之前，它不参与选方案。
- 长链集每请求回放间隔均值 7.3 s、中位 2.9 s（开发集为 4.2 s / 1.6 s）。不为迎合模型去调整等待。
