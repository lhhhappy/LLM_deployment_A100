# Fable：对齐正式负载的合成负载——可行性与设计（2026-09-24）

Claude 已抽查核对：`chains.jsonl` 中 311 条原始整链共 5601 个请求（均值 18、中位 8），与主办方确认的最终评测 341 链 / 5150 请求（均值 15.1）量级一致；开发集 gap p50 2.0 s、p95 18.7 s；开发集中有 143 条链抽到了多个请求。节拍规则（每档总速率固定、N 只改变同时在场的会话数）仍是推断。

---

## 0. 先给判定：这件事"部分可行"，可靠的部分要说清楚

**结论：能做，但只能做成"结构对齐的机制试验台"，不能做成"正式 N@SLO 的预测器"。** 四个问题逐条答：

**(1) 信息够不够？——结构够，节拍不够。**
- 够的部分（VERIFIED）：`chains.jsonl` 里每条被抽样链都带**原始整链**的统计（`n_requests`、`sum_glm_tokens`、`sum_uncached_expected`、`phases`、`append_only_edges`、首末时间），311 条链的整链共 5,601 条请求；`requests.jsonl` 每条请求带原始 gap 分解（`replay_gap_ms == net_think_ms + tool_union_ms`，617/618 条相等）、`glm_lcp_with_prev`、`edge_type/subtype`、`source_*`；bodies 给出真实的 system/tools/messages 结构；cohort 文件给出正式参考集的门构成（808/9023/65）与全人口分位（intra uncached p95 11,740、chain_start 113,977、turn 42,015、fast 层占 85.2%）。链长、每轮增量、上下文增长、角色/工具边界、gap 分布、输出长度、跨链共享前缀、context reset——这些都能从数据估，且置信度中到高（见 §1 表）。
- 不够的部分：**正式 harness 怎样把 N 变成节拍**。三条证据都指向"每档总速率固定、N 只改变同时在场会话数"（我们自己 B@N10 与 A@N14 的 tpm_all 1.7593M/1.7576M 相等；榜单 N14–N22 顶部都在 1.75–1.79M；task.md 说单档约 4 h 不随 N 变；用开发集 gap 做闭环推算得到的 TPM 是实测的 2 倍且应随 N 增长），但这仍是 INFERRED（置信 ~65%）。另外正式 cohort 的规模、链条数、`system-tools-changed`（LCP=0 的链中请求）在正式集里的占比、跨链家族大小都不知道。**生成器的这几个参数只能是假设。**

**(2) 两个正式点能否定参？——不能定"随 N 怎么变"，能定速率与构成。**
A@N14/B@N10 各给 9 个数（4 道 TTFT、tpot mean/p95、tpm_all/decode、slo_attainment）。tpm 两项把每分钟请求数 × 平均 prompt/输出钉死（推得 ≈28 rpm、平均 prompt ≈63k、平均输出 ≈733，见 §1）；TTFT 四项约束排队结构。但"固定速率"与"闭环+某种 gap 缩放"两类节拍模型都能调到同时匹配这两点，然后在 N18+ 分道扬镳——分道的地方恰是我们想预测的地方。**第三个点只能来自下一次不同档位的正式提交**（任何通过档都会回报 tpm；若 N18 的 tpm 仍 ≈1.76M，固定速率模型即被证实）。

**(3) 一天能不能做出来？——最小版本半天，完整生成器 1–2 天。**
组织方的 loadgen/scorer 对数据目录格式是透明的（`requests.jsonl` + `chains.jsonl` + `samples/*.jsonl` + `bodies/*.jsonl.gz`，`load_index`/`freeze_cohort`/`ensure_bodies` 都读这些；`s1_common.py:153-176, 252-292`），合成集按同样格式落盘即可用 `run_dev.py` 原样跑，评分器可用 `--steady-start-min/--steady-len-min` 改稳态窗（`s1_score.py:671-685`）。tokenizer 与模板在开发机 `env/sgl` 可用（transformers 5.12.1，`<|user|>=154827 <|observation|>=154829 <|assistant|>=154828` 已验证）。8 卡时间是真正的成本：每档约 1 h（合成 cohort 缩到 ~1,500 条请求）。

**(4) 哪里会误导、更便宜的替代能不能拿到大部分价值？**
误导点：节拍规则（上面）；MTP 接受率在"拼接内容"上可能偏离（tpot_mean 偏差）；`system-tools-changed` 与跨链家族的频率靠假设；绝对 N@SLO 不可外推。替代方案评估：
- 按 `sampling_weight` 重加权开发集：**无用**——权重与链长/prompt 无关（相关系数 −0.005/−0.016），改变不了 43% 链首的结构。
- 开发集只取多请求链 + 拉长 gap + 固定速率节拍：**便宜且拿到一半价值**（143 链/554 请求：intra 占 74%、链首 26%、未命中占比从 35% 降到 22%），不用合成 body，改一个数据目录就能跑。这是我建议的最小版本。
- 正式提交做 A/B：**不可替代**，它是唯一能测节拍规则和驻留效应的地方；合成集的定位是替它筛掉明显错的候选、解释它的结果，而不是替代它。

所以：**可靠的部分**是"用真实 body 按正式构成与固定速率重排的负载"以及在其上做**相对比较**（缓存驻留、调度、槽位/显存配置）；**不可靠的部分**是任何"合成集在 N22 过了所以正式也能过"的推断。下面的设计围绕可靠部分展开，节拍规则作为显式开关而不是隐含假设。

## 2. prompt 怎么构造，让缓存/状态机制和真实负载一样

原则：**不做 token 级拼接文本，而是合成 body（system/tools/messages 的 JSON），用组织方的 `Renderer.render` 渲染、真 tokenizer 计数**。这样 `[gMASK]<sop><|system|>…<|user|>…<|observation|>…<|assistant|><think>` 的标记、tool_call id 校验（模板 `tc_id_exists`/`has_dup_tool_result_id`）、`<think></think>` 处理全部与正式路径一致；101/140 依赖的 154827/154829 自然出现在正确位置。

1. **种子**：真实链前缀（有 body 的 722 条）。可延长的种子：前缀 ≥3 且原链 ≥10 的 73 条；前缀 ≥5 且原链 ≥20 的 21 条；66 条完整链（多为 1–4 条）。
2. **延长**：按原链 `n_requests` 补齐到目标长度。每次追加一个块 `(assistant{tool_calls:[…]}, tool{content}, [user{reminder}])`，块从同一 pack（biomaster/scimaster）的真实消息池抽；tool 结果按长度分布抽（保留 456k 字符的长尾）；reminder 从真实 reminder 池抽并按 `reminder-replaced` 概率（282/618）替换上一条尾部；tool_call id 重新编号保证唯一且与 tool 消息配对。
3. **边类型**：按开发集比例注入 `system-tools-changed`（同一链换 tools 列表或 system 文本 ⇒ LCP=0）、`unexplained-break`（改写一条历史 tool 结果 ⇒ LCP 落在中间）、`compact-rebuild`；`context_reset` 作为同 session 新 chain_id、prompt 延续。
4. **家族**：链首共享 system+tools（同 `sys_tools_hash`）；家族大小可调（默认按开发集：156 家族/314 链首）。
5. **计数与冻结字段**：在开发机 `env/sgl` 用真 tokenizer 算 `glm_tokens`，与前一条渲染文本做 token 级 LCP 得 `glm_lcp_with_prev`，`uncached_expected = glm_tokens − LCP`（链首与 tools-changed 行上 VERIFIED 等式成立；其余行小偏差，INFERRED 为对齐），`max_output_i` 按 (phase, 层) 从 `source_completion_tokens` 经验分布抽；`phase/idx/edge_type/sampling_weight=1` 写齐，保证 `in_ttft_gate` 分桶与正式一致。
6. **自检**：`s1_loadgen.py --self-check` 逐条核对重建 token 数；抽样 `encode(decode(ids)) == ids`。发送仍走 `text`（与正式相同）；`/generate` 的 `input_ids` 仅留作定位 tokenizer 差异的调试通道（`io_struct.py:185-463` VERIFIED 支持）。

## 3. 校准流程、判据与证伪

**节拍实现**：不改 loadgen。N 个槽各持一条链；把每条链的 `replay_gap_ms` 改写为 `gap' = gap × α_N`，α_N 由目标速率决定：`N / R = 平均周期 = 平均 gap' + 预计服务时间`（服务时间用官方 A 的 TTFT≈2 s + 733×tpot 估计）。R 默认 28 rpm；同时保留"α=1 闭环"作为对照开关。这样 N10/N14/N18/N22/N26 的 offered load 相同，只有在场会话数不同——即固定速率假设的显式实现。

**cohort**：从合成整链集抽 ~1,500 条请求（约 55 min/档），门构成按正式参考，稳态窗用 `--steady-start-min 5 --steady-len-min 40`。每档前 flush（run_dev 已做）。

**校准两跑**：官方 A 栈原样 @N14、官方 B 栈原样 @N10（与 044r/045r 同一镜像栈）。判据（全部要满足才叫"已校准"）：
- tpm_all、tpm_decode 在官方值 ±10%；
- 四道 TTFT p95：fast/overall 在官方值 ±0.5 s 或 ±30%，turn/chain ±40%；tpot_mean ±20%；
- **模式必须复现**：B@N10 的 fast_intra（3.46）明显差于 A@N14（1.52），而 A 的 chain（30.2）明显差于 B（10.9）。这一交叉是 chunk 8192/无 interval 与 cold cap 4096/interval 2 两种调度的指纹，比绝对值更能说明结构对不对。
- 参数只允许调 R 与 `system-tools-changed`/家族频率两项，且调完必须同时满足两点；其余全由元数据固定。

**证伪**：任一条不满足且不能用上述两参数修正 ⇒ 生成器结构错误，不得用于 N18+；两点都满足但下一次正式提交的通过档 tpm 明显偏离 1.76M ⇒ 节拍假设错误，重做 α_N。**即使校准通过，合成结果也只用于排序候选与解释机制，不写作任何档位成绩。**

## 4. 值得生成的边界情况

| 场景 | 压的机制 | 正式集里为何可能存在 |
|---|---|---|
| gap 超过缓存存活 | KDA 状态 LRU（200 槽）、FULL KV LRU、`match_prefix` 截回到最深状态节点 | 原始 gap p99 34 s、max 301 s；固定速率下 N26 的 gap 会再拉长 ~2.6× |
| N 路长上下文同时驻留 | KV 1.04–1.32M token 上限；`5 槽/请求`；驻留需求 N×63k | 链均值 63–97k、p99 225k；N=22/26 ⇒ 1.4–1.6M token |
| 冷链首成串到达 | 单 partial、LPM 把冷请求排尾、cold cap；chain 允许超标 6.3% | 8% 链首、家族批量启动；开发集里链首 queue p50 36 s 已出现 |
| 200k+ prompt（含 456k 字符工具结果） | 16k/8k 分块 13–30 轮、indexer 激活峰值、`over_context`/truncated | p99 225k、max 257k、3 条被截断链 |
| context reset | 30 s 门下的 append-only 请求；session 内多链 | 141 次/5,601 请求 |
| tools/system 中途变化（LCP=0 的 intra） | 整段重算落在 5 s 门里（uncached p50 36k） | 开发集 148/618；正式占比未知 |
| 工具结果密集追加（每轮 +5–40k） | 短请求被截成两轮 prefill、chunk 预算 | append-only p95 11.6k、p99 38k |
| 极短输出（≤64 token） | TPOT 对单次停顿极敏感（(末−首)/(n−1)） | intra p10 102、turn p10 110；R21 的短输出坏例 |
| 请求在大块中途到达 | `chunk_budget_exhausted`、120 的 cap 逻辑、interval | 固定速率下到达与链首块必然重叠 |
| 非追加边（历史被改写、reminder 替换、compact-rebuild） | 树分叉、tombstone、140 的 role/tail 淘汰顺序 | `unexplained-break` 23、`compact-rebuild` 6、reminder-replaced 282 |
| 同家族多链首并发 | 跨链前缀共享与状态节点竞争 | 最大家族 26 链首 |

## 5. 在哪跑、最小版本

- **CPU（本机）**：生成器与自检——body 合成、边类型注入、cohort 冻结、格式校验；无 tokenizer，只能做结构检查。
- **开发机 `env/sgl`**：渲染 + tokenizer 计数 + LCP + `--self-check`；dummy 权重替身跑真实 `UnifiedRadixCache`/scheduler 看命中与状态槽行为（不看时间）。
- **8 卡 pod**：只跑校准两点与随后的 N18/22/26 档，每档 ~1 h；节拍用 α_N，评分用原 scorer 改窗。

**最小可用版本（今天半天）**：不合成 body。复制开发集目录，`samples/synth-mvp.jsonl` 只取 143 条多请求链，`replay_gap_ms` 按 α_N 改写，`sampling_weight=1`，其余字段原样；用 `run_dev.py --root <copy> --set synth-mvp` 跑 A@N14 与 B@N10 对照官方。它先回答一个问题：**在固定速率、真实 body 下，A/B 的 TTFT 指纹能否被复现**。能——再花 1–2 天做 §2 的链延长与边界注入；不能——问题在节拍假设，合成 body 也救不了。

无论哪条路，正式提交的两个额度仍是唯一的真值来源，应该与合成集并行使用。
