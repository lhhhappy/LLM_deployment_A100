# Claude 进展：为什么 N@SLO 上不去，编排能做什么（2026-09-24）

每个数字标注**实测**（来自原始记录）或**推断**（模型估算，待验证）。

## 一句话结论

**我们的服务在正式压测里 N10 时就已经满载。** 再加 N 不会多做活，只会让每个请求多等。多等的时间落在哪一道门，决定 N 能到多少：
- 我们现在的配置把 decode 保护得很好（tpot_mean 0.017，全榜最低），所以多等的时间几乎全落在首 token（TTFT）上，N18 就挂了；
- 榜首在 N26 时 TPOT 是 0.04–0.055，说明他们让 decode 吸收了这部分等待。

编排能做的是两件事：
1. 把等待从 TTFT 挪到 TPOT 的余量里（已写成补丁 122）；
2. 把每秒能做的活做多（更大的块、缓存复用）。

下一道墙可能是 KV 容量。

## 1. 负载是闭环的：满载后加 N 只加等待

### 压测怎么发请求（读 `s1-dev/harness/s1_loadgen.py`）
N 个槽，每个槽顺序回放一整条会话链：上一个请求完成，等一段"思考间隙"，再发下一个。所以服务慢，请求就发得慢。

这类系统有一条恒等式（Little 定律的闭环形式）：

`N = 吞吐 X × (等首 token + decode + 间隙)`

- 服务没满时，加 N 会加吞吐；
- 服务满了，X 固定，每多一个 N，每个请求平均多等 1/X 秒。

### 开发集验证（实测）

| 运行 | 墙钟 | 平均在飞请求 | 其中等首 token | 其中 decode | 在间隙中 | 合计 vs N |
|---|---|---|---|---|---|---|
| 045r B@N10 | 1217 s | 7.3 | 1.9 | 5.4 | 2.5 | 9.8 / 10 |
| 044r A@N14 | 1226 s | 11.1 | 3.8 | 7.3 | 2.5 | 13.6 / 14 |
| 042 S1@N22 | 1166 s | 17.4 | 2.0 | 15.3 | 2.6 | 20.0 / 22 |

- 恒等式对得上（尾部槽位变空，合计略低于 N），说明这笔账可信。
- 三档 N 跑完同一份 722 条、约 10M 未命中 prefill token，墙钟都约 1200 s。这说明开发集在这些档上都是服务端满载：N 越大，排队越多，吞吐不变。044r GPU 平均利用率 93%（实测）。
- 这也解释了 S1@N22 为什么 TTFT 能过、TPOT 挂：它把多出的等待都放进了 decode（15.3 个流同时在 decode）。

### 正式结果里的同一现象

实测，来自 `scripts/official_status.sh` 的返回：

| 提交 | 通过档 | tpm_all | tpm_decode | tpot_mean | 平均在 decode 的流（推断 = decode tok/s × tpot） |
|---|---|---|---|---|---|
| A 45979 | N14 | 1,757,558 | 20,547 | 0.0174 | 6.0 |
| B 45980 | N10 | 1,759,336 | 20,450 | 0.0121 | 4.1 |

- N10 与 N14 的吞吐几乎完全一样（差 0.1%），两套配置也不同。**推断：正式负载下 N10 时我们已满载。** 否则 N14 的吞吐应该多约 40%。
- 这只有两个点，且配置不同，不是严格的同配置扫描。但方向和开发集一致。
- 榜首 N26 的 tpm 为 1.46–1.61M，比我们还低（用户转贴），TPOT 为 0.04–0.055。他们并没有"更多吞吐"，而是把等待放在了 decode 上。

### 粗算：如果让 decode 吸收等待，N 能到多少（推断）

以正式 A@N14 为起点，假设吞吐不变、TTFT 与间隙保持 N14 水平，多出的等待全进 decode：

`tpot_mean(N) ≈ 0.0174 × (N/14 − 0.57) / 0.43`

| N | 18 | 22 | 26 |
|---|---|---|---|
| 推断的 tpot_mean | 0.029 | 0.045 | 0.061 |

- 我们现在 p95/mean 约 2.1，p95 ≤0.10 要求 mean ≲0.048，对应 **N22 可能过、N26 临界**。
- 与榜单的对照：N22 那几名是 0.027–0.052，N26 是 0.040–0.055。量级吻合，但是不同系统，只能当旁证。
- 这是一个模型，不是承诺。它假设：满载吞吐不变（实际上 decode batch 变大会更省，可能更好），TTFT 能守在 N14 水平。

## 2. 编排怎么做：补丁 122（按 TPOT 进度决定 prefill 预算）

### 为什么是它（实测，044r）
- 0/722 条 TPOT 超 0.10，中位请求还有 11 s 停顿预算没用；
- 79% 的 prefill 在 ≤4096 的小块里做；
- 满载下 4096 块周期 0.446 s、8192 块 0.739 s（有效 9.2k→11.1k token/s）。

### 机制
借鉴 Sarathi-Serve 的"按延迟目标定每轮 token 预算"。改动：按每个请求实测的出字进度记账（我们的门是每请求平均 TPOT）。
- 只要所有在出字的请求都没落后于目标进度（0.085 s/token），就做一整块 prefill；
- 否则 decode 一轮攒余量。
- 块内优先给等待中的缓存命中短请求留位置。

8 个 GPU 进程先对齐一次时钟再决策，避免分歧。它正好是第 1 节说的"把等待挪进 decode"，同时用大块把吞吐做高。

### 状态
- 补丁：`patches/122-tpot-paced-prefill.patch` 与 `.md`，提交 869ff66。默认关闭；关闭时与正式 A 逐步一致（CPU 测试）。
- CPU：真实调度代码上 35 个测试通过。
- 仿真（假成本模型，不是成绩预测）：冷请求 TTFT p95 降 30–45%，TPOT p95 约 0.08。
- 仿真推翻过我自己的第一版：见缝插针算小块反而更慢，已改为只算整块。
- 限制：只适合有 MTP、TPOT 有余量的部署。没有 MTP 时它会优先守 TPOT，首 token 变差。
- 会把 tpot_mean 从 0.017 抬高。只有 N 提升时这才划算：排名先比 N，N 相同才比 TPOT。

### 能推翻它的观测
8 卡上，A+122 在同档：
- 首 token 各门没有改善；
- 或 TPOT p95 超门；
- 或 `[ax-pace]` 日志显示块并没有变大。

## 3. 下一道墙：KV 容量（推断，需实测）

decode 吸收等待，意味着同时在飞的请求变多：正式 A@N14 约 6 个在 decode，N26 可能到 20 个以上。每个在飞请求占着自己整段上下文的 KV。

- 正式 A 的 KV 池是 1,036,288 token（实测，启动日志；bf16 KV + MTP）。
- 开发集平均 prompt 约 47.6k token（实测）。24 个在飞 × 47.6k ≈ 1.14M，已超过池子。
- 正式链平均约 15 个请求，上下文可能更长。
- 超了之后，空闲会话的前缀被淘汰，下一轮重算，活变多，形成恶性循环。

044r 在 N14 时 KV 使用率峰值已到 0.89（实测）。这需要 Codex 那边一起算账：
- KV 用 fp8（数值风险，要能力门复核）；
- DCP 分片（041 故障未修）；
- mem-fraction 与 MTP 草稿模型的显存；
- KDA 状态槽数。

我这边能做的是按"会话还会回来"来淘汰缓存，但这只是省活，不增加容量。

## 4. 校准：开发集比正式严多少（实测，044r/045r）

两套正式通过档，在开发集同档都没过：
- 首 token 各门的 p95 约为官方的 2–2.6 倍；
- A、B 谁好谁差，两边一致。

所以开发集只用来比较我们自己的配置，不要求"开发集全过"。详见 `notes/experiments.md` 校准节。

## 未知与风险
- 正式负载的满载点只有两个配置不同的数据点支撑；如果正式其实没满载，第 1 节的推断要重做。
- 122 的块成本常数有一部分是推断（C0、C2）。闭环能纠正误差，但误差大时块会偏小。
- 抬高 tpot_mean 是有代价的赌注，只有 N 提升才值得。建议作为激进一档提交，稳定一档保留 A。
