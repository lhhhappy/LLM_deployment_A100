# Claude 进展：N@SLO 与编排（2026-09-24）

每个数字标注**实测**（来自原始记录）或**推断**（模型估算，未验证）。本页是 Claude 的分析；复核边界见 [collaboration.md](collaboration.md)。

## 结论（收紧后）

- **实测：** 压测回放是闭环，开发集上的槽位账对得上。正式 A、B 在开发集同档都失败。044r 里 TPOT 余量大，失败集中在首 token 排队；79% 的 prefill 走 ≤4096 的小块。
- **待验证的假设：** 服务满载后，加 N 主要增加每个请求的等待；N@SLO 取决于这部分等待落在首 token 还是 decode。现有数据不足以证明正式负载在 N10/N14 已满载，也不能说明其他队伍怎么做。
- **编排候选：** 补丁 122 按每个请求实测的出字进度决定 prefill 预算，目的是用 TPOT 余量换首 token，并用整块提高 prefill 效率。CPU 与仿真通过，8 卡未测。

## 1. 闭环负载（实测）

`s1-dev/harness/s1_loadgen.py`：N 个槽各自顺序回放一整条链。上一请求完成，再等回放间隙，才发下一条。闭环系统满足：

`N = 吞吐 × (等首 token + decode + 间隙)`

开发集核对（在飞/间隙为时间平均的槽数）：

| 运行 | 墙钟 | 在飞 | 其中等首 token | 其中 decode | 间隙 | 合计 vs N |
|---|---|---|---|---|---|---|
| 045r B@N10 | 1217 s | 7.3 | 1.9 | 5.4 | 2.5 | 9.8 / 10 |
| 044r A@N14 | 1226 s | 11.1 | 3.8 | 7.3 | 2.5 | 13.6 / 14 |
| 042 S1@N22 | 1166 s | 17.4 | 2.0 | 15.3 | 2.6 | 20.0 / 22 |

- 合计略低于 N，是尾部槽位变空造成的；这笔账可以用来拆时间。
- 三档跑完同一份 722 条、约 10M 未命中 token，墙钟接近。044r GPU 平均利用率 93%。这与"开发集在这些档已满载"一致，但墙钟也受最长链影响，不是单独的证明。
- 042 首 token 门都过、TPOT 挂：它有 15.3 个流同时在 decode。同一时间账里，等待可以落在不同的门上。

## 2. 关于正式负载的假设（待验证）

- **实测：** A@N14 与 B@N10 的逻辑 tpm_all 为 1,757,558 与 1,759,336。
- **不能据此下结论：**
  - 逻辑 TPM 含缓存输入；
  - 两点配置不同，也不是同配置的 N 扫描；
  - 其他队伍 TPOT 较高，也不能说明他们把等待转进了 decode。
- **假设：** 如果正式负载在这些档已接近满载，给 decode 更多余量、守住首 token，可能提高 N。
  - 我曾用 Little 定律按 A@N14 粗算 N 与 tpot_mean 的关系。它依赖"吞吐不变、首 token 与间隙不变"两个未验证前提，只作为设计动机，不作预测。
- **验证方法：** 在同一冻结负载上，同配置做 N 扫描，看吞吐是否随 N 停止增长、等待落在哪一段。数据 Codex 的长链负载冻结后可以做。

## 3. 补丁 122：按 TPOT 进度决定 prefill 预算

说明在 `patches/122-tpot-paced-prefill.md`。

### 动机（实测，044r）
- 0/722 条 TPOT 超门，中位请求还有 11 s 停顿预算没用；
- 满载下一个周期：4096 块 0.446 s（n=1933），8192 块 0.739 s（n=43）。

### 机制
借鉴 Sarathi-Serve 的"按延迟目标定每轮 token 预算"。按每个请求的出字进度（目标 0.085 s/token）记账：
- 预测一整块的耗时放得进最紧那个请求的余量，才做 prefill；否则 decode 一轮；
- 块内给等待中的缓存命中短请求预留位置。

### 真实调度器边界复核（本轮）
| 边界 | 结论 |
|---|---|
| TP rank 一致性 | 决策输入（运行批、等待队列、续算请求）各 rank 相同；时钟在 TP CPU 组上取 max，各 rank 用同一值。collective 只在"有未完成 decoder 且有 prefill 待做"时进入，这个条件各 rank 相同 |
| MTP 产出计数 | 用 `req.output_ids` 长度；spec 路径在结果处理时 extend 接受的 token（`batch_result_processor.py:956`）。计数滞后只会让余量偏小，是保守方向 |
| overlap 首 token 未处理 | **修复：** 原版会跳过尚无输出的新 decoder，可能在它首 token 后插进一整块而不计账。现在按"刚出首 token"计入 |
| 等待请求长度 | **修复：** 真实 Req 的 `full_untruncated_fill_ids` 在准入前为空（`schedule_batch.py:974`），原版会把新到请求的待做量算成 0/1。改用 `seqlen`（origin+output）。原 CPU 测试的假 Req 把这个字段填满了，掩盖了问题 |
| 时间预算不足 | 连续 decode 满 32 轮后放行一整块。原版只放一个 256 的碎块 |
| 空批 / 仅 prefill 批 / 全部完成 | 直接按原路径走，不进 collective |
| 短输出 | 允许欠账 ≤ (0.10−τ)·(n−1)；n=1 的请求出首 token 即完成，不参与 |

### 测试：哪些调真实代码，哪些是仿真
- **真实代码：** 测试从正式 A+122 源码树中抽出真实的 `get_next_batch_to_run`、`_get_new_batch_prefill_raw`、`PrefillAdder` 等方法执行。模型、KV 池和 batch 是假的。
- **单元测试（11 个）：**
  - 关闭时与正式 A 逐步相同；
  - 预算算术；
  - 落后时的 decode 轮数；
  - 上限放行整块；
  - 等待请求 fill ids 为空；
  - overlap 未处理首 token；
  - rank 时钟一致；
  - 两个仿真断言。
- **120 原有 27 个测试：** 都通过。
- **仿真：** 同一套真实调度代码，加假时钟和假成本模型：C0=0.08 s，C1=60 µs/token，decode 一步 0.036 s，MTP 平均 3.3 token/步；泊松到达约 7.7k token/s。它只说明机制按设计工作：
  - 5 个种子上冷请求首 token p95 降约 30–45%，TPOT p95 约 0.08；
  - 第一版"见缝插针小块"在仿真中更差，已改为整块；
  - 无 MTP 仿真中首 token 变差。
- **不是性能预测。**

## 4. KV 容量（推断，需实测）

如果 decode 吸收更多等待，同时在飞的请求会变多。正式 A 的 KV 池是 1,036,288 token（实测，启动日志）。044r 的 KV 使用率峰值 0.89（实测，prefill 日志）。

平均 prompt × 在飞数不是物理 KV 驻留：前缀共享、复用和淘汰要从真实日志另算。122 的 8 卡运行里应一起记录 KV 使用率、在飞数和淘汰后重算量。
