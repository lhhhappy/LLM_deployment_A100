## Conclusions so far
- **035**: at N22 the only failing gate is tpot_p95. During heavy prefill a stream gets one decode step per 16k chunk
  (~1.3 s), so 28% of requests exceed 0.10 s/token.
- **036**: 114 is a clear single-change win (less prefill time per long-context token → less queueing and fewer stalls).
  **New baseline S1 = S0 + 114.** TPOT is still the only failing gate. Bad cases (`scripts/analysis/fetch_level.sh`):
  192 TPOT overs (26.6%); the worst streams sat through 40–60 prefill batches of 8192+ tokens while decoding; 217 of 869
  big chunks ran while requests decoded and nothing waited. All 7 fast_intra overs are own-cache losses (queue p50 0.6 s,
  execution 5.2 s). chain_start is the thinnest margin (17/22, queue p50 38 s behind other prefill) — the risk for any
  change that gives decode more time.
- Cache (R20, true token LCP on 026 N18): the recoverable same-chain loss is at most 850k tokens (8% of prefill). 146 of 411
  follow-ups continue the whole previous prompt (they need the prompt-end state); 61 of them found that state gone. 140
  evicts tail states first and skips the extra role slot when no slot is free (200 slots in S0) — the fix is in the patch.
