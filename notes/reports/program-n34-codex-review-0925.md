## 对阶段 0 和 Fable 解读的保留

073/074 实测说明本地开场有明显积压，提高 N 没带来同比吞吐增长。它不能单凭这一点证明 GPU 算子已饱和；固定 decode 穿插、CPU 提交和恢复也可能限制墙钟产出。38–39% 是带覆盖范围的模型估计，不能直接换算为去掉 decode 后的速度。

离线排序模型可以用于选择探针，但它忽略链内竞争、真实资源条件、缓存与闭环到达反馈；表中结果不是已证明的最优下限。252k / 9.2k ≈ 27.4 秒仅说明余量很小，不证明这种请求在当前吞吐下一定救不回。是否降级仍取决于到达、已等时间及实际剩余服务。

173 个比值符合 k/1788 是有价值的分母线索，尚未证明请求选取、TPOT 分母、开场是否计入以及窗口起止。TPM×60 接近常数也不能证明整个 cohort 都落在稳态窗口内。替身先校准，只作补充；不能据此贬低全量缓存压力。MoE 局部加速 1.5–2 倍也不等于全服务吞吐提高同样倍数。

冷块 4096 对 decode 延迟有保护作用，尚不能称“纯浪费”。先测现有 chunk=8192 下放宽上限，16k/32k 和 graph 范围另立实验。

## 123 多卡一致性：已复现的问题

各 rank 的 wait_queue_entry_time 来自本地 perf_counter；比较两个请求时共同 now 项抵消，只对齐 now 无法修复入队时间差异。真实排序函数中 1 ms 差异即可翻转两个请求次序，收据见 [反例](../../evidence/opening-q123-20260925/123-rank-order-counterexample.json)。

接口采用 request-plane CPU group 的首 rank 计算、广播最终决定。所有 rank 必须在相同分支进入；回调只返回小型可序列化决定，不能假设回调修改的本地状态也被广播。Q4–Q6 可复用，分别应用排序、暂缓标志和节拍状态。

## Q4–Q6 设计意见

Q4–Q6 基底 83197755 含 120 修复，与 074 不同；开始前要明确对照基线。以下不阻止 075–077。

**Q4：**“命中不足一半给 30 秒，否则 5 秒”是在线启发式，不是官方桶，遗漏 fast 3 秒与 turn 15 秒的区别；不得读取冻结 phase 或链身份。成本 α+rβ 对长请求遗漏每块固定开销，应至少考虑 ceil(r/chunk)·α、上下文和恢复状态。071 的 122on/8192 成本不直接适用于 074 的冷4096。估计过高同样可能把可救请求误归为无望，降级必须可恢复且观察饥饿。固定 now 不足以统一 w，应广播最终顺序。

**Q5：**停车不等于能接上别的请求。120 的搭车资格目前要求 device 短命中，短冷请求未必有资格；必须确认真实可接纳路径，避免停下 owner 后无人能入批。也不能用改变引用/分配状态的正式函数偷偷作无副作用资格探测。保留状态会继续占 KV/KDA，最多暂停 8 轮不是墙钟上界。沿用 120 已修好的“只有真实入批才加 inflight/传 chunked_req/扣 pending”边界。

**Q6：**完成请求的服务端 TPOT 计数有滞后，且不同于客户端 SSE TPOT，只能作反馈护栏，不能保证客户端 p95。服务端不知道 harness 的“本档”何时开始；若引擎复用，计数重置边界必须明确，不能读取评测 phase。固定 40 条不适用于任意分母，应同时记录实际分母、尚在运行且有风险的请求及最长停顿。吞吐、阈值和计数都应由首 rank 决定并广播，计入 CPU 同步成本。此次基线 122off，明确它与固定 interval、120 decode_due 的优先关系。

## 积压曲线口径

到达账使用实际 raw 的 prompt−cached，不用冻结 uncached_expected。逐批日志的 new-token 是按页向上取整的计划工作，并非逐请求真实未命中。报告保留真实到达账、按页服务账、padding 修正及排空终点残差；有余项就显示未知，不能把负差额截成零并宣称精确清空。批次日志时间也不是 CUDA 完成时间，曲线明确标为离线重建。
