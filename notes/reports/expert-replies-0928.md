## 专家一（工程与契约视角）

- 目标是超标条数，不是 chain p95。每个机制第一行：救回 X、新坏 Y、净减少，开场/稳态分开。
- 下一处机制：块边界暂停巨头，让可救链首连续完成 prefill；第一版只允许"一条运行、一条暂停"，只暂停"确定无救"的请求（已过截止或乐观估计也赶不上）；无救不等于永久冻结（可能生产前缀、必须最终完成、不能碰覆盖率与 1200 s 无事件超时）。
- 先做逐块反事实：S1 下那条 35k 等 35.8 s 的请求，在本轮配置（132 + 浅前缀修复）下是否已经能救；不能拿旧配置的坏例当新配置的病因。
- 暂停 ≠ 释放，恢复 ≠ 重新提交。契约：已完成位置 L 表示真正提交的 token 数；MLA KV/DSA 缓存与 KDA 状态对应同一 L；请求到槽位映射暂停期不释放；旧批次回调不能把暂停请求误当完成/decode/再释放；abort、排空、flush、异常清理都能发现暂停请求且只释放一次。单 chunked_req 假设散在上一批次过滤、缓存暂存、未完成块计数等路径，重点审 get_new_batch_prefill、PrefillAdder、上一批次收尾、请求池释放。
- KDA 最危险的错误是状态位置与调度位置差一个 token（公开案例：恢复完整状态但调度只承认 L−1）。驻留暂停边界与可复用检查点边界（256 网格）不必等同，首版保留原请求的活状态。
- TP8：暂停/恢复/算到哪里由同一权威决定并广播；overlap 下 CPU 到块边界时下一块可能已安排，切换点要停止继续安排 A 并等状态提交依赖。
- 块大小：16k 比 8k 只省 8%（1180→1085 ms），固定开销次数减半不是总成本减半；"每第 k 轮让路"没有绕开两条 partial；便宜的中间方案是"救援时允许一次完整完成块略超 16k"，先离线统计剩余坏例里有多少是略超单轮门槛。所有判断用实际剩余工作（恢复 + 实际未命中后缀 + 尾部处理），不用原始 prompt 长度。
- 容量：自动配置按内存比例分状态池，不按实际使用；411→779 要用启动日志算平；"峰值 110"要核是否含缓存检查点/跟踪缓冲；400 槽不能凭容量收益进候选（chain 6→8 的回归要先消失）；物理容量预算与执行准入预算分开，新增显存优先保留前缀，不能变成"更多巨头立即入批"的许可；host 层优先保留活跃会话最后一个完整可恢复的混合检查点（KV + 对应 KDA + 一致位置），扩 host 前核清每进程/整节点口径与恢复关键路径。
- TPOT p95：按逐请求剩余预算 B_i(t) = 0.10(n−1) − (t − t_first) − 剩余 decode 估计 来交错，不按固定轮数；示例 n=16 时一次 1.085 s 停顿就超；不延迟首 token、不改时间戳、不合并 SSE。
- 执行层：118 已量到 17.6→16.1 s 但 chain 6=6；MoE 25% 自身省 25% 只省总 6.25%；mHC 14% 值得查；all-reduce 看关键路径暴露的等待；A100 无原生 FP8 计算，FP8 KV 先当容量方案；缩 top-k 是改模型计算；"模型略笨换速度"排在驻留让路之后；榜首 tpot 50 ms 不能证明其关 MTP。
- 两个约束：开场（初始排序与总工作量，最短优先近似最优）与稳态让路是两个问题；防饥饿用绝对年龄，停车不重新计时，维护到下一个 SSE 事件的安全余量。
- 验证三关：状态正确性；机制是否覆盖剩余坏例（逐次让路记录、救回的请求 ID）；同 cohort 完整结果——闭环负载下同 ID ≠ 同到达，判定用完整派发与排空，配对用于解释；本轮上传配置若无 rot150 基线，不能宣称"相对上传配置有配对净收益"。
- 顺序：核清剩余阻塞是否越过单轮停车 → 一暂停一运行 + 逐请求 decode 预算 → 过关后带回 400 槽与复核过的 118。证据支持"减少不可打断的巨头阻塞"是下一处机制，但不足以给 N30 成功概率。

## 专家二（读了我们调度器代码的视角）

- 榜单：榜首四队 N34、tpot 0.037–0.051；我们 N26、0.025，还有约 2 倍 decode 时间可让给链首（均值到 0.045 时 p95≈0.079）；TPM 各队 1.4–1.7M，由链的思考间隔主导。
- 三笔账：开场 30 s 内通道最多算 39 万 token，最短优先已最优，N30 开场估计漏 11–19、N34 13–15、N38 17–19，稳态必须 ≤12–15 → 稳态抢占必须做；tpot 账：输出长度 p50 198 → 可容忍总停顿 13.8 s，250k 头入批后 16–17 s 期间输出 ≤250 的请求必超 0.10（全程重叠时 decode 份额 f 需 ≥30%），服务端准入时精确知道 n；通道账：抢占只改顺序不加工作，优于配额让路与一轮大块救援。
- Q1：现有停车（ax_continuation 放不下就 return req；partial 的 KV 每块 stash 进 radix 树并加锁；KDA 状态留槽；停车期不执行 kernel）→ 多轮停车不需要新的 KV/KDA 契约，缺的是簿记（chunked_req 单字段、4216 assert、process_batch_result_prefill(chunked_req=…)、abort、pending token 计数、overlap 的 inflight_middle_chunks）。设计：活动 partial + 停车列表；可救头到达且活动 partial 判死（或 SRPT 更长）时切换；最后一块结束后恢复；决策为队列状态的纯函数，rank0 广播。工程量 200–400 行 + CPU 测试；风险在 overlap 簿记。停车巨头持有 ≤250k KV（约池 20%）+ 1 个 KDA 槽；饥饿用 600 s 与"无可救等待者即恢复"兜底。
- Q2：有多轮停车后块大小与小头等待脱钩，16k 保留；add_chunked_req 只在整个 256 网格单元放得下时切块，停车点永远对齐。
- Q3：779 的来源是统一内存池按字节共池，去 MTP 后草稿/spec 缓冲释放的字节按规则进了 KDA 槽数；未用的 KDA 字节对 KV 是死的（钉 400 后 KV 1.26→1.81M 证明）。**KDA 槽还存 radix 树的 KDA 快照，状态不能由 KV 重建，树里没状态等于整段重算**；钉之前数树里快照数；主机层按设备 KV:KDA 比例切，钉池会缩主机侧 KDA 份额（看 180 的截短计数）。容量不参与排序：把"放不下就跳到下一个能放下的"改成"队首放不下就等（完整短命中除外）"。主机层 --hicache-size 是每卡 GB（64×8=512 GB pinned），每卡 96 大概是上限；淘汰按会话保留"前缀末尾 + 该处 KDA 状态"。
- Q4：按精确截止时间分配 decode 并有意花掉 5% 允许额：deadline = 首 token + 0.10×(n−1)（留余量），slack = deadline − now − 剩余 token×30 ms；受保护请求的最小 slack 放得下下一块就 prefill 否则 decode 一步；slack 已负的不再保护。122 的骨架加精确 n，去掉估计与外推；决策 rank 一致。
- Q5：A100 无 FP8 tensor core，唯一 2× 算力杠杆是 INT8 W8A8（估计整块 10–15%，能力风险中等）；mHC 融合估计 7–10%（风险最低，优先）；通信重叠 3–5%（工程重）；不缩 top-k、不降 MoE 精度。
- Q6：顺序：多轮停车 + 可救者抢占 → 精确 tpot 截止时间 + 5% 允许额 → 钉 KDA 池 + 容量不参与排序 + 主机层按会话保留。
