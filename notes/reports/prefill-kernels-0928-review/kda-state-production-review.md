# KDA BV16 production source review (2026-09-28)

Scope: read-only inspection of the new worktree's `kda_state_sm80.py`, both `chunk_delta_h` wrappers, `kda.py`, `kda_triton.py`, backend arm site, and the proposed GPU test. No GPU was used for this review. The production BV16 run F is not yet part of this sign-off.

## Source conclusion

I found no source-level blocker in the guarded BV16 path. The actual recurrence bodies in `chunk_delta_h.py` and `chunk_delta_h_snapshot.py` are unchanged. The only selected-path changes choose the underlying JIT function instead of the one-config Autotuner and pass `BV=16`, `num_warps=4`, `num_stages=2`, `num_ctas=1`; they preserve the original grid function, arguments, in-place state update, `h` and `v_new` allocations, and snapshot side effects. The normal and snapshot wrappers default `sm80_bv16=False`; `chunk_kda` also defaults the forwarded keyword to false. `TritonKDAKernel.extend` emits true only after successful instance arm and on the same device. The backend arms only its selected Triton extend dispatcher, before capture. With the environment flag unset, `arm_prefill_state` returns before querying CUDA and the native Autotuner remains selected.

The warmup covers 12 compile-key combinations: normal recurrence vs snapshot kernel without export vs snapshot kernel with export, each with int32/int64 request-slot indices and `NT_BUCKET` 1/2. It uses BF16 k/v/w, FP32 gk and state, int32 `cu_seqlens`, int64 chunk offsets and snapshot metadata, `H=Hg=8`, `K=V=128`, and the same KDA booleans as `chunk_kda_fwd`. `T` is explicitly `do_not_specialize`; the true loop count is read from `cu_seqlens`. One tiny 64-token warmup thus runs the relevant code while compiling the long-request buckets, and the actual launches load CUDA modules. The flag refuses non-default shared GDN tile/warp/stage settings; shared GDN without this KDA opt-in continues through the original Autotuner.

The runtime guard limits use to 8k/16k, at most 3 sequences, BF16 contiguous k/w/u and FP32 contiguous gk, an FP32 state with exactly `(8,128,128)` inner layout, same-device aligned pointers, int32 `cu_seqlens`, int64 chunk offsets, and paired contiguous int64 `(N,2)` snapshot arrays. The state slot pitch is passed at runtime from `initial_state.stride(0)`, rather than inferred from the logical state shape; the guard accepts the contiguous pitch 131072 and aligned envelope pitches below 2^31. The kernel casts slot indices to int64 before multiplying this pitch. Production snapshot creation in `mem_cache/kda_dual_snapshot.py` produces int64 offsets/slots; `-1` inactive slot sentinels are already guarded in both recurrence kernels. The guard deliberately does not synchronize to inspect GPU values; sequence lengths and slot validity remain the existing caller contract.

The proposed `tests/gpu/test_kda_state_sm80.py` has useful independent gates: off/CPU/unsupported SM/GDN override; expected 4 normal plus 8 snapshot loaded entries; no first serving JIT/disk/module work; 12 combinations of index dtype, bucket and snapshot mode; extra ragged 8k bucket-2; BF16 `h`/`v_new` and *complete* FP32 state-envelope raw bits; two fresh graph replays with changed input, sequence boundaries, slots and snapshots; and unsupported-metadata fallback to the native Autotuner. In particular, the envelope-stride and zero-cache checks prove that the warmup pitch is in the same Triton specialization class as the tested serving pitch.

Remaining bounds: a first full-model serving run should verify the actual production k/w/u/gk and pool views hit the guard and record that F has no serving-time compilation. The current source guard is safe on an unsupported layout because it falls back to the native kernel. The local synthetic core gains cannot be treated as whole-prefill gains.

## Full-core production F raw sign-off

`kda-prepare-f` and `kda-prepare-production-test-f` both exited 0 with empty stderr. Every source hash in both environment records matches `evidence/prefill-kernels-0928/kda-production-f.tar`. F uses four independently armed real `TritonKDAKernel` instances (native, prepare only, state BV16 only, both), with the production wrappers rather than research overrides. All 16 `production_dispatch` records show exactly one `[True]` state guard decision for the two BV16 variants and none for native/prepare. The three-plane prepare check passes raw bits for both lengths. All 16 eager core numerical records and 16 fresh graph records report raw-bit equality for output, complete convolution envelope and complete SSM envelope. The ragged cases use int64 request slots and real int64 snapshot metadata; the single-sequence cases use int32 slots. Output storage equals logical output size for all 16 eager-memory records. Per-call peak tensor allocations are about 252 MiB at 8k and 504 MiB at 16k for every variant (16k N1 differs by only 28 KiB between native and other arms); this is *local core* peak, not retained model or graph-pool memory.

The clear negative eager 8k/3 result supports excluding that shape from the BV16 production guard. The 8k/1 eager gain is smaller and noisier than the captured gain, so it is an empirical choice rather than a robust 5% improvement. The 16k gains are consistent. These are complete synthetic KDA-core timings with fixed lengths, live state updates and paired randomized ordering; they exclude model projections, TP collectives and scheduler. If the 8k/3 guard is narrowed after F, F's source hash no longer identifies the final guard; a focused fallback test should cover the new boundary. B's initial driver-free delta must not be attributed to BV16 alone; the later controlled measurement follows below.

## Final narrowed dispatch and controlled memory addendum

The new `TritonKDAKernel.extend` cheap gate permits armed same-device BV16 only when `q.shape[1] == 8192` and `query_start_loc.numel() == 2` (one sequence), or when `q.shape[1] == 16384`. The unchanged downstream `can_use_state_sm80` guard then requires `cu` shape length 2–4, limiting 16k to at most three sequences and enforcing all dtype/layout/device/signature conditions. Thus 8k/3 falls through to native BV32, 8k/1 remains eligible, and 16k/1–3 remain eligible. Flag-off short-circuits before the new gate; no GPU scalar is read. This is a static inspection of the final source; F predates this one dispatch-only narrowing.

The controlled `kda-state-memory-a/receipt.tgz` (SHA256 `ffdbfd3372143a4fa71871084b4f6a9244e8c405a3d2cb89f856fbdd09662561`) exited 0 with empty stderr, and all seven archived source hashes match the run record. In one process/device it first loaded the matching 12 native BV32 signatures, then loaded 12 BV16 signatures. The native stage consumed 102,760,448 bytes of device-wide free memory and 23,068,672 bytes of PyTorch reservation; the subsequent BV16 stage measured **zero additional** allocated, reserved, and device-wide free bytes, with zero retained tensor bytes. A cached repeat also measured zero. This is a controlled incremental observation on that warmed device, not a guarantee of zero module/code cost in every fresh process. It supersedes any attribution of B's initial driver-free drop to BV16 alone.
