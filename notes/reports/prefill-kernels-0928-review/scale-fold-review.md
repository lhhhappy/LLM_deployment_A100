The `b` receipt supports a real but small local improvement. With the current 117 W13/W2 tuning, the *full synthetic FusedMoE* CUDA-graph median is 3.318620→3.229828 ms at 8192 rows (paired median 2.846%) and 6.563152→6.421220 ms at 16384 rows (1.967%). ## Receipt and numerical scope

- The actual run is [`moe-scale-fold-b.jsonl`](../../../evidence/moe-scale-fold-0928/results/moe-scale-fold-b.jsonl), with exit code 0 and empty stderr. Its archived probe SHA256 (`9a3af57c…`) matches the current `scripts/analysis/bench_moe_scale_fold_sm80.py`; the helper SHA256 is `9b584f21…`. The receipts archive SHA256 is `21354aaca4f31ecaa1785d6597d244e78fe6799cf96180b273e3c8edd5ef8d09`. I recomputed every SHA256 in its 156-entry manifest against the tar members; all match. The 157th tar member is the manifest itself.
- `cpu_check` exhausts all **17,280 nonnegative BF16 bit patterns from +0 through 255** times **254 finite FP8 E4M3FN bit patterns**, or 4,389,120 pairs. The GPU intrinsic kernel runs the same pair space on SM80 with `__hmul2` for both rounding orders and finds zero mismatches, including BF16 subnormals. It demonstrates failure at scale 256 (254 mismatches) and conservatively sends 256, -1, Inf, NaN to native. The generated Humming mainloop dequantization is bit-field `fp_to_fp<Float8E4M3,BFloat16>` followed by the `2^120` correction and group-scale multiplication, matching the probe's raw-bit construction. The private fold moves that correction to the reloaded group-scale register before repeated weight transforms. The exact arithmetic property applies to this guarded domain, not to arbitrary BF16 scales or all Humming modes.
- Both stages' loaded synthetic scales are BF16, positive and within 0.000488–0.001038. The checkpoint fixture quantizes synthetic weights through the actual `FusedMoE` loader; it is **not** the model's real checkpoint. The script checks W13 raw bits, W2 raw bits on the same native activation, full eager MoE raw bits, and two fresh-input graph replays against native graph plus fresh native eager at each M. The 16 recorded raw-bit checks are exact and finite. Fresh cases update `x`, top-k IDs, and top-k weights; captured graphs rerun live alignment. The eager full comparison pins alignment because the native atomic alignment is not order-stable. The fallback test changes the first scale to 256, checks the script's guard selects the native kernel ID, runs native twice, then restores the scale; it does **not** validate any production dispatch guard.
- Two domain corners remain outside the exhaustive proof: FP8 NaN encodings `0x7f/0xff` are excluded, while the research guard only scans scales; and BF16 negative zero passes `scales >= 0` but was not enumerated. The present finite synthetic checkpoint does not exercise these. A future production guard should reject unproved bit patterns or explicitly prove/test them before enabling the fold. No production guard or kernel change was made here.

## Binary isolation and measurement limits

The private native and fold header trees differ in exactly `humming/arith/mainloop_arith.cuh`; the archive shows only the compile-time fold branch insertion, scale-register bias, and removal of repeated weight correction. Both generated `kernel.cu` files for each stage are byte-identical except the first-line variant stamp. After normalizing the private include directory and cache path, native/fold NVRTC command arrays are identical (35 arguments, SM80, same flags). Parsed kernel configs are identical at each size: W13 M128/N256/K64, four stages, CTA hint 1; W2 M128/N128/K64, three stages, CTA hint 2; both indexed, BF16 activation/output, FP8 E4M3 weight, BF16 K128 group scale, FP32 accumulation, no stream-K. Native/fold kernel IDs and cubin hashes differ for both stages (`5f5d…` vs `6259…` W13; `fd2f…` vs `5297…` W2). Constructor memoization is evicted, compiled IDs stay referenced, and an assertion disallows JIT after both variants are prepared. This is good evidence of separate compiled kernels without tile/raster/config confounding.

The receipt has no `cuobjdump` on the GPU machine, so it has no SASS or register/resource counts. Distinct cubin hashes plus source/command isolation establish binary difference, **not** a measured count of eliminated HMUL2 instructions or a resource-pressure mechanism. Timing uses CUDA events around 16 graph replays, nine randomized arm-order rounds, then three eager timing repetitions. Full MoE includes alignment, both GEMMs, activation, and reduction; graph capture and scale guard are outside timing. Synthetic route/weight distribution, cached graph replay, one GPU, and lack of a whole-prefill run limit extrapolation. All 9/9 paired full-MoE gains are positive, but the absolute gains are only 0.089 and 0.142 ms.

## W2 N-stripe followed immediately by reduction: bandwidth account

For M tokens, top-k 9, BF16, intermediate 256, hidden 4096, the native W2 activation is `M×9×256×2` bytes: **36/72 MiB** at 8k/16k. Its `down_output` is `M×9×4096×2`: **576/1152 MiB**. A complete scratch write plus reduction read is nominally **1152/2304 MiB**. An N128 stripe is **18/36 MiB** of scratch, and N64 is **9/18 MiB**. [NVIDIA describes A100 L2 as 40 MB](https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/), without this probe measuring its usable cache capacity; a 16k/N128 stripe is already near that scale before weights and other state, so L2 residency is not guaranteed.

If N128 requires 32 sequential W2+reduce launches, the 31 additional full activation scans are **1116/2232 MiB** at 8k/16k—almost the entire **1152/2304 MiB** nominal scratch write+read that one could maximally remove. N64 doubles to 64 segments and 63 extra activation scans (**2268/4536 MiB**), worse than the removable scratch traffic even if every scratch byte were saved. These are upper-bound *traffic opportunities*, not measured DRAM counters: native W2 scheduling already has `n_id = mn_index % N_BLOCKS` inside an M block (`humming/scheduler.cuh:193–196`), plausibly reusing an activation slab across adjacent N tiles; sequential stripes sacrifice that locality. Activation plus stripe exceeds L2 at 8k/N128 and at 16k/N64; the full activation alone exceeds L2 at 16k. More launch pairs and repeating weight/cache traffic further weaken the case. The previous M-split full-MoE experiment was already slower (16k split into 4k: 9.238 vs roughly 7 ms), so splitting alone is not a free win.

The existing interfaces also make the stripe a structural change, not a tensor slice: `humming.py:get_buffer_metas` allocates a contiguous `(M×9,4096)` W2 output, and `_run_indexed_gemm` passes it to `moe_fused_mul_sum`. The current Triton reduction requires contiguous `(M,9,size)` input and uses `stride_m=9*size`, `a_base+n*size`, and output offset `m*size+k`. Humming's launcher requires exact contiguous B/C metadata; W2 packed weights and scales have physical 4096-wide N strides. A valid private prototype would keep physical B/scale strides, add an N-range to scheduler and compact stripe C layout, then add partial-output offset/stride to reduction while preserving top-k accumulation order and raw bits. The repeated activation traffic and 32/64 launch pairs make this a low-priority direction until a design can avoid the extra scans or fuse producer/consumer work within a persistent execution organization. No N-stripe performance claim has been measured.
