## KDA fixed-topology local graph

The graph captures one KDA core with fixed physical/logical M, sequence count, sum of ceil(length/64), and a conservative convolution maximum (`HostPlan`; ragged 8k example has 3 sequences and 129 chunks). It refreshes the same static `cu_seqlens`, chunk-index/offset, state-slot, prefix, and dual-snapshot tables before each replay; 3 fresh cases change sequence boundaries, slots, prefix flags, FP8-independent QKV/gate/beta values, and (in the snapshot arm) a disabled destination. It compares full output, full conv pool, full SSM pool as raw bits against eager, and separately checks untouched slots. The snapshot destinations are disjoint from active request slots and the new lengths stay under the captured conv grid bound. This is a meaningful **single-layer, fixed-topology** state/metadata test; it does not exercise layer-to-layer model inputs, TP communication, dynamic chunk counts, scheduler batch changes, or the full breakable graph pool in [SGLang #41105](https://github.com/sgl-project/sglang/pull/41105).

The temporary `explicit_tables` patch is scoped with `try/finally` and changes the three symbols used by this KDA call chain (`fla.kda.prepare_chunk_indices`, normal/snapshot delta-h `prepare_chunk_offsets`) plus the convolution wrapper's launch bound. `chunk_kda_fwd` prepares indices once and passes them down to gate, intra, recurrent and output kernels (`fla/kda.py:1103-1190`), so those callees do not query their own tensor-identity caches on this path. The ordinary `tensor_cache` uses input object identity (`fla/utils.py:103-139`); eager reference constructs a separate `cu_seqlens` tensor and warms it before timing, so it cannot silently reuse the graph's explicit tables. The captured batch's Python `extend_seq_lens_cpu` stays at its first topology, but Triton KDA ignores that keyword and the captured convolution grid is deliberately set to the maximum; replay kernels read the updated device `cu` and prefix tensors. This is valid only within the declared fixed topology.

**One controlled specialization difference remains:** `HostPlan.pack` stores *all* tables in int32, including `chunk_offsets`. The native `prepare_chunk_offsets` ends with `torch.cumsum`, whose output is int64 for int32 input (verified with Torch CPU). Values are well within int32 for these rows, so this is not an observed correctness fault, but the graph and eager delta-h kernels compile different pointer dtypes. A measured speed difference is therefore not solely graph replay versus eager launch organization. The performance agent was notified; a follow-up with an int64 offset buffer would remove this confound if the first run wins. The packed plan also assumes exactly two snapshot destinations and one 64-token chunk size; it cannot stand in for arbitrary #41105 bucket tables.

`graph_staged` includes CPU `HostPlan.pack`, a newly allocated pinned host tensor, async H2D of the packed table, D2D of raw QKV/gate/beta into graph-static input buffers, and graph replay. The CUDA event encloses the copies and replay; `host_ms` encloses host packing/allocation/launch, and `wall_ms` waits for completion. `graph_replay` measures a warm, already staged buffer. `eager_native`/`eager_cpu` share the same synthetic raw inputs and prewarmed native chunk-table cache. All arms reset conv/SSM pools **outside** timing, and projections, TP communication, scheduler, full-model mHC/MoE, and allocation/pool setup are excluded and disclosed. The pinned allocation is dropped after `copy_`; correctness of its asynchronous lifetime relies on PyTorch's pinned-host allocator/event tracking, not on an explicit retained Python reference. Three correctness replays and repeated staged timing probe this path, but a production implementation should own a pinned ring/event handoff explicitly if using another allocator or copy stream.

Memory reporting gives before/after allocated/reserved, a capture peak, explicit persistent bytes, and `memory_snapshot` segments matched to this graph pool. Treat `private_pool_bytes=None` or zero as *unavailable/unmatched* when allocator segment fields differ, not proof of zero graph memory. This is **one isolated graph's marginal memory**, not a per-KDA-layer cost. Neither multiplying it by 34 KDA layers nor equating it with #41105's approximately 22 GB larger **whole 16k bucket** graph pool is justified: full graph allocation lifetime, segment reuse, DSA breaks and number of captured buckets control that capacity. Conversely, this small graph cannot prove the whole model will fit 16k on 80 GB.

## Indexer tile probe

The probe calls the actual 113 `_unpack_prefill`, `_prefill`, then `topk_from_pooled_history_logits`; the reference wrapper `fp8_mqa_logits` uses config `(BQ=2,BK=128,GROUP=32,LOOP=4,warps=4)`. For a full 8k/16k chunk sharded across 8 attention ranks by 114, `nq=1024/2048` is the correct **equal per-rank row count**. The fixed `nk=65536` at pool size 4 represents about 262k prior tokens and thus models a late long-context block, not an 8k/16k cold-prefill block. The probe excludes the index projection, KPool gather/row packing, TP collectives and downstream sparse attention; its `scorer_topk` graph includes actual pooled top-k, but the speed percentage is still local.

The current stricter gate is sensible for the 117/113 numerical contract: it compares every FP32 score's raw bits against the production wrapper and then compares the **sorted selected token multiset**; a fresh graph run changes weights, shrinks `ke`, updates tail length, and requires the same raw score bits and selected multiset. `kpool_topk_transform.cuh::fast_topk_cuda_tl_impl` uses several `atomicAdd` reservations to write selected groups (`:112,129,169,187`), so output order is not guaranteed even for identical scores. The initial exact-index gate rejected native itself; the revised baseline-repeat check exposes this. Sorted multiset equality is stronger than merely checking equal scores but may still fail if the existing kernel chooses a different equal-score group at its threshold. If that happens, inspect cutoff scores and tie legality rather than silently weakening the numerical gate. Even the same selected set in a different order does **not** imply bitwise-identical downstream sparse-attention sums; real-weight TP8 output/service validation remains required. Root was notified. The earlier BQ4/8 variants changed last score bits, so keeping them out of timing is appropriate under the raw-bit gate; BQ2 GROUP/LOOP changes are a cleaner next arm.

Graph liveness looks sound for the shown code: Q/K/weight/scale/ks/ke, unpack buffers and external logits remain live through both captured phases; `retained[-1]` keeps the captured top-k output; each graph is replayed only while its buffers exist. The fresh test updates weight, `ke` and `seq_lens`, but leaves FP8 Q/K unchanged, so it does not independently prove the captured unpack reads *new* FP8 bytes. In-place Q/K mutation and a refreshed wrapper reference would close that gap. The scorer-only graph and scorer+topk graph are both timed by paired randomized CUDA-event replays, with telemetry around rounds. Capturing six variants at 2048×65536 retains at least six 512-MiB logits plus the 512-MiB reference (roughly 3.5 GiB before scratch/graph pools); the script currently reports kernel registers/spills/shared memory but no CUDA allocated/reserved/peak or private graph pool. Add per-case memory deltas before interpreting practical A100 fit, and do not multiply this isolated per-rank probe by TP8 or by model layer count without lifetime analysis.
