# KDA CPU logical-token length prototype: read-only review (2026-09-28)

Scope: `build/worktrees/prefill-kernels-0928/engine/sglang/srt/layers/attention/linear/kda_backend.py` and `tests/test_kda_prefill_cpu_length.py`. No KDA file was edited and no GPU was used in this review. Reference: [upstream SGLang #39688](https://github.com/sgl-project/sglang/pull/39688). This prototype extracts only its host logical-length idea; the upstream reported throughput combines projection and beta fusion, so its percentage is not evidence for this isolated change.

## Contract and finding

For ordinary EXTEND, the CPU sum has a defensible production invariant: `ForwardBatch.init_new` builds both `extend_seq_lens_cpu` and the GPU `extend_seq_lens` from the same host list (`forward_batch_info.py:900-922`); `compute_position_triton` writes each `extend_start_loc[i]` as the prefix sum of GPU lengths (`engine/sglang/kernels/ops/attention/position.py:6-53`); `HybridLinearAttnBackend._forward_metadata` appends the final GPU start plus final GPU length as `query_start_loc[bs]` (`hybrid_linear_attn_backend.py:247-255`). Padding extends the CPU list and GPU length tensor with matching dummy lengths (`forward_batch_info.py:1586-1600`). Thus `sum(extend_seq_lens_cpu)` should equal the device end even when physical `mixed_qkv.shape[0]` is padded. The helper's list/type/shape and `count <= physical_num_tokens` guards stop some malformed inputs, but do not dynamically prove equality if a caller changes the CPU list after the H2D copy.

**CP guard timing was found and corrected in the final prototype.** `EagerRunner._execute_extend` calls `attn_backend.init_forward_metadata` before the model forward (`eager_runner.py:352`); GLM-5's `_prepare_context_parallel_metadata` sets `forward_batch.attn_cp_metadata` inside `Glm5NextForCausalLM.forward` (`glm5_next.py:1537-1572`). The original metadata-only guard could therefore see `None` even for later CP work. The final helper also receives `get_parallel().attn_cp_size` at KDA initialization and returns `None` whenever it differs from 1, before examining the host lengths; it retains the metadata guard. The CPU test now covers the late-metadata case both by direct helper call and by AST-executing the real init hook with `attn_cp_size=2`, and passes. This conservative choice loses the host-length optimization on any CP>1 topology, even when CP is idle for a particular batch, but avoids guessing that layout. No KDA GPU run was performed by this reviewer; the performance agent reported four pre-guard non-CP GPU cases bit-exact with scalar reads 1→0. Those GPU cases do not exercise the added guard, whose effect is confined to CP>1 fallback.

Other boundaries look conservative: TBO child batches carry `tbo_parent_token_range` before planning (`two_batch_overlap.py:811`), so they fall back; SPLIT_PREFILL, DLLM_EXTEND, TARGET_VERIFY and DRAFT_EXTEND_V2 are excluded by the explicit EXTEND/MIXED allowlist. MIXED's running requests are converted into one-token extend tails before `ForwardBatch.init_new` (`schedule_batch.py:2924-2995`), so the same prefix-sum invariant should apply. Decode/verify graph replay uses `init_forward_metadata_out_graph` and `_replay_metadata`, which constructs a new `ForwardMetadata` without the prototype attribute (`hybrid_linear_attn_backend.py:288-306, 555-583`); the resolver falls back to the device scalar. BCG's eager metadata refresh constructs a new object per live batch; no stale count found there. The flag defaults false, and the resolver then executes the original `int(query_start_loc[-1])` read, although through one small Python helper.

## Test assessment and limits

`python3 tests/test_kda_prefill_cpu_length.py` passes four CPU tests; `python3 scripts/analysis/check_kpool_req_mirror.py` also passes independently. The CPU KDA tests cover ordinary/mixed/padded counts, default-off scalar read, rejected TBO/CP/spec/invalid lengths, and metadata hook placement. The GPU test is a useful isolated KDA operator diagnostic: it compares output and conv/SSM state bitwise, counts `aten::_local_scalar_dense`, and times both modes. It constructs `query_start_loc` and the host list from the same synthetic lengths, so it **does not validate the live `ScheduleBatch → ForwardBatch → backend` ordering**, nor CP/TBO/full graph behavior. It excludes projection and TP communication. Any scalar-count improvement should be reported separately from full-prefill speed.

Remaining syncs are material: `_forward_metadata` still evaluates `mamba_track_mask.any()` and track selection when enabled (`hybrid_linear_attn_backend.py:140-145`), and FLA `prepare_chunk_indices` retains its initial host list conversion. Removing `int(query_start_loc[-1])` only removes one per-KDA-layer scalar read when the guarded eager path is reached; it does not prove 34 syncs vanish on every request. A production decision needs a TP8 GLM-5.3-Flash prefill A/B at 8k and 16k with actual metadata, profiler scalar/sync counts, full chunk latency and output/state equivalence. Treat any gain from [#39688](https://github.com/sgl-project/sglang/pull/39688) as bundled, not this prototype's expected benefit.
