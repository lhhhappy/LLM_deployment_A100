# KDA Q/K/V prepare probe: independent static review

Reviewed `scripts/analysis/bench_kda_prepare_sm80.py` in `build/worktrees/prefill-kernels-0928`, against `kda_backend.py`, `kda_triton.py`, FLA `kda.py`/`l2norm.py`, and the causal-conv wrapper. I did **not** run GPU tests or edit the probe/engine. The implementation is a plausible default-off SM80 candidate, subject to its pending raw-bit gates and timing result.

## Formula, strides, and side effects

`forward_extend` first slices physical padding to logical length, runs the packed depthwise convolution, then splits its BF16 output into Q/K/V views of shape `(1,T,8,128)`. The convolution's `torch.empty_like(x)` preserves the channel-last transposed input layout; transposing its output back gives token stride `3*8*128`, head stride 128, feature stride 1. The probe's packed `[:,plane].unsqueeze(0)` has the same strides. `prepare_qkv` indexes `row//8 * STRIDE_T + row%8 * 128 + col` from each plane's own base pointer, so it reads precisely the BF16 rounded convolution result without crossing Q/K/V plane boundaries. Its output is three disjoint contiguous `(1,T,8,128)` planes.

The native `chunk_kda` path does `l2norm_fwd(q.contiguous())`, `l2norm_fwd(k.contiguous())`, and `v.contiguous()`. For D128, native `l2norm_fwd_kernel` computes FP32 `x / sqrt(sum(x*x)+1e-6)` rowwise and stores BF16. The proposed kernel uses the same formula, D128 row reduction, and BF16 store. It passes `use_qk_l2norm_in_kernel=False` to the original `chunk_kda`, which only suppresses those Q/K copies and normalization before the unchanged `chunk_kda_fwd`. Source Q/K/V and conv/SSM state are not written by the new kernel. The wrapper patch is scoped by `try/finally` and `TritonKDAKernel.extend` resolves the patched `kda_triton.chunk_kda` global at call/capture time. One launch handles three planes via grid axis 1, though the planes are separate CTAs.

The kernel guards tested shape `(1,T,8,128)`, BF16, equal strides, head stride 128, feature stride 1. Its `ROWS` mask covers partial last tiles. This is appropriate for a prototype. Production needs the same strict shape/layout/SM80 guard and a default-off flag. Triton may lower different BT/warps to different reduction trees despite the same expression; therefore only configs that pass the raw-bit gate should be considered. The direct preparation test uses zero vectors and tiny values, and checks all three plane bits against native for BT16/32/64 variants. **V has an avoidable exceptional-value gap:** current code converts every plane BF16→FP32→BF16, while native V is only copied. Finite BF16 values round-trip exactly, but NaN payload/signaling bits may not. Existing NaNs are placed only in padding that `forward_extend` slices off, so they do not test this. Keep V as BF16 for its `tl.load`→`tl.store`, or explicitly test and accept changed NaN bits before productionizing.

## Correctness and graph lifetime

The complete core test uses actual `KDAAttnBackend.forward_extend` with `TritonKDAKernel`, not a stand-alone normalization microbenchmark. It covers single sequence and a three-sequence ragged batch summing to T, prefix-state use, seven padded physical rows filled with NaNs, and two snapshots per ragged sequence. Conv/SSM state are envelope-strided views with extra untouched slots. Each variant resets both entire envelopes, checks the full output and full conv/SSM envelopes raw-bit equal to a native reference, then captures the same core. After capture, it changes raw QKV/gate/beta, reverses the live slot mapping, resets state, and checks each graph against a fresh native eager run. This catches stale input pointers, stale slots, snapshot destination mistakes, and accidental writes to untouched envelope cells. It also requires finite graph output. Fixed sequence lengths are intentional for this kernel comparison, so it does not validate dynamic topology replay.

The source `raw`, `gate`, `beta`, slot/prefix/snapshot tensors, backend state views, and both envelopes remain live across graph captures and replays. Each `variants[name]` keeps its `CUDAGraph` and returned output tensor, while the graph's private memory pool keeps captured intermediate allocations. The three temporary plane views alias one private output allocation only within an arm; no cross-arm reuse is visible. Capturing inside `override()` is sufficient because replay executes recorded CUDA work rather than re-entering Python. I found no evident dangling-reference or state-side-effect error in the current fixed-topology probe.

## Measurement and memory interpretation

The script warms the unchanged tensor-identity chunk metadata cache before comparing variants; all arms retain original KDA core kernels and differ only in the Q/K/V prepare section. It forces the CPU logical-token optimization on, with `_ax_cpu_logical_num_tokens=T`, so the older scalar D2H sync is not a candidate confound. It times complete captured core graphs with nine randomized rounds and eight replays per sample, with state reset and three warmups before each arm. Reset, telemetry reads, Python dispatch/capture, and JIT are outside GPU events. The eight measured graph replays **do not reset state between repetitions**: they measure steady fixed-input stateful replay after the first iteration, not eight independent fresh forwards. This is symmetric across arms and likely stable for fixed-shape kernels, but it must be stated when interpreting latency. Graph capture compares actual full core, not whole model prefill or all 34 KDA layers.

`eager_memory.peak_delta` resets peak accounting before one eager call and subtracts live allocated bytes just before the call. It captures transient allocations of that call, but retained native references and previously captured graph pools remain in the allocator as a variant-dependent baseline; it is not a clean absolute live-model peak or a 34-layer memory estimate. Compare deltas cautiously and inspect graph-pool/reserved separately if memory becomes a deciding factor. The script **does not time eager complete-core execution**. Because production KDA still has graph breaks, a graph-only gain is insufficient for a serving-prefill claim; follow any positive result with warmed eager core GPU-event and host enqueue timing under the same fixed metadata/cache conditions.

One reproducibility omission: `chunk_delta_h.py` and `chunk_delta_h_snapshot.py` freeze `GDN_CHUNK_H_BV=int(os.getenv("SGLANG_GDN_CHUNK_H_BV","32"))` at import, but this probe neither asserts nor logs that value. An inherited BV16 environment would silently change the claimed “native BV32” baseline. Record both imported constants and assert 32 in this baseline comparison. The BV16 agent's separate process does not inherently affect this run; the issue is the probe's unverified environment.

## Production wiring review (implementation in progress)

The new `engine/sglang/kernels/ops/attention/fla/kda_prepare_sm80.py` uses an instance-armed path rather than patching the global FLA `chunk_kda`. `KDAAttnBackend.__init__` arms only when its dispatcher's selected `extend_kernel` is the same `TritonKDAKernel` instance, after the model runner has set its CUDA device and before prefill graph capture. This avoids warming unused Helion/PTX/NVIDIA fallback Triton objects. `arm_prefill_prepare` exits immediately with the flag off, before CUDA queries; with the flag on it requires CUDA SM80. The hot `extend` path uses the prepared planes only after the helper checks BF16, identical `(1,T,8,128)` shapes for T=8192 or 16384, identical devices, token/head/feature strides `(3072,128,1)`, and 16-byte pointer alignment for all three planes. Other inputs still call original `chunk_kda(..., use_qk_l2norm_in_kernel=True)`.

The production kernel now loads V as BF16 and stores it without the prototype's FP32 round trip, closing the avoidable NaN-payload issue at source level; all-BF16-pattern raw-bit testing is still needed. Q/K keep native FP32 reduction/division and BF16 stores. A tiny `(16,3,8,128)` packed tensor has the same source strides and pointer alignment as the guarded serving path. `ROWS` is marked `do_not_specialize`, and all other constexpr/launch fields match, so the warmup should compile the same kernel variant. Static review alone cannot prove Triton's full cache key; the planned post-arm compile-count check at T=8192 and 16384 is the right verification. The `lru_cache` retains only device-index keys, no GPU tensors. No production source files were changed by this review.

The initial production helper allocated one `(3,1,T,8,128)` tensor. That would keep all three planes alive after Q/K die because `chunk_kda_fwd` passes prepared V as `o=v` to `chunk_gla_fwd_o_gk`, which writes into and returns that V tensor (`fla/kda.py:1185–1201`, `:870–903`). The amended helper allocates three independent `(1,T,8,128)` tensors and passes six pointers to the same one-launch, three-plane kernel. The returned V now owns only one plane: 16 MiB at 8k or 32 MiB at 16k, avoiding 32/64 MiB of extra retained Q/K storage. The GPU test asserts each returned plane's `untyped_storage().nbytes()` equals its own tensor bytes and that the three storage pointers differ. A new timing receipt is required because three allocations and six kernel arguments can change eager host/GPU latency.
