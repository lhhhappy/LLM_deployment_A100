## What was measured

For `Glm5NextForConditionalGeneration`, `glm5_next.py::_hc_pre` calls `mhc.py::hc_pre → _mhc_pre_dispatch → mhc_pre`; at M>2048, with DeepGEMM prenorm disabled, `mhc_pre` uses `mhc_pre_gemm_sqrsum_tilelang` then `mhc_pre_big_fuse_with_norm_tilelang` (`mhc.py:955-1129`). The synthetic probe executes the preceding `mhc_post_tilelang` too. Candidate split-K calls the **existing** `mhc_pre_gemm_sqrsum_splitk_kernel(...)[0]` (`mhc.py:587-671`) and passes its K partials directly to the same finalizer, avoiding stage 1, exactly as the current small-M production branch does. It has not yet been wired into large-M dispatch.

`SGLANG_OPT_DEEPGEMM_HC_PRENORM` has a generic default of true (`environ.py:1361`), but that default is **not** this Pod's effective setting. Both `130eznm` and `130eznn` queue jobs source `scripts/pod/jobs/dev_ladder_template.sh`; line 8 exports `SGLANG_OPT_DEEPGEMM_HC_PRENORM=0`, and their later `G_ENV` does not override it. The probe runner's `scripts/analysis/run_kernel_devbox.sh:22` also exports 0. `ax_mtp_sm80.py:26` sets 0 on its applicable EAGLE path, although the cited `130ezn*` jobs have `spec=-`, so that hook is not the necessary evidence. The model hook at `model_hook.py:344/349` belongs to SM120/HIP DeepSeek V4 and does not establish this A100 setting. Thus the TileLang native comparator matches the relevant **prenorm dispatch branch** for these jobs; no real-weight TP8 service A/B has yet been measured for the split-K change.

The A100-SXM4-80GB probe tests M=8192/16384, hc=4, H=4096, Fn=[24,16384], BF16 residual, FP32 Fn, and the complete `post → prenorm projection/square sum → post/comb mix + Sinkhorn + weighted sum + fused RMSNorm` boundary. It changes only split count/token tile/hidden tile, randomizes variant order for seven paired rounds, times 16 CUDA-graph replays per sample with CUDA events, and checks fresh changed inputs through the captured graph. The best tested config, `split4_m32_k128`, gives **0.8444→0.7693 ms at 8k (paired median 9.03%)** and **1.5797→1.4990 ms at 16k (5.12%)**; other configs do not consistently win, so no generic “split-K is faster” claim follows. Extra partial scratch for this config is 4.33 MB at 8k and 8.65 MB at 16k versus 0.82/1.64 MB native. These are one synthetic mHC boundary's GPU times, not complete prefill or serving gains.

The FP64 oracle mirrors the relevant formulas: it uses the BF16 output of `mhc_post`, FP64 GEMM and input square sum, normalizes mixes by the **pre-BF16** RMS of the post residual, performs the same initial column normalization plus 19 row/column Sinkhorn passes, computes the weighted sum in FP64, takes the output RMS from the **unrounded** weighted sum, then rounds that sum to BF16 before applying RMS scale and BF16 norm weight. This matches `mhc_pre_big_fuse_with_norm_tilelang:844-948`, which accumulates `ol*ol` before storing `T.bfloat16(ol)` to shared memory. The 8k best config's sampled FP64 relative L2 errors were approximately 5.12e-5 (post), 7.14e-5 (comb), 5.60e-4 (normalized output); 16k output was 5.40e-4. The comparison samples only 32 rows from each M, with random synthetic weights/state, relative L2 rather than max/bitwise error. It is a sound local arithmetic check, not a model-quality or full-state proof. Run artifacts and source/probe SHA256 (`29de6524…`, `e52a6018…`) agree with the local reviewed files.

## TileLang “data race” warning: generated-store analysis

The compiler warns that `sqrsum_partial(by,t)` and `out_partial(by,t,j)` can receive concurrent writes from loop `i`; an example sets `num_tokens=1`, `i=0/1`, `t=0`, `tx=0`. This warning cannot be dismissed from source-level `T.Parallel` alone. I inspected the generated CUDA for all six split variants: the 32-token files use the same store mapping, and the 64-token file has a corresponding mapping. Two representative generated files are cache keys `09441142…` (32-token, SHA256 `fde2473e…`, stores at lines 169–180) and `eb2711ef…` (64-token, SHA256 `0c443636…`, lines 175–186) under `cache/tilelang/0.1.12/linux-x86_64/kernels/`.

For token block 32, the actual `sqrsum_partial` store is emitted only for `((tx&3)*2 + tx/64)==0`, i.e. `tx∈{0,4,…,60}`. Its row within `blockIdx.x` is `16*((tx&63)/32)+8*i+((tx&31)/4)`, `i=0,1`, covering each row 0–31 exactly once. The `out_partial` store is a `float2`; its row is `16*((tx&63)/32)+8*(i&1)+((tx&31)/4)` and its first column is `16*(tx/64)+8*(i/2)+2*(tx&3)`, for `tx=0..127`, `i=0..3`. Every `(row, two-column pair)` is unique and covers 32×16 pairs. For token block 64, `sqrsum` uses row `32*((tx&63)/32)+8*i+((tx&31)/4)`, `i=0..3`; `out` uses row `32*((tx&63)/32)+16*(i/4)+8*(i&1)+((tx&31)/4)` and first column `16*(tx/64)+8*((i&3)/2)+2*(tx&3)`, `i=0..7`. CPU enumeration of all 128 threads and every emitted loop iteration found 32/64 unique square-sum stores and 512/1024 unique `float2` stores respectively, with zero duplicates. `blockIdx.x` adds a disjoint token block, `blockIdx.y` a disjoint `num_tokens`-stride split plane (and 32× that for `out`); the emitted `t<num_tokens` predicate removes tail writes. In particular, in the warning's `num_tokens=1` example, `tx=0,i=1` targets row 8 and is masked off, rather than racing with row 0.

**Conclusion for these compiled global partial stores:** the generated CUDA has one writer per address for the tested token blocks, so the TileLang source-level warning is a false positive after lowering. This is narrower than a general statement that the kernel is race-free: it does not inspect every shared-memory or pipeline operation, every TileLang version, or other tile shapes. Keep the candidate as research; do not globally disable the race checker. Before a production dispatch change, capture generated CUDA hashes for the chosen specialization, run a targeted race sanitizer/fully initialized scratch stress test if available, compare all rows and outputs/states on real weights, and remeasure the whole prefill/TP8 service.

## Next optimization direction

The current split-K is a credible **small local gain** but leaves a large BF16 post residual written to and reread from HBM (M×4×4096×2 bytes: 268 MB at 8k, 537 MB at 16k) between `mhc_post` and prenorm projection. A larger execution-only direction is a tile-matched post+projection kernel: compute a BF16 post tile once, write it for the later weighted-sum/state path, and keep the same rounded tile in shared memory for the split-K projection and square sum. Each hidden split owns a disjoint slice, avoiding duplicated post work; the finalizer remains unchanged. This is substantially more work than selecting split-K and must be compared with the earlier slower scalar-FMA post/prenorm prototype, but it attacks the repeated HBM read rather than merely changing the GEMM K schedule. No speedup is claimed for it yet.
