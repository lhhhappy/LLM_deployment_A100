## 122 实际改了什么

已核对冻结提交的 `scheduler.py::_ax_pace_should_decode/_ax_pace_limits`，不是从当前更新后的源码反推运行。

1. 069 用固定 decode interval=2 和冷块上限4096；071 的122替代这两者，按正在解码请求的进度计算可花在 prefill 上的时间余量，τ=.085。
2. 用 `C0 + tokens×(C1+C2×context)` 估成本；能容纳整块/剩余工作才放行，否则先 decode。默认希望凑8192块，减少重复前向固定成本。
3. 给可完整入批的 device 短命中留 token 预算；不会仅因为 host 命中就解除120的恢复资格限制。没有更改LPM排序、单partial、KV/请求槽准入或full锁存。
4. overlap 下扣除在飞 prefill 的预测成本；有 decoder 与待处理 prefill 时，每次决策额外一次TP CPU all_reduce。其耗时没有实测。
5. 最多连续32次 decode 后强制放行，且成本/锚点存在误差；τ不是TPOT硬保证。

本窗口真实日志有1008个prefill批、5,716,672个新token，439批≥8192。相同经过时长的069日志为1482批、
5,524,864新token、仅6批≥8192（其中900批为4096）。**这里只证明批形态确实变了**；闭环下同一时间段的请求集合不同，
不能把批数减少32%等价成性能提高32%，也不能把日志token直接等同已完成请求的token账。

07:54:13–08:09:36 的122累计计数差：4651次决策、2686次选择先decode、guard=0。
计数是次数，不是耗时。在这个近似对齐区间，有1965次“不要求先decode”的决策、991条prefill批日志；
122放行不保证后续准入成功。需要定位的是放行以后哪些资格/容量门仍拒绝请求，而不是只继续扩大预算。
边界日志只有秒精度，这个差额不作为精确拒绝次数。

- `partial_host_restore`主导：研究有界host准备/准入，保留状态完整性与容量约束。
