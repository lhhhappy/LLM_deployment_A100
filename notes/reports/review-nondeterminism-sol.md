# 正式 A 首 token 自比分叉：只读源码审查

- 049/050 的 ref1/ref2 都是正式 A；171/172 候选未加载。`reference-review.json` 分别 13/16、15/16 严格筛查失败；050 的冷 37 在 token 0 分叉。049/050 输入 token 数及 `cached_tokens` 相同，不能把其后不同历史的 logprob 差当局部数值误差。
- 051 在同一服务中每次成功 `/flush_cache` 后单 token 重复：冷 37 首 token 为 `[7,5691,5691]`；第一次 top1/top2 概率完全并列，后两次差 0.125。冷 256 首 token 不变，但首 token logprob 最高相差 0.263；数值摆动不只由采样随机数解释。`/flush_cache` 失败在 HTTP 层返回 400（`http_server.py:980-994`），脚本的 urllib 会抛错。
- **KDA 状态闭环未见明显冷槽漏清。** 新槽在 `memory_pool.py:1355-1368` 标 `mamba_needs_clear`；`schedule_batch.py:2864-2883` 收集 clear 索引；`model_runner.py:1671-1708,1755-1760` 在 extend 前向同流清理；`memory_pool.py:961-989` 清 conv 和 temporal。`kda_backend.py:735-763` 冷请求的 conv 不读旧状态，KDA chunk 仍接收 temporal，所以若要排除状态读，需在首层前验证对应物理槽全零。`flush_cache` 重置 allocator/radix，但不逐字节清池；正确性依赖每次新槽 clear。
- **mHC 为最具体的未证实读边界。** GLM `hc_mult=4`，故 `hc_mult3=24`（`glm5_next.py:720-739`）；默认 TileLang PRE 开（`environ.py:1362`），<=2048 token 用 split-K（`mhc.py:1031-1064`）。kernel 声明 `fn[24,H]`，却分配 `fn_smem[32,hidden_block]` 并 `T.copy(fn[0,k_base+...], fn_smem)`（`mhc.py:609,629-650`）。TileLang 是否自动对第 24–31 行掩码未由源码证明；后续只消费前 24 行，因此也未证明它造成输出分叉。先以单变量 `SGLANG_OPT_USE_TILELANG_MHC_PRE=0` 对照相同单 token 冷 37/256/text_short，每臂至少三次、逐次记录首 token top10；若 TileLang 臂独有摆动，再用 standalone `fn` 哨兵/内存检查及中间张量定位。比较臂内稳定性，不把两种实现的平均差当故障。
- **DSA 小请求路径需定点观察，尚无确定漏写。** 114 行切分仅在 `n_rows>=1024` 启用（`114-indexer-row-shard.patch:13-21`），不能解释冷 37；110 的 sm80 ragged 输出虽用 `torch.empty`，`_ragged` 对所有有效 `(q,k)` 写回（`110-sm80-dsa-indexer.patch:371-412`）。下一步若 mHC 对照仍摆动，在同一请求的逐层 DSA indexer 输出 topk 和层输出做 hash，找第一次分叉层；不要直接把 topk 近并列或 empty 分配判为未初始化读。
- 170 breakable prefill graph 需要显式 opt-in；049/050 启动参数没有 `--cuda-graph-backend-prefill breakable`（`official_a_171_num.sh`、049 job.log），本次不能归因其 eager 桥/静态 buffer。MTP 在正式 A 开着，但 051 的 `max_new_tokens=1` 已把后续多 token 解码历史从观测中剥离。
- **结论：已证实同配置首 token/logprob 可摆动，未找到可定罪的跨请求未初始化读。** 最高价值最小隔离是 mHC PRE 单开关臂内自比；随后用首层前 KDA 状态零值与逐层 DSA/topk hash 定位。以上均由执行层排队实施，本审查未动 GPU、服务或候选补丁。
