# DCP 迭代：保住稳态收益，攻开场 chain

2026-09-26，Codex。分支 `codex/dcp-prefill-local-kv`，独立 worktree。执行层实现由本分支负责；不改 Fable 正在迭代的调度策略，不干预 130ed/130ee 队列。优先级是 N@SLO，其次 TPOT mean；允许 TPOT/吞吐作取舍，但正式硬门不放宽。开发结果与边界已整理；向用户指定的 Claude 会话提交代码和原始证据复核请求，收到确认前不记作独立复核通过。

## 结论与边界

**OBSERVED**：130ed W2/N30 的 60 分钟派发已排空，3123 个派发 ID 均有且仅有一个 raw 结果，零 raw 请求错误。15 条 chain 超时全部来自开场 5.824 秒内到达的请求；其中 12 条在首次选入 prefill 前已等待超过 30 秒。后续没有新增 chain 超时。这个问题值得投入执行层优化，同时不能排除执行顺序的作用。

**OBSERVED**：新 DCP prefill 路径已实现。两卡缩小模型上，同进程交错执行的完整前向观察到短尾约 2.9%、2K 约 8.4%、8K 约 7.1% 的中位耗时下降。它没有在 130ed 中启用，不能把 130ed 的服务收益归给本轮新代码。TP8 真实权重、真实内存峰值和 N34/N38 仍待验。

**INFERRED**：W2 的容量增加与稳态失败骤减相符。但 130ed 与旧 A 的引擎、缓存状态和闭环到达不同；DCP 净效果必须对同引擎 W1（130ee）判断。局部“无排队”采样不能证明整轮无排队，也不能证明调度不起作用。

### chain 的时间账

必须使用正确的字段语义：`t_admit_s` 是 API dispatch finish；`t_exec_start_s` 是首次选入 prefill batch 后、ScheduleBatch 初始化前打点，且只打一次。首次选择到首 token 包含后续块间等待、host 工作和执行，不能叫“纯 GPU 时间”。源码入口为原 harness `extract_server_timing`、`req_time_stats.set_forward_entry_time` 和 scheduler 的 `set_time_batch` 调用。

15 条坏 chain 的合计（请求秒，不能当作墙钟时间）：API 接收到派发 2.195 s；派发到首次选择 625.163 s；首次选择到首 token 73.720 s。12 条的第二段本身超过 30 s；没有一条第三段超过 30 s。15 条中 7 条在 30–35 s，另外 8 条更晚；降低累计占用时间值得试，但不能承诺一个局部百分比会救回多少条。

对 130 的 **511 个共同 ID**，chain 13→15、turn 1→0、overall 35→15、fast 36→17；这是同 ID 诊断，不是 DCP 因果对照。新增两条 chain：

| logical_call_id | prompt / cached | TTFT 130→130ed | 首次选择前等待增量 | 选择后增量 |
|---|---:|---:|---:|---:|
| member-v5-subagent-decc99ccea990cea699d5b97:llm:3 | 92306 / 0 | 29.045→30.286 s | +1.091 s | +0.152 s |
| member-v5-subagent-cf6c4e2ad57ddac6b56febef:llm:2 | 37751 / 32768 | 29.632→30.906 s | +1.246 s | +0.028 s |

前面请求的通信/计算代价也会转化成后面请求的等待，因此此分解不排除 DCP 代价。它排除的是“看见两条新超时，就认定这两条自身 attention 慢了很多”的说法。

开场前 90 s 的 9 个 metrics 样本中，8 个有队列、峰值 20，空闲 KV 至少 54.54%，活跃占用最高 42.42%。**这段没有显存耗尽的证据。** 125 在开场 16:02:20 开启 relief，16:03:40 关闭，期间 cold cap=8192、prefill/decode interval=0；不能把开场瓶颈解释为常规 interval=2 强制插入的 decode。

命中 32K 的坏例也不能直接归为“本来立刻可运行却被压着”。同 family 冷生产者可能在等待期间才发布 prefix；raw 的 cached_tokens 是最终命中量，不包含前缀何时可用。当前 batch 日志没有每轮候选可运行性，不能从最终命中反推整个等待段都可救。

### 修正早期读数

- 第 11 分钟已有 22 个 turn 样本，零超时不等于“没有 turn”。
- 第 11 分钟之后的 298 个 metrics 样本中，88 个队列非零、峰值 6，活跃 KV 占用峰值 95.05%。短窗口队列零只能说明那段采样；整轮仍有瞬时排队。
- `used = capacity - available - evictable`。已用 43%/可淘汰 57% 几乎占满池，绝不是 57% 空闲；持续释放可淘汰前缀是合理行为。49 分钟样本的 available 只有 6272 / 2375168。
- 49 分钟的原始 series 已有 `load_back_tokens_total{pool="kv"}=5670912`、`pool="mamba"=2304`，回载字节约 87.59 GB，非零。采样器刻意不把不同 pool 的 token 单位压平；读不存在的 flat key 并默认 0 会产生假“无回载”。
- eviction 从 full-component 的设备 value 长度累加，不是 host 淘汰量；DCP 的 tree value 使用逻辑位置。radix counter 没有 rank label，所有 scheduler 会建立 collector，多进程聚合会混入副本计数。未逐 rank 读取计数前，不把导出的 3.96M 直接当单个 KV 池的唯一 token 周转，也不随意除以 DCP=2。

## 开发方向与实际交付

采用 [115 实现说明](../../engine/docs/115-dcp-local-extend.md) 的局部 KV 路径。它缩短执行占用；不修改调度队列、token、输出或历史。所有改动相对于同一 DCP 引擎开关关闭比较。分支建立在 f546934e 的审查修正底座上，接入已审查 DCP/NextN/host 补丁；与 130ed 的 b261cbd9 不是同一底座，8 卡对照必须两臂使用本分支同一引擎。

短尾选择默认上限 512；大块选择另行显式开启，上限 2048 或 8192。大块不是把短尾通信量模型向外硬推，而是来自完整 attention step 曲线：H8、W2、D512，P=0/8192/32768/131072/262144，T=2048/8192，两个 rank、真实集合通信、30 次交错测量；数值最坏逐行相对 L∞ ≤0.78125%。例如 T8192/P0 的整步约 11.07→8.30 ms，P262144 约 14.04→8.48 ms。这仍不是整模型或 TP8 服务速度。

同进程完整 ModelRunner.forward（元数据、8 层模型、logits；不含调度/tokenizer）40 次交错测量，H8/TP2/W2、名字固定的敏感 dummy 权重，Humming 两臂均开启：

| extend token | gather KV 中位 | local KV 中位 | 本次下降 | 完整前向临时峰值 gather/local |
|---|---:|---:|---:|---:|
| 27（padding 后选择） | 39.547 ms | 38.410 ms | 2.9% | 73.4 / 5.9 MiB |
| 2048 | 45.616 ms | 41.776 ms | 8.4% | 338.8 / 322.7 MiB |
| 8192 | 91.586 ms | 85.090 ms | 7.1% | 1313.0 / 1290.8 MiB |

证据位于 `evidence/dcp-local-extend-20260926/gpu-results/*pt*.json`，保留两个 rank 的全部样本。早期独立启动的短尾 48.1→38.7 ms，以及 H8 ABBA 的 base 50.88→38.49 ms，存在启动间漂移，**不采用约 19% 为稳定结论**。交错计时发生在敏感数值观察之后；重复前向会修改 KDA state，只用于时间测量。

显存需分层看：单 attention step 在 P0/T8192 的 transient 峰值约 208.5→740 MiB，而完整小模型峰值被其他层覆盖，并未随之增加。没有新增持久 buffer；不能据此保证真实模型无显存回退。新增就地空 shard 清理会减少一次输出分配，最终修订另有验证；不把单步内存与整模型内存直接相加。

## 验证与复核

CPU policy/phase 合同 6 项、已有 DCP/MTP 审查回归 7 项通过。GPU 检查包括高虚拟地址超过物理 pool、ragged batch、MIXED、512 上界、2K/8K、空 owner 与全遮蔽行、非连续 indices 精确 oracle、两个 rank 的真实 decode graph replay。

MTP H4 短尾矩阵：host/restore 对照 882 条敏感 trace，controlled-proposal 对照 330 条；逐行相对 L∞ 最大分别 0.6757%/0.6579%，输出 token 一致；target EXTEND/VERIFY、draft EXTEND/DECODE/EXTEND_V2 均覆盖。host 回载 4096 token、device hit=0，与 device repeat 一致；flush 后命中归零。controlled proposals 使用原始 verifier，不改接受规则，覆盖接受长度 1/2/3/4；该测试不能作为真实接受率或速度证据。

H8 大块/最终修订的 MTP host/restore 882 条、controlled 330 条敏感 trace 均通过，逐行相对 L∞ 最大 0.68494%；各组结果见[数值摘要](../../evidence/dcp-local-extend-20260926/numerical-summary.json)。额外接受跨页用例在两 rank 均观测到实际接受位置 [4351,4352]，跨越 128-token 页；自然与 controlled 两组数值比较通过。

最终 8K 普通前向一次复跑有一个第二层 attention 行出现 5.34% 偏差。新增基线 A/A 与首轮带输入捕获的 A/B 通过，但后续 [repeat2 再次失败](../../evidence/dcp-local-extend-20260926/gpu-results/local_8k_repeat2-compare.txt)，复现同一行：K/V 当前投影完全一致，第二层的选键集合实际替换了一个 KPool 组，候选为 [21028,21029,21030,21031]，基线为 [23340,23341,23342,23343]。这证明两次 attention 的输入已不同，不能直接把输出差额归为 LSE 合并误差。选键变化是否由浮点扰动/边界并列引起，未保存 indexer logits，仍不下结论。保留原始 FAIL，不提高容差。

固定第 3950 行的 top-k 后，两次独立运行、两个 rank 的敏感数值比较均恢复通过；这两次在覆盖前都再次观测到同一个 4-token 组选键替换，详见[隔离记录](../../evidence/dcp-local-extend-20260926/gpu-results/topk-isolation.json)及[对照一](../../evidence/dcp-local-extend-20260926/gpu-results/local_8k_fixed1-compare.txt)、[对照二](../../evidence/dcp-local-extend-20260926/gpu-results/local_8k_fixed2-compare.txt)。隔离只在诊断脚本发生，没有改生产 indexer，也不用于计时；结果支持这处输出偏差来自选键变化，不能把原生端到端 FAIL 改写成全路径数值 PASS。大块仍是需 TP8 质量验证的实验选项。指定 Claude 的复核反馈待交付后补充。未经复核与 TP8 实测，不把局部结果提升为已验证的服务决策。
