# 46676 / 46677 之后，下一轮开发应解决什么

2026-09-26，Codex。基于正式提交配置、112/130b 原始请求与服务日志、`f546934e` 实现及 DCP 独立审阅。本次只做分析和报告，不修改引擎、不启动实验、不占 GPU、不归档。文中“优先级”是工程判断，不是已经获得的性能收益。

结论：下一轮最值得投入的是 **把保留 MTP 的 DCP2 接到真正的新基线上，解决设备 KV 容量与长前缀搬运成本**；同时把 125 从“历史慢请求计数达到阈值就永久关闭”改进为有实际成本依据的控制器。短请求 prefill graph 是下一项执行层候选。继续堆排序阈值、开更大的块或重做 EP8，当前证据不足以支持优先投入。

## 2. 从原始日志重新算，得到的修正

### 2.1 125 在约第 6.3 分钟锁存，不是第 14 分钟

以 raw 的首次 `client_dispatch_at_s` 为零点，对齐 TP0 日志；日志精度为秒。不是以服务启动时刻计时。

| 运行 | 首次实测请求 UTC | `slow=82` 的关闭事件 UTC | 相对实测起点 |
|---|---|---|---:|
| 112 | 09:47:07.078 | 09:53:22 | 约 375 秒 |
| 130b | 11:47:16.055 | 11:53:37 | 约 381 秒 |

源码 `f546934e:engine/sglang/srt/managers/ax_deadline.py` 的 `BacklogState.decide()` 一旦设置 `tripped`，直到 flush 都不再启用 relief。日志中之后没有重新开启，周期计数也不再增长，支持这一点。**“关了约 54 分钟”比“第 14 分钟后关了 46 分钟”更接近这两次实测。** 原记录混用了什么起点，本次没有足够证据确定。

这修正了实验设计依据：10 分钟探针有机会观察触发与初期差异，不能说它原则上测不到；但它仍不能回答后续几十分钟的净收益，60 分钟对照有必要。触发时刻会随 workload、warmup 后状态及新引擎变化，不能把 6.3 分钟当新常数。

另外，`_ax_flush_admission_state()` 重置的是 `BacklogState`，没有重置 `_ax_admission_stats`。`relief_rounds=307/300` 是进程累计值；实测开始后第一条周期日志已经分别为 89/85。比较测量区间需要取差值，不能把绝对计数直接写成“本小时 relief 轮数”。

### 2.2 S1 的 warm 修正有明确取舍

用原 harness 的 `in_ttft_gate()` 重新分桶，112/130b 的共同 3063 个请求如下，与既有配对记录一致：

| 超时请求 | 112 | 130b |
|---|---:|---:|
| chain | 26 | 30 |
| turn | 24 | 16 |
| overall | 448 | 512 |
| fast | 506 | 554 |
| 最终 TPOT > 0.10 | 35 | 37 |

它支持“把 warm 预算由 5 秒放宽到 15 秒改善 turn”，也显示代价。不能把这次单变量结果称为四门共同改善，更不能把四个桶的修复数相加成独立收益：fast 本来就是 overall 的子集。

112/130b 在护栏触发后到达的 chain 分别有 208/203 条，其中 13/17 条超时；最终 TPOT 超线的后到请求均为 3 条。这说明关闭持续时间长、后续仍有等待问题，**不证明重新开启即可救回这 13/17 条**，更不证明提高阈值不会新增 TPOT 坏例。

`slow=82` 数的是服务端运行中“曾经超过阈值”的集合；35/37 数的是客户端完整输出后的最终 TPOT。日志没有逐请求的曾慢集合，所以只能说口径不同，不能计算精确误报率。“250 接近 5150×5%”也不是安全证明：分母、统计时刻、传输耗时、是否仍在运行都不同。

复现：[脚本](../../scripts/analysis/audit_125_measurement_window.py)、[完整重算收据](../../evidence/post-submission-46676-46677/guard-window.json)。脚本只读已保留的原始文件，不修改 harness，不判正式成绩。

## 4. 第一优先：交付 S1 基线上的 DCP2 + MTP

这是当前最接近改变容量上限的一条路径，且已经付过主要实现和审阅成本。

### 先把对照做对

现有 DCP W1/W2 脚本彼此是成对的，但**不等于这次 S1 + DCP**：它们仍固定 `e4d7ca68`，warm=5、running/graph=48、显式 418 状态槽；正式 S1 是 `f546934e`，warm=15、running/graph=32。DCP 分支还缺这次四个审查修正。

下一候选应从 `f546934e` 接入 115/180 的 DCP 实现及 `b261cbd9` 默认 topk 守卫修正。先保持 S1 的 warm15、MTP 3/1/4、host64、32/32 和 125 阈值；W1/W2 使用同一提交和同一组其他参数。若要升到 48 或钉住 KDA 槽，两臂一起改并承认基线改变，不能把这笔收益或代价归给 DCP。

### 容量账与需要交付的代码

11 个目标 DSA 层 + 1 个 NextN 层，每逻辑 token 每卡的 KV 数据字节约为：

`12 × (1024 / W + 132)`

W1 为 13,872 B，W2 为 7,728 B；**固定 KV 字节预算下约 1.80 倍逻辑容量**。这是组件算术，排除了 KDA、工作区、graph、通信缓冲变化，不是 N@SLO 的 1.80 倍。

具体交付分两步：

1. 完成新基线集成与 TP8 正确性：target/draft 高虚拟地址、三种推测 graph、接受长度 1/2/3/4、实际跨 256/512 边界、混合 batch、HiCache 恢复后继续接受多个 token。TP2 的“跨 owner”不等于“接受窗口跨边界”。
2. 若 W2 的完整 step 显示通信抵消收益，再做**短 extend 的 Q gather + local attention + LSE merge**，避开每层 gather 整段 prefix KV；先加零前缀/对齐前缀快路径与有界元数据复用。保留普通长块路径，用实测 P/T/batch 选择路由。

以 128Ki prefix、512 BF16 latent 计，每层完整 prefix buffer 是 128MiB。短尾请求反复搬它，可能吞掉扩大 KV 带来的好处。这一实现机会直接落在 `forward_absorb_prepare → all_gather_kv_cache_for_mla_extend → sparse attention → LSE merge`；不能只看稀疏 attention kernel 的局部计时。

验收看同请求的首次执行前等待、host 恢复量、实际 KV/KDA 容量、完整 DCP step、四门和 TPOT；容量涨而等待不降时，追资源资格和通信，不直接继续升 W4/W8。

## 5. 第二优先：125 的成本与反馈，连同 124 的资源判断

这不是简单把 250 再改成 500，也不建议原样换回 122。130e 的 122 对照已经出现 chain/turn 代价。

沿调用链 `get_next_batch_to_run → _ax_admission_plan → BacklogState.decide → _arm_prefill_decode_interval`，值得做的改动是：

1. **补齐闭环所需观测。** 分开记录最终完成 TPOT、当前活跃 TPOT、曾经超线次数、触发原因与 flush epoch；服务端计时用来控制，客户端原 harness 用来验收。周期计数在 flush 时按区间分账；不把启动/预热间隔混入产能。
2. **用真实批成本替换陈旧常数。** 124 仍用 run071 的 `0.13s/chunk + 68µs/token` 及 1.27 系数；117、MTP、不同 prefix 和 DCP 都会改变它。以真实执行的 `prefix、extend、batch、MTP、W、host_restore_bytes` 建有界桶统计，处理 overlap 中仍在飞的 prefill，先检查预测误差，再控制调度。
3. **分阶段反馈而非一次锁存。** 保留整轮最终慢请求账，用活跃解码风险与近期压力决定 8192/6144 和 interval 0/1/2；带进入/退出滞回和最小保持期。已发生的慢请求不能凭空清零，恢复 relief 也必须有新测量依据。候选选择要同时看预计能完成的等待请求和新增长的解码延迟。
4. **排序前先有真实资源资格。** 复用已修的 `ax_complete_waiter_budget` 与正式 adder 资源检查，区分新算 token 与需恢复的完整 KV；不把只有 1k 新 token、但需恢复 50k 前缀的请求当成“只要 1k 空间”。停车不释放续算持有的 KV，因此纯改排序救不了所有资源受限请求。

已有主工作区的 admission trace 正在改进，复用它记录“未扫描、资源拒绝、partial 约束、可运行但排序靠后”的**等待秒数**，不另造一套采集器，不用拒绝次数代替等待时间。TP0 统一作出并广播决定，诊断不能重复调用有副作用的 prefix-match/COW。

第一项可以独立交付；第二项先观测；第三项是新算法，需与 80/250 固定配置比较。改善 chain 而把 turn/fast 推坏，应按组合净结果判断，不归为无条件成功。

## 6. 第三优先：小块 prefill graph，目标是少占通道和少占 KV 时间

继续推进 170，但范围先限实际常见的短 warm extend。先带入上一轮实际 replay bucket 的 scatter 修复 `afdca82e`，核对 MTP/HiCache 接口；只有当前执行路径支持时才开相应 bucket。

[R10](../../research/claude/R10_prefill_fixed_overhead.md) 的旧 TP1 结果证明小块存在 host 发射间隙，不能用其中的 150ms 当今天 TP8 的可回收收益。117 已减少一部分 host 元数据开销，需要在 f546 上量剩余部分。优先少量 256/512/1024/2048 bucket，真实命中分布决定保留哪些；大块本来更偏 GPU 计算，不先追全形状 capture。

验收同时报告每块时间与新增 graph 显存。图若只省几十毫秒却挤掉大量 KV，使 host 恢复和准入等待增加，服务总结果可能倒退。若小块地板确实下降，可以在更小 chunk 下保护 TPOT、又不明显拖慢 chain，这比继续用大块交换尾延迟更有持续价值。

## 7. 后备方向与暂缓方向

| 方向 | 具体值得做的内容 | 何时升级优先级 |
|---|---|---|
| MTP 深度与状态池 | 先复用 130f/142 的去 MTP 对照；再固定 KDA 槽比较较短 draft window。按完整 `verify + draft extend + draft decode` 时间 / 实际接受 token 计收益，不能用接受长度代替加速比 | 若容量扩大前，MTP 状态/计算代价已主导；启动级固定深度先于动态深度和多套 graph |
| KDA 检查点成本 | 记录 KV 可复用前缀与 KDA 可恢复检查点的差值、状态淘汰后实算 token；据此决定 418→256。若做低精度，先区分活跃 FP32 递推状态和冻结检查点的存储精度 | 139/144 显示容量有价值，并且长链误差/能力验证能支撑；冻结检查点量化仍是有损，不能直接视为安全 |
| HiCache 更有效利用 | 先完成既有 143 write_back 对照，区分 D2H 阻塞、host 满、KDA 检查点缺失；下一步才是去重/选择性写回、空间可用时的恢复预取 | host 恢复或重算在逐请求时间账里占主要份额；单纯加 host 不会增加活跃请求的设备 KV |
| indexer 紧凑页 | 先减少 KPool4 空页传输，再考虑独立页映射压缩 allocation；同步改写 kernel、host 和 profiler 合同 | DCP 做大后 replicated indexer 成为显著容量/带宽项；不能直接把 `index_buf_size` 除四 |
| FP8 latent KV | A100 TileLang 中按块反量化，复用现有量化布局并覆盖 NextN、HiCache、零 rope、长链 | DCP 实测通信代价过大，或仍需更多容量；目前工程/数值风险高于兑现已有 DCP |

不优先：未经新证据的 EP8 重做、8k→16k 的盲目大块、128 家族规则继续加分、反复调整 warm 饥饿阈值、一次把 DCP/FP8/BF16 KDA/新调度全开。128 目前识别家族未转成更早执行，需要先用真实决策轨迹解释，且启用前带入已审修正。

## 8. 建议的下一轮顺序

1. 用 `f546934e` 固定新的开发基线；等待并复用 130eb/130ec/130f 的结果，不重复排同问题实验。S1/S2 正式结果回来时，只解释实际回报，不猜未公开失败档的门。
2. 优先交付 DCP2 集成、上述 TP8 正确性边界及同基线 W1/W2 对照；在等待共用 8 卡时可开发短 extend 通信路径与 125 的观测/成本分桶，不占 GPU 做纯代码工作。
3. 用原始等待账决定：资源仍紧则继续 KV/状态布局；资源已可用但冷/暖互相压住，则推进新的 125 控制；短块固定成本显著则推进 170。

N34/N38 需要的是在更高负载下仍能过全部门。以“省多少 GPU 时间、少占多久/多少显存、救回哪类请求”为每个补丁的交付单位；正式排序仍以 task.md 的 N@SLO、其次 TPOT 为准。
