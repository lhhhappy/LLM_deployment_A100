## 0. 榜单怎么读（用户 09-28 贴的榜）

|---|---|---|---|
| 1–4 | N34 | 0.037 / 0.049 / 0.050 / 0.051 | 1.55M–1.66M |

- 我们每档只挂 chain（实测，46676/46757/46758 四次全是 chain p95 37–46 s）。tpot 我们最好，比榜首低 12 ms；TPM 各队都在 1.4M–1.7M，一档的时长由链自身的思考间隔主导（p90 链 42 分钟），TPM 说明不了引擎快慢。
- 榜首四队 tpot 0.037–0.051：他们把 decode 的时间让给了 prefill。我们 0.025 意味着还有约 2 倍的 decode 时间可以拿出来给链首（估计：均值到 0.045 时 p95 ≈ 1.75×0.045 = 0.079，仍在 0.10 内）。这次上传（去 MTP，期望均值 32–38 ms）只花了一半。
- 结论与用户一致：只做并发。方向不是"少插 decode"这种旋钮，而是把 decode 让路做成按每条请求的截止时间精确分配（见问题 4），再加上 prefill 通道的抢占式排序（见问题 1）。

## 1. 三笔账（决定所有方案的边界）

**开场账（估计，用简报的实测吞吐）。** N 个冷头 t=0 同到，30 s 内通道最多算 30 s × 13k = 39 万 token。按最短优先，能过门的只有累计 prompt ≤ 39 万的那几个头；链首 p50 35k → N30 约过 12–19 个（本地实测 30 个头漏 11）。开场漏数随 N 线性涨，只有吞吐能减，排序已经是最优（最短优先 = 使超时条数最少的经典解）。N34 开场估计漏 13–15，N38 漏 17–19；线上一档允许约 31，所以稳态必须控制在 12–15 条以内，这就是稳态抢占为什么必须做。

**tpot 账（数据 + 估计）。** 主办方 722 行的输出长度 max_output_i：p5 58、p10 94、p25 143、p50 198、p90 554。去 MTP 一步 decode 约 30 ms（估计）。一条 n 个输出 token 的请求全程能容忍的总停顿 ≤ (0.10−0.03)×(n−1)：n=58 → 4 s；n=94 → 6.5 s；n=198 → 13.8 s；n=554 → 39 s。一个 250k 头入批后 16–17 s（实测）：decode 期整段落在巨头里、输出 ≤ 250 的请求必超 0.10，插 decode 的频率再高也没用（全程重叠时只有 decode 占 GPU 的份额起作用：份额 f 下每 token = 0.03/f，要 ≤ 0.10 需 f ≥ 30%）。本地 4% 超门、线上 p95 47.7 ms 都对得上这笔账。
关键事实：服务端在准入时**精确知道** n（max_new_tokens + ignore_eos 强制），所以每条运行中请求的末 token 截止时刻是可算的，不需要 122 那种 τ 估计与锚点推断。

**通道账（实测的推论）。** 抢占只改顺序，不改 prefill 总量，也不改 decode 承受的总停顿。谁先算，通道总时长一样。这是抢占优于"配额让路 / 一轮大块救援"的根本理由：后两者都往通道里加工作或加停顿。

## 2. 逐题回答

### Q1 抢占正在算的无救巨头
现状（读 engine/sglang/srt/managers/schedule_policy.py add_chunked_req、scheduler.py 3755–3766、4214–4225）：
- 已经有"停车"状态：`ax_continuation` 在整单元放不下时直接 `return req`，不进 can_run_list；停车的 partial 的 KV 每块结束就 `stash_chunked_request` 进 radix 树并加锁，KDA 状态原地留在它自己的槽里。停车期间它不执行任何 kernel，所以**多轮停车不需要任何新的 KV/KDA 状态契约**，124 的单轮停车已经在 TP8 上验证过同一契约。
- 缺的只是簿记：`chunked_req` 单字段、`assert self.chunked_req is None`（4216）、`process_batch_result_prefill(chunked_req=self.chunked_req)`（4755，应传批自己的 chunked_req）、abort 路径、pending token 计数、`inflight_middle_chunks`（overlap 下结果晚一步）。
- 设计：`chunked_req` 拆成"当前活动 partial + 停车列表"。规则：等待队列里出现 124 判定"可救"的头，而活动 partial 是"判死"层（或按 SRPT 剩余工作更长）时，活动的转入停车列表，可救的头成为新 partial；它最后一块结束后停车的恢复。决策只能是队列状态的纯函数（不能看墙钟），否则 8 个 rank 分叉，这正是 131 要做 rank0 广播的原因。
- 代价与风险：停车的巨头持有最多 250k token KV（约 1.26M 池的 20%，钉 KDA 池后 1.81M 更宽裕）和一个 KDA 槽；饥饿要用现有 600 s 上限和"无可救等待者即恢复"兜底（还要顾 harness 的 1200 s 无事件超时和每链 3600 s 等待上限——它们是覆盖率门）。工程量：只改调度器，估计 200–400 行 + CPU 测试；主要风险在 overlap 簿记，不在 kernel。
- 更省的做法不推荐：配额式每第 k 轮让路只救一轮能算完的头；"一轮大块救援"（把可救头的 18k–32k 一轮算完）给 decode 加 1–2 s 停顿，而 decode 此时已经在巨头的停顿里。两者都是加工作或加停顿，抢占是零加价。

### Q2 块大小与让路
有了多轮停车，块大小不再和小头的等待挂钩：小头接管通道后连算自己的几轮，巨头停着。16k 块保留（固定开销减半）。KDA 安全由现有网格对齐保证：add_chunked_req 只在整个 256-网格单元放得下时才切块，否则停车，所以停车点永远在对齐边界，多轮停和单轮停没有区别。不要为让路把块切碎。

### Q3 容量与淘汰
- 779 槽的来源（读 unified_memory_pool.py 1178–1390）：统一池按字节共池，KV 从高地址向下、KDA 槽从低地址向上；`max_mamba_cache_size` 参与总字节和启动时的 token 计数，`mamba_full_memory_ratio` 只管总预算不管运行期切分。去 MTP 后草稿层的状态缓冲和 spec 中间缓冲消失，释放的字节按同一规则算进了 KDA 最大槽数，所以 411→779。启动日志 `[unified-memory-pool] total_bytes / max_total_num_tokens / max_mamba_cache_size` 那行能核。KV 侧是否能在运行期用掉 KDA 空闲字节，看 token 计数上限是否硬限；从实测（钉 400 后 KV 1.26M→1.81M）看是硬限，即未用的 KDA 字节是死的。
- 钉多少：槽不只给运行中请求用。radix 树在 256 网格上存 KDA 快照，"上下文重建只算 2k"和链首命中都靠树里有前缀末尾的 KDA 状态——**KDA 状态不能由 KV 重建，树里没状态等于整段重算**。运行峰值 110 只是运行中的槽，钉之前要数树里持有的快照数。另外主机层 64 GB 按设备 KV:KDA 字节比例切（180 文档 §92），钉 400 也会缩主机侧 KDA 份额，主机命中会因"状态没了"被截短——钉的时候要看 180 的截短计数。
- 扩容不改入批次序：这次实测里巨头提前入批，是因为"放不下就跳到下一个能放下的"这条准入规则让容量参与了排序。改成：124/132 排好序后，队首放不下就等（完整短命中除外），不跳到更大的请求。这样池子变大只增加同时驻留，不改变谁先算。
- 主机层：`--hicache-size` 是每卡 GB，64×8 = 512 GB 已经是 pinned 内存；1509 GiB 总内存扣模型加载与 /dev/shm 留量，每卡 96（768 GB）大概是上限（估计），"200+ GB"只能是总量。淘汰策略按会话保留"前缀末尾 + 该处 KDA 状态"这一对，优先于通用 LRU：丢一个上下文重建的前缀 = 一条必漏的 chain 加 15 s 通道时间。

### Q4 tpot_p95 无余量
按第 1 节的账：真正的杠杆不是插 decode 的频率，而是**按精确截止时间分配 decode 份额，并有意花掉 5% 的允许额**。
- 每条运行中请求：deadline = 首 token 时刻 + 0.10×(n−1)（留 5% 余量），slack = deadline − now − 剩余 token × 30 ms。
- 每步决策：受保护请求（slack ≥ 0）里最小 slack 放得下下一块（16k ≈ 1.0 s）就 prefill，否则 decode 一步；slack 已负的请求不再保护（它们计入 5% 允许额，约每档 257 条，估计）。
- 这就是 122 的骨架，但用精确 n 代替 τ、去掉锚点估计和成本模型外推；决策变量必须 rank 一致（同 131）。tpot 均值会升到 0.04–0.05，和榜首一样，符合用户"tpot 可以放"。
- 对 chain 的好处：长输出请求（p90 554 可容忍 39 s 停顿）在场时通道可以连续给链首，不必固定每块插 2 步。

### Q5 执行层还能省什么
- A100 没有 FP8 tensor core，Marlin FP8 是权重侧反量化，16k 块的 MoE 是 bf16 算力瓶颈；A100 唯一 2× 的算力杠杆是 INT8 tensor core（W8A8，SmoothQuant 类激活校准）。估计整块省 10–15%；能力风险中等，AIME/GPQA 复核必做。
- mHC 14% 是访存型逐元素与小矩阵，融合成一个 Triton kernel 通常拿回一半以上，估计整块省 7–10%，风险最低，优先。
- all-reduce 12%：16k×hidden 的 bf16 张量走 NCCL ring；改 reduce-scatter/all-gather 序列并行以便与 MoE 重叠，估计 3–5%，工程重。
- DSA top-k 缩小和更低精度 MoE 权重：不建议，能力门是硬门，而每 8% 吞吐只换开场约 1 个头。
- 排序：mHC 融合 > MoE int8 > 通信重叠；但当前性价比最高的仍是调度（Q1/Q4），执行层改动的收益按开场账折算是线性的、小的。

### Q6 我会先改哪里
把调度器改成"数超时条数"的优化器，三件事按顺序：
1. Q1 的多轮停车 + 可救者抢占（零加价，直接打稳态的两类病：巨头压小头、小头纯等待）。
2. Q4 的精确 tpot 截止时间 + 有意消耗的 5% 允许额（把 decode 时间兑换成链首）。
3. 钉 KDA 池 + 容量不参与排序 + 主机层按会话保留前缀末尾状态（保住 2k 的上下文重建不变成 200k 的判死）。
判死巨头：可救者在等时让路，没人等就算，不能无限停（1200 s 无事件与 3600 s 每链上限是覆盖率门）。
