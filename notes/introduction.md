## 1. 赛题

原文见 [task.md](../llm-challenge-arena-v1/task.md)。

- **固定条件**：模型 GLM-5.3-Flash，8 张 A100-SXM4-80GB（NVLink，sm80，没有 FP8 计算单元），负载是冻结好的多轮 Agent 会话。可以改的只有部署：引擎、并行方式、kernel、调度和缓存。
- **提交**：一个推理服务镜像和启动命令。主办方拉起服务后，先考能力，再做压测。
- **能力门**：AIME26 与 GPQA Diamond 两科都必须严格高于 90 分。不能关 thinking、压输出、截历史、删 tools；`/flush_cache` 必须真清；时间戳和 token 计数必须如实上报。
- **压测方式**：回放 341 条会话链、5150 条请求。N 表示同时在场的会话数。一个会话在等工具或用户时仍占着名额，只是没有请求在跑。平台从 N10 开始，某档通过就加 4、失败就减 4，每档约 4 小时。
- **每档 11 道硬门**：
  - 完整性与错误率门若干；
  - 四道首 token 延迟（TTFT）p95：
    - `fast_intra`：链中间、新增 token ≤4096 的请求，≤3 s；
    - `overall_intra`：全部链中间请求，≤5 s；
    - `turn_start`：一轮新用户输入的第一条，≤15 s；
    - `chain_start`：链首或上下文重建，≤30 s；
  - 这四道门按样本量允许一定的统计余量；
  - 解码门 `tpot_p95 ≤ 0.10 s/token`，没有余量。TPOT 按请求算 `(末 token 时刻 − 首 token 时刻)/(输出数 − 1)`，再取 p95。所以同样一次停顿，对短输出请求伤害更大。
- **排名**（主办方确认）：先比全部硬门都过的最高档 `n_at_slo`，再比该档的 `tpot_mean`（越小越好），再比 TPM，最后比提交先后。
- **开发集**：主办方给了 `s1-dev/`，311 链、722 条请求，正文齐全，带原版 harness 和评分器。task.md 明说它是链前缀抽样，只能比较自己的 A/B，不能预测正式 N。

## 2. 模型：GLM-5.3-Flash

来源：`s1-dev/glm_tok/config.json`（原文），以及 SGLang 官方部署页 `refs/sglang-fe236ea6c3/docs/cookbook/autoregressive/GLM/GLM-5.3-Flash.mdx`（原文）。

- **规模**：总参数 320B，每 token 激活 18B（官方）。
- **注意力**：45 层，其中 **34 层 KDA 线性注意力**、**11 层 DeepSeek 式稀疏注意力（DSA）**。
  - DSA 用 MLA 压缩 KV（`kv_lora_rank 512`，`qk_rope_head_dim 0`，即没有 rope 分量）。
  - DSA 带"索引器"（32 头 × 128 维，FP8 存储），每个 token 只读 top-2048 个历史 token；`index_kpool 4` 表示压缩。
- **其他结构**：mHC 超连接（`hc_mult 4`，残差流宽 4×4096）；MoE 共 288 个路由专家，每 token 选 8 个，另有 1 个共享专家，前 3 层是稠密层；1 层 MTP 草稿层；权重为 FP8 e4m3（块大小 128）。
- **对服务的关键含义（推断，官方资料的核实正在进行，见 §9）**：
  - 缓存分两种：
    - **KV**：只在 11 层 DSA 上有，按 token 分页，可以在任意前缀位置复用；
    - **KDA 状态**：每个会话一块固定大小的状态，**只能在存过快照的位置复用**。
  - 所以前缀命中长度等于"KV 能匹配的长度"和"最近一个快照的位置"中较小的那个。
  - TP8 下，MLA 的压缩 KV 按头切不开，每张卡都存完整一份。
- **官方部署页的几条原文要点**：
  - KV 池和 KDA 状态池要成对定大小；
  - Blackwell 上默认用 FP8 KV，同字节约 1.8 倍 token；
  - **"TileLang DSA 配 FP8 KV 不是有效 CUDA 组合"**，而 A100 只能走 TileLang；
  - DCP 只在 4×GB300 上验证过 DCP4；
  - HiCache 可以把缓存溢出到主机内存。

## 3. 负载画像（真实数据）

数据共有四种，不能混用，详见 [data/README.md](../data/README.md)：

1. **主办方开发集的正文**：722 条请求，都是 311 条链的开头片段。
2. **主办方给出的这 311 条链的完整统计**（`chains.jsonl`）：合计 5601 次调用。例如最长一条链有 240 次调用、持续约 14 小时，正文却只给了开头 4 条。
3. **我们按这份统计合成的长链集**：补齐了缺失的 4879 条正文。
4. **正式评测集**：341 链、5150 请求，隐藏，本地没有。

下面的链长表出自第 2 种（主办方的真实统计，不是我们合成的）；新增 token 和回放间隔出自第 1 种。正式集与它们的关系只能推断。

**链长：按条数看多数短，按负载看长链为主（主办方整链统计）**

| 链长（请求数） | 链数占比 | 请求占比 | prompt token 占比 |
|---|---|---|---|
| 1 | 15% | 1% | 0% |
| 2–5 | 27% | 5% | 4% |
| 6–15 | 32% | 18% | 14% |
| 16–30 | 10% | 12% | 9% |
| 31–120 | 14% | 48% | 44% |
| 121–240 | 2% | 17% | 29% |

- prompt 总量 485M token，其中冻结标注的"预期未命中"只有 30.9M（6.4%）；输出预算合计 4.1M token。
- 长链存活时间长，所以任何时刻占着槽位的多半是长链（推断）。

**其他特征**

| 特征 | 数值 |
|---|---|
| 单条 prompt | 中位约 4 万–7 万 token，最长约 25 万 |
| 普通追问的新增 token（722 条正文中 414 条 append-only 追问，逐条差分） | 中位 1.6k，p90 5.6k，p95 12k，p99 38k，最大 103k（工具返回很长的情况） |
| 输出长度 | 中位约 190 token，p95 约 760。这是一个以 prefill 为主的负载 |
| 回放间隔（harness 公式） | 用户思考按 `min(think, 10 s)` 计，工具时间按 `min(tool, 300 s)` 计，每链总等待上限 3600 s。实测回放间隔中位 2.4 s，p90 12 s，p99 36 s |

- 真实用户会隔很久才回来，但**回放里没有这种长时间离开**。缓存丢失主要不是因为等得久，而是在这几秒到几十秒里被其他会话挤掉（推断）。
- **system/tools 变更很常见**：311 条链里只有 104 条是真正的新会话开头，另外 207 条是同一会话中途 system 提示或 tools 变了被切出来的新链，按 chain_start（30 s）考核，冻结标注为零命中。
  - 抽查 127 个这样的切换：典型情况是 system 末尾的子任务描述变了，例如"写第 4 章"和"写第 2、3 章"两个子任务交替。
  - 按字符估算（**尚未做 token 级复核**），与同会话更早的请求相比，中位 67% 的前缀相同。
- **上下文重建**（context_reset）共 141 次，分布在 74 条链上。

**我们的合成长链集** `data/s1-dev-longchain/`（数据 Codex 生成）：链长和各类请求的数量沿用主办方的整链统计；缺失的 4879 条正文由开发集素材合成；事件位置和等待时间是估计值；每次新增 token 的分布和链内 system/tools 切换**还没有还原**。它通过了原 harness 自检，**还没有 GPU 成绩**。它只用来复现"长链、高复用、缓存会被挤满"的状态，不预测正式 N。

## 4. 成绩

**正式提交（实测，官方返回；[submissions.md](submissions.md)）**

| attempt | 配置 | 能力 | n_at_slo | tpot mean / p95 | TTFT p95：fast / overall / turn / chain |
|---|---|---|---|---|---|
| 45979（A） | 镜像 0923a，MTP，interval 2，COLD_CAP 4096 | AIME 43/44，GPQA 153/156 | **14** | 0.0174 / 0.0364 | 1.52 / 3.87 / 6.39 / 30.23 |
| 45980（B） | 同镜像，MTP，chunk 8192，无 interval | AIME 42/44，GPQA 153/156 | 10 | 0.0121 / 0.0206 | 3.46 / 3.72 / 4.91 / 10.89 |

- 平台只返回通过档的数据，失败档（A 的 N18、B 的 N14）的分项不返回，所以**我们不知道正式 N18 挂在哪道门**。

**公开榜首**：N30，tpot_mean 0.046，TPM 约 156 万/分钟，decode TPM 约 1.9 万/分钟。

- 粗略推算：输出吞吐约每秒 324 token，**乘以** 0.046 秒/token，平均约有 15 条请求在同时出字。TPOT 是按请求平均的，吞吐是按 token 汇总的，所以这只是数量级。
- 这里**不能**再往下推"真实新 prefill 很少、平均算力足够"：6.4% 是主办方整链统计里冻结标注的"预期未命中"比例，不是榜首或正式 A 的实际重算比例。
- 也不能从这几个数反推对手的调度策略：更大的活跃 batch、不同的缓存命中率、不同的 MTP 设置，都可能造成"TPOT 更高、N 也更高"。
- 我们的主线假设（待验证）：高 N 的瓶颈在可复用缓存的容量，以及尾部事件撞在一起的时刻。

## 7. 已经确认的事实（实测）

- **047（正式 A，开发集 N22）**：
  - 新算 token 共 9.92M，窗口约 1150 s，GPU 忙 94%。
  - ≥8k 的 prefill 块 p50 为 1.075 万 token/s，≤2k 的小块只有 4.4k token/s。
  - 2301 个 prefill 批次里 1815 个是单独跑的部分块。
  - bs ≥ 20 时 decode p50 约 300 token/s；KV 占用峰值 0.85。
  - 62 条 chain 门超时中，有 55 条在第一次执行前就已等了 30 s 以上。
- **开发集比正式严**：044r 用正式 A 原样跑开发集 N14，挂 overall（39/27）和 chain（32/22）两道门；而官方同档通过。开发集链首占 43%，正式约 6%。
- **噪声**：同配置重跑只在旧 S1 上做过一次，fast 门超标 7 条对 15 条。正式 A 这套配置还没有重跑数据。
- **DCP**：上游 SGLang 有 DCP（PR #14194、#25090），但 GLM 这条 DSA/no-rope/A100 路径是半成品。我们修了两层（64 头 kernel 的共享内存超限、KV 写入没分片），第三层（与 scatter 补齐之间的 33/40 行契约冲突，推断）还没修。按字节推算容量约 ×4.4，达不到 ×8，因为索引键仍是每卡一份完整的。
- **MoE 效率**（单卡 A100、TP8 每卡形状、随机权重，实测）：
  - 大块时约 80 TFLOPS，只有 bf16 峰值的 26%；MoE 约占大块 prefill kernel 时间的 38%（046r）。
  - **同形状下未调优的 Triton BF16 也只有 82 TF**，Marlin 是 84.5 TF（16k token，`evidence/INT8/bench_moe_int8_devbox.log`）。所以瓶颈在形状，不在 kernel：TP8 把每个专家切成了每卡 256 宽，下投影的内维只有 256。
  - 详见 [R25](../research/claude/R25_moe_sm80_path.md)。
- **pod 硬件**（2026-09-24 实测）：主机内存 2 TB（可用 1.9 TB），128 核，两个 NUMA 节点；8 卡 NVSwitch 全互联；每两张卡共用一个 PCIe 交换芯片。
- **底包 HiCache 对本模型不正确**（读代码核实）：在 CUDA 路径上，host↔device 只搬 MLA latent，索引键只在华为 Ascend 分支里搬（`srt/mem_cache/pool_host/mla.py`）。上游 PR #40915 实测，从主机恢复后与原结果的 KL 是 0.06–0.71，修复后约 0.002。修复都没合入。

## 8. 我们目前的理解

**核心判断（推断，待长链集上的 8 卡运行验证）**

- 正式负载的 prompt 有 94% 以上理论上可以复用。能否达到高 N，取决于两件事：一是 30 条长会话的缓存（KV 加 KDA 快照）能不能同时留在卡上；二是缓存被挤掉、超长工具返回、子任务切换这些尾部事件撞在一起时，谁先得到服务。
- 此前所有 8 卡实验都在开发集上。开发集链首多、缓存从来没被挤满，**这个区间我们从未测量过**。
- 推算容量需求：30 个会话 × 中位约 6 万 token，约需 180 万 token 的 KV，长尾会话再加一截；而我们的池只有 104 万。
- 能扩容量的几个杠杆，都还没做成：
  - **DCP**：推算约 ×4.4；
  - **FP8 latent KV**：约 ×2，需要改 A100 的 TileLang kernel；
  - **显存预算**：捕获 graph 后每卡空闲约 14 GB，能收回多少没测过；
  - **HiCache（溢出到主机内存）**：
    - pod 实测有 2 TB 主机内存（可用 1.9 TB）、128 核；8 卡之间 NVSwitch 全互联，每两张卡共用一个 PCIe 交换芯片（`free -g` / `nvidia-smi topo -m`，2026-09-24）。
    - 按每卡 12.7 KB/token 推算，每卡分 200 GB 主机内存就能存约 1500 万 token 的 KV，远超工作集。
    - 从主机搬回一个 6 万 token 的会话，每卡约 0.76 GB，推算约 0.05–0.1 s；重算要 6 s 以上。
    - 但底包的 HiCache 在 CUDA 路径上不搬 DSA 索引键，搬回后输出会错（上游 PR #40915 实测 KL 0.06–0.71），修复都没合入。我们自己修，见 R24。
    - 正式评测机的主机内存假定与自测 pod 相同，这一点未确认；
  - **DCP 与 FP8 不能简单相乘**：索引键在 DCP 下仍是每卡一份完整的。按字节推算，DCP8 约 4.4×，FP8 约 1.8×，DCP4+FP8 约 4.4×，DCP8+FP8 约 5.8×（外部评审的推导，未实测）；
  - **MTP 下重新打开 101/140 快照**：两者冲突只是"未测试"，并没有被证实。

**平台层疑点（推断）**

之前评价补丁只问"能不能跑"和"开发集的门变没变"，没有问"这个 kernel 离 A100 的上限还有多远"。具体疑点：

- **111 MoE**：大块时只有峰值的 26%。实测已排除"Marlin 本身慢"。R25 的推算：
  - 可达上限约 1.7–2.0×，现实约 1.3–1.5×，折合 prefill GPU 时间最多少 10–18%。
  - 16k token 时，非 GEMM 的显存搬运（清零、写回、再求和）占 13–20%。
  - 111 按 SGLang 规范看有 6 处偏差：自造环境变量开关、在已有类里插提前返回分支、没有注册测试等，需要重写。
- **mHC**：每次前向 90 次小调用，sm80 上走的是替代实现，替身模型 profile 里约 11 ms，与 MoE 同一量级。
- **索引器**：开销随上下文增长，正式负载的上下文区间里（6 万到 25 万）8 卡上没测过。

## 10. 下一阶段顺序（已吸收第一轮外部评审，详见 [roadmap.md](roadmap.md) §4）

1. **基线**：正式 A 在长链集上原样跑，外加一次噪声重跑。每条追问记录安全复用长度 `L_safe`：token LCP 范围内 KV、索引键/KPool、KDA 状态三者同时可用的最长位置。回退时记录缺的是哪一项、回退了多少 token、多花了多少毫秒。
2. **显存预算**：不改数值路径，按最坏形状实测动态峰值，把能安全收回的显存给 KV。
3. **HiCache 修复**（补丁 180）。
4. **FP8 latent KV**：紧凑行 528 B（512 B FP8 加 4 个 FP32 scale，每 128 维一个）；推算 latent 行本身约 1.94×，整缓存约 1.75×；在 A100 上软件解码成 BF16 tile 再做 MMA。这是用户定的必做项。
5. **MTP 下恢复快照**：先只恢复 prompt 末尾的只读快照。
6. **MoE**：EP8 放置（不需要 all-to-all）；削减非 GEMM 搬运；评估 Humming。
7. **DCP**：放在 FP8 之后，按"行身份契约"修 33/40。
8. **调度**：122 与 aging。aging 要保证请求能完成，而不只是开始执行。

规则不变：只在已验证的基线上改一处；判分只用原 harness 加题面规则，数据不完整即判无效；差异小于同配置重跑的噪声不算结果；代码按 SGLang 开发规范写。

## 11. 希望外部专家帮忙判断的问题（第二轮）

第一轮问题的回答已吸收进 §8 和 §10：EP8 不必引入 all-to-all；DCP 与 FP8 的容量不能相乘；FP8 用 528 B 带 scale 的行；MTP 先恢复 prompt 末尾快照，不直接关闭；先测显存预算。第二轮建立在 §7 的三个新事实上：2 TB 主机内存、底包 HiCache 不正确、MoE 慢在形状。

1. **HiCache 能否成为主要的容量手段？** 假设正确性修好：
   - (a) 每两张卡共用一条 PCIe，8 卡同时搬回时，实际带宽和搬回时延会怎样？会不会给首 token 时延带来新的长尾？
   - (b) 写回策略怎么选：每次 prefill 完就同步写到主机，还是被挤出时再写？回放中同一条链的请求间隔中位 2.4 s、p99 36 s。
   - (c) 搬回和正在进行的 prefill、decode 抢显存带宽，这笔账怎么算？
2. **256 token 分组的所有权**：
   - 方案一：只在 256 对齐的边界上登记、命中主机缓存，最多多重算 255 个 token。
   - 方案二：改设备端布局，让每个 64 token 页独立存自己的索引（上游 #40134 的做法）。

   前者简单，后者通用。倾向哪个？有没有第三种？
3. **有了 HiCache，FP8 latent KV 还排第二吗？** 显卡上的 KV 池会从"装所有会话"变成"装正在跑的会话"。FP8 的价值变成两点：显卡上能同时跑的请求更多，以及 PCIe 搬运量约少 1.9 倍。它与"显存预算""MTP 下恢复快照"相比应该怎么排？
4. **EP8 放置的细节**：
   - (a) 共享专家现在是作为第 289 个专家融进去的。EP 下它是每卡各算 1/8 的行，还是保持 TP 切片？
   - (b) 专家负载不均时，最慢的那张卡决定整层时间，decode 的 TPOT 会不会因此变差？
   - (c) TP2×EP4 之类的折中值得测吗？
5. **怎样最便宜地推断正式 N18 挂在哪？** 平台只返回通过档的分项。计划是在长链集上跑正式 A 的 N14/N18，对比 `L_safe` 和排队是怎么形成的。这样足以缩小未知吗？还缺哪种测量？
6. **MTP**：官方推荐 5/1/6 自适应，我们用的是 3/1/4。以容量和尾部为主要目标，先测深度，还是先测恢复 prompt 末尾快照？
