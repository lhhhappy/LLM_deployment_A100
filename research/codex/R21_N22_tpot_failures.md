# R21 — 035/N22：205条TPOT超标请求的特点

作者：Codex main；2026-09-23；T59 / F97。只分析已完成的035/N22，未运行GPU实验或提交。

**结论：这些请求有明显的时间聚集；大量受影响请求本身缓存很好、首token很快，随后在密集prefill期间生成缓慢。现有证据支持prefill挤占decode是重要机制，不能再把205条统一解释为“自己的缓存丢了”或“输出太短”。**

## 3. 全部205条的共同点与反例

### 3.1 输出并不普遍很短

| 输出长度 | 全部请求 | 超标 | 该组超标率 |
|---|---:|---:|---:|
| <100 token | 80 | 26 | 32.5% |
| 100–255 | 478 | 139 | 29.1% |
| 256–511 | 83 | 20 | 24.1% |
| 512–1023 | 54 | 13 | 24.1% |
| ≥1024 | 27 | 7 | 25.9% |

**VERIFIED**：179/205（87.3%）输出至少100 token。100–255组贡献最多，也因为这个组本来就占全量66.2%，不能只凭139条就称它有异常高风险。短输出会放大一次停顿对平均TPOT的影响，但这次故障范围更广。

### 3.2 长上下文、长未命中请求风险高，但高命中也会慢

| 特征 | 全部请求 | 超标 | 该组超标率 |
|---|---:|---:|---:|
| 上下文<65536 | 574 | 141 | 24.6% |
| 上下文≥65536 | 148 | 64 | 43.2% |
| 自身未命中≤4096 | 415 | 106 | 25.5% |
| 自身未命中≥65536 | 43 | 30 | 69.8% |
| 缓存命中率≥90% | 401 | 97 | 24.2% |

各行有交集，不能相加。106/205（51.7%）本身只补算≤4096 token；97/205（47.3%）命中率≥90%。大prefill请求既可能受影响，也会占用别的请求所需的执行时间；上述风险率没有消除数据集、时间段、并发等混杂，不是独立因果效应。

### 3.3 时段比单一请求标签更值得追

按**首token所在分钟（UTC）**分组：

| 时段 | 该时段出首token的请求 | 其中最终TPOT超标 |
|---|---:|---:|
| 17:27 | 14 | 14（100%） |
| 17:30 | 67 | 0 |
| 17:32 | 56 | 0 |
| 17:35 | 18 | 17（94.4%） |
| 17:42–17:44 | 36 | 32（88.9%） |
| 17:46–17:47 | 27 | 0 |

不是“该分钟只有这么多请求在跑”，也不是按该分钟完成量计算吞吐。17:43–17:44共136次prefill报告，129批≥8192；与三条高命中请求共同处于长生成窗口吻合。结尾负载退去后TPOT下降，不能据此外推满载N22的decode速度。

数据集标签也有差异：biomaster=140/546（25.6%），scimaster=65/176（36.9%）；本轮链首94/311（30.2%）、后续111/411（27.0%）。**不能据此断言某类题目内容或某个会话标识导致故障**；尚未做控制时间/长度/并发后的分析。

### 3.4 N18对照显示很强的运行时效应

| 同req_id对照 | 请求数 |
|---|---:|
| N18、N22均超标 | 92 |
| N18过、N22超标 | 113 |
| N18超标、N22过 | 44 |
| 两档均过 | 473 |

**VERIFIED**：N22超标205条中，140条命中量与N18相同、36条更多，只有29条更少。两档总实际prefill为10,629,513→10,648,329，只增18,816（0.18%）。

**INFERRED**：总工作量接近而失败集合大量变化，支持并发、到达次序和工作在时间上的堆积值得优先检查。闭环负载下并发变化也改变后续请求到达时刻；这不是固定时间线的受控A/B，不能把这69条净新增失败全部算成某一个参数的独立效果。

## 4. 对应的具体调度缺口

**VERIFIED（运行日志）**：[035 server.log](../../evidence/T59/035_server.log)的17:43:03、17:43:05等行同时有：

```text
#new-token: 16384 ... #running-req: 20, #queue-req: 0 ... cuda graph: False
```

即使等待队列空，仍有20条运行中请求需要生成。大prefill块仍然进入执行。

**VERIFIED（历史源码）**：[120 v2副本](../../evidence/T59/120_v2_historical.patch)在continuation上只检查`waiting_queue_len > 0`，首次长请求检查`waiting_queue_len > 1`才限制cap；同时保留每次prefill后一次decode机会。该版本没有按“正在decode的请求数”触发cap。它保证decode获得调度机会，却不保证每个token在100ms内产出。

**INFERRED**：这个策略与本档观察一致，解释了为何TTFT改善后TPOT仍可能失败。不能只保护尚未拿到首token的请求，还要控制大prefill对已在生成请求的影响。

035作业记录声明使用120 v2。仓库正在清理旧补丁，本轮从git历史读取并保留来源commit/SHA，见[来源记录](../../evidence/T59/historical_patch_origin.json)；没有独立取得pod运行源码的逐字节指纹，因此不把历史副本冒称为完整运行二进制审计。

建议下一步以这一具体场景做回归：**已有decoder、等待队列为空、再进入长prefill**，记录prefill与decode实际执行节拍。仅增加decode间隔会挤压TTFT，仅缩小块会放大已有host固定开销；应结合降低prefill单块开销，再用完整N22各门对照。当前722条下TPOT p95过门最多允许36条>0.10，205条至少要改善169条，是系统性改进需求。

## 5. 方法、失败记录与复现

```bash
python3 evidence/T59/analyze.py
```

该脚本只读固定SHA的035 raw、026 raw和完整035日志，写T59自身产物。[validation.json](../../evidence/T59/validation.json)验证722唯一同ID、相同prompt/output计数、205条名单、所有分组闭合与331个唯一形状/时间锚点。T59-01、T59-02通过。

- UTC偏移由原始请求epoch和单请求完整prefill的唯一token形状匹配核验为0秒。
- 输出首末时间差以raw中的`TPOT*(output_tokens−1)`计算；绝对窗口起点使用保存的client_first_token_at_s，属于近似。原harness并未保存逐SSE单调时钟原值，细节见T58。
- 每条prefill报告仅在整个`[日志秒, 日志秒+1)`落于窗口内、且距首token至少额外1秒时计入。这是保守的**报告事件重叠**，不是prefill完整执行区间或精确停顿。
- 先前尝试直接复用T56亚秒级批成员重建，在raw63失败：第一token与最近估计报告结束相差约112ms，超出100ms匹配条件。没有放宽阈值硬配对，失败保存在[mapping_failure.txt](../../evidence/T59/mapping_failure.txt)；旧`time_alignment.json/prefill_batches.json`为探索产物，不用于本文停顿估算。单请求锚点约束不能自动推广到所有混合批。
- 底包`metrics_reporter.py`的prefill吞吐以两次统计调用间隔计算；decode也按多轮报告。`new-token/input-throughput`不能直接当GPU耗时，日志没有Decode行也不意味着没有执行Decode。
- 日志末尾17:48:16有退出异常，但在全部请求17:48:08完成、17:48:13收到SIGTERM之后，不能据此解释17:43的TPOT。本文没有触发该退出，也不推断是谁发出信号。

原始日志经只读helper压缩传回，解压校验802,352字节与SHA；输入、取回回执、逐请求事件行号均保留于`evidence/T59/`。
