# N30→N34：短请求首先失去执行机会

2026-09-25。完整同一 5601 请求回放：081/N30 与 082/N34 只改并发档；原 harness 判定前者 VALID PASS，后者 VALID FAIL。原始记录在 `evidence/L081-cap6144_full_n30/N30/`、`evidence/L082-cap6144_full_n34/N34/`。复算工具是 `scripts/analysis/compare_waiting_bottleneck.py`，逐请求结果在 `evidence/full-cap6144-20260925/n34-waiting/`。

复算命令：

```sh
python3 -B scripts/analysis/compare_waiting_bottleneck.py \
  evidence/L081-cap6144_full_n30/N30/raw_s1-dev-longchain_N30_1790351495.jsonl \
  evidence/L082-cap6144_full_n34/N34/raw_s1-dev-longchain_N34_1790360168.jsonl \
  evidence/full-cap6144-20260925/n34-waiting
```

| 门 | N30 超时 | N34 超时 | 新增/修复 | 新增坏例命中完全相同 | 新增坏例 API 分发完成→首次执行增量中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| fast 3s | 242 | 559 | 456/139 | 428/456 | +5.49s |
| overall 5s | 193 | 409 | 350/134 | 326/350 | +7.75s |

fast 新增坏例实际待算量中位 946 token；接收→API 分发完成增量中位约零，首次执行→首 token 增量中位 +0.10s。原始 `t_admit_s` 对应 harness 的 `api_server_dispatch_finish_ts`，**并非 GPU 调度准入**；`t_exec_start_s` 对应首次 `forward_entry_time`。SGLang 报告的 `queue_time_s` 在这批坏例里增量中位 +5.40s，与前述时间差一致。454/456 条的首执行前等待超过 TTFT 一半。fast 新增坏例按 **N34 本次实际到达时间**：前 10 分钟 45 条、10–30 分钟 198 条、30–60 分钟 210 条、60 分钟后 3 条。因此不能只盯开场第一波。整场 N34 实际待算量比 N30 多 161,024 token（+0.8%），远小于 TTFT 恶化幅度；“大面积缓存丢失”不是这次 fast 退化的主解释。

这里的“短”只指**新计算量**。这 456 条新增 fast 坏例，N34 的 prompt 中位长 52,576 token，cached 中位 51,456 token；339 条已缓存部分至少 32k。若其缓存状态需要从 host 恢复到设备，入批所需的设备驻留空间可能远大于 946 个新 token。原始请求行不标明 device/host 命中来源，因此不能从 cached 数值断言其资源资格。

固定引擎 759a6eb 的 `schedule_policy.py` 中，`_ax_short_hit` 明确要求 `not req.needs_host_load_back()`；已有长续块时，`add_one_req` 仅允许完整 device-cache 短命中搭车，host 恢复请求返回 `OTHER`。所以层级迁移可能同时增加恢复/分配工作，并让原本很短的请求失去与长 partial 同批执行的机会。这是源码上成立的机制，**不是对 456 条坏例的逐请求归因**；还缺其真实 tier、partial 状态及资源资格时间账。

TP0 服务日志中的预填批样本，10–60 分钟期间：N30 有等待队列的批次约 46–53%，队列 p95 约 4–5；N34 分别约 57–71%、8。`full token usage` p95 两档都接近 .98–.99，N34 持续更满。源码 `srt/managers/scheduler_components/pool_stats_observer.py` 的该比率以 schedulable full-KV capacity 为分母，已扣除可驱逐缓存；因此接近 1 代表非可驱逐状态的实际压力，不是仅仅缓存“占满”。但日志只在预填批打点，既不按墙钟加权，也不记录每个等待请求当时是否可分配；不能单凭此把 5.49 秒判成 KV 拒绝或排序错误。

`metrics.jsonl` 每 10 秒采样一次，提供较少受预填批选择偏差影响的交叉检查：

| 时段 | N30 有队列样本 | N34 有队列样本 | N30 full-KV≥.95 | N34 full-KV≥.95 | N30/N34 队列 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 开始 0–10 分钟 | 75% | 83% | 8% | 25% | 18 / 24 |
| 10–30 分钟 | 34% | 61% | 18% | 50% | 4 / 8 |
| 30–60 分钟 | 31% | 50% | 18% | 28% | 6 / 9 |
| 60 分钟后 | 6% | 8% | 1% | 1% | 1 / 1 |

这说明 N34 的压力不止开场冷链首；它延续到 60 分钟左右。`kv_available_tokens` 在 10–30 分钟的中位数两档都只有约 3,900，N34 的可驱逐 KV 中位数则从 N30 的约 200k 降至约 69k；这与更多状态被在途请求锁住相符。主机已用约 2.9M token 在两档均接近满额，不能因此推断额外的 host churn 是 N34 首要原因。

**缓存层级确实改变了。**同一个 TP0 计数器 `prefill_effective_tokens_total` 从测量 flush 后首个样本到末样本：N30 的 device/host 命中分别是 325.05M/49.69M token，N34 为 292.01M/82.61M；总命中几乎相同，但约 33M token 从 device 命中转为 host 命中。这个计数器按有效预填 token 累计，单个长前缀会在多次请求中重复计数，不能解释成独立缓存容量或额外计算量。它支持“设备驻留压力使更多请求走 host 恢复”的解释，也提示 host 恢复队列和恢复后的设备 KV 分配都可能贡献准入等待；仍需逐请求状态才能定量归因。

按计数器时间窗口求差，10–30 分钟 host 占缓存命中 token 的比例约从 23% 升到 51%，30–60 分钟从 24% 升到 35%；两段正好覆盖 408/456 条新增 fast 坏例的实际到达时刻。层级迁移与坏例时间重合是值得追的线索，而非逐请求因果证明。

对 N34 新增 fast 坏例，以收到请求前 2 秒内最近一条 batch 日志作为粗略状态快照：415/456 条有覆盖，其中 53% 的快照 full-KV 使用率至少 .95，87% 有等待队列；N34 仍达标的 fast 请求中，分别为 14% 与 34%（3917 条有覆盖）。这是相关性证据，受时间分布及日志采样影响，不能证明释放 KV 或改排序可救多少条。

下一次决策应先回答两个互斥问题：短请求是否已有资源且只是被现有长 partial/LPM 顺序越过；还是 full-KV、KDA 或 slot 资格不足。需要按真实调度决策区间记录“未扫描、已扫描但资源不满足、已有 partial、排序落后”，用决策到下一次机会的秒数而非拒绝次数计账；不要调用有副作用的正式匹配函数做旁路诊断。若资源压力主导，优先研究减少驻留时间、缓存/状态布局或降低执行时间；若可运行越过主导，再用 123/126/短请求搭车验证。117 的 MoE 替换先用 TP8 短测量真实服务收益，开发机单层 1.65× 不能直接当整档收益。
