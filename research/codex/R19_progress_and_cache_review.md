## 2. 已证实的脚本问题（按影响排序）

### S1 — 严重：不完整的测量可被判全通过

`scripts/pod/verify/analyze_run.py:29–38`：空桶 `hard=(not t) or ...` 为真；缺 TPOT 时赋 0；无完整 cohort/重复 ID 检查；错误只按混合总数判 `<=1%`，不保留 harness 对 data/render/infra/engine 的各自硬门，1% 边界也与 `<1%` 不同。

**CPU 实测：空 raw 输出两种 ALL_PASS=true、TPOT=0。** 不是假设。`evidence/T53/empty_verdict.json`。

`scripts/pod/jobs/dev_ladder_template.sh:34–40` 忽略 `run_dev.py` 退出码、选目录里最新 raw，且不检查分析器退出码。预检后失败、运行中断或同目录旧结果均可能进入错误判定。当前 026 完整且真实失败，不能说它已经发生假通过；确认的是这道门存在漏洞。

建议统一使用已有 `scripts/score_formal.py` 的原 scorer/完整门口径，并额外核验 run manifest、cohort ID 集合、测量 raw、各进程退出状态；不要再维护第二套简化硬门。已有 `scripts/test_ladder_search.py` 包含空桶、缺 TPOT、coverage 反例，却未保护 pod 的另一个实现。

### S2 — 严重：分桶/浪费统计重复实现，已实际误导结论

`prefill_waste.py:7–13` 与 `cachecmp.py:18–29` 按 phase 聚合、用冻结预期差称 waste/lost，未区分本轮链首。`ttft_decomp.py:5–11` 按 phase 写死阈值，漏掉 idx=0 对门的覆盖，也没有独立 fast 门。`analyze_run.py:51` 已按 R18 排除了链首，但其它分析路径未同步。

需要三列独立字段：原始 edge、回放前驱是否存在、原 harness 门。门始终使用冻结分桶；缓存根因另用真实 token LCP 和 KV/KDA 事件。不能用实际 cache miss 重新定义官方 fast 桶。

### S3 — 严重：清缓存失败没有阻断实验

只读 harness `s1-dev/run_dev.py:46–56` 只看 HTTP 成功、不验 JSON `success`，`:232` 忽略返回值；pod 梯子直接使用它。`numcheck.py:13–16` 同样忽略 JSON，全部 30 次异常后还能正常返回；`dcp116_probe.sh:24` 也只读响应。

因此 HTTP 200 + `success:false`、或重试耗尽，仍可能用旧缓存继续测。建议沿用仓库已有严格 flush guard，在外层确认真清并失败即终止；不改只读 harness。源码风险已证实，本轮未声称旧 026 测前 flush 失败。

### S4 — 严重：数值比较器既有误报，也能漏掉明显异常

`numcheck_cmp.py:8–17` 只 zip 公共长度；不校验长度一致；只把首 token 不同/首 token logprob 差>0.5 判 WRONG；其它前几个 token 分叉是 drift，不计入 wrong；任何结果都返回 rc0。

CPU 反例：参考 `[1,2,3]`，候选 `[1]` → `ok; wrong=0/1`；候选 `[1,9,8]` → `drift; wrong=0/1`。现有 `grep wrong=0/` 门会接受两者。允许合理数值漂移需要受控基线，但长度缺失不可接受，首 token 一致也不能证明后续 decode/状态恢复正确。原随机输入对 scatter 正常变化的 6/18 WRONG 又证明它有误报。

`numcheck.py` 的两个并发线程不传播线程异常，也未证明实际合批；`cached` 被记录但未作为命中覆盖条件。需固定案例清单、完整输出、有限数值、真实命中/graph 分支收据，再比较预先标定的 logits/logprob 或任务能力。

### S5 — 严重：116 的 8 卡 probe 写了验收标准，却未执行这些门

`dcp116_probe.sh:37–52` 对失败仅 echo 后继续；最后只打印 numcmp，既不验证 wrong 数，也不强制能力≥10/12、cached>0、allocator 高位真的越过每卡边界；shell 管道还可能吞掉前面程序错误。

五次顺序 cold 每次生成1 token，不等于“900k 活跃 token 同时驻留”，缓存可能被截断/淘汰，旧 usage 口径也不能证明高虚拟地址覆盖。应记录 allocator 实际 loc 最大值和所走读写路径。这个脚本现在不能可靠担任116验收门。

### S6 — 严重：120 补丁和生成器不一致，重生成会带回旧逻辑

`make_120.py:58–61/:86–90` 无条件把 cold 限到 cap；当前 `120-sched-protect-chain.patch` 则是 v3：只有存在等待或 decode 才限块。生成器 main 最后直接覆盖原补丁。

本轮只在内存调用生成器 `edit_policy`，确认生成结果没有当前 wait/decode 条件，未运行生成器 main、未覆盖生产补丁。证据 `120_generator_review.json`。原 T41 的测试/确定生成收据不能自动替当前 v3 背书。

### S7 — 中等：前缀潜力模拟的顺序不是实际闭环派发顺序

`scripts/analysis/prefix_reuse_potential.py:20/:33–37` 按原数据 `dispatch_offset_ms` 排序，并以原 `chain_index` 判断链首。实际 N 路闭环从 cohort 链队列取任务，随各链完成速度改变派发顺序。模拟中“更早出现”的前缀可能在该次测量里尚未出现；未计是否已经计算入树、状态槽、淘汰。

它可以作为指定排序下的无容量限制潜力情景，不能作为026/034每条请求应命中的证据。实际根因需按 raw 的派发/执行/插入时间核对。

### S8 — 中等：运行日志、形状和版本证据未完整绑定

- `lib.sh:40` 把 `server.log` **复制**成 `engine_current.log`，后者不是持续日志；复用引擎分支 `:35–36` 不给新 run 建完整日志关联。梯子又读新 `$RUN_DIR/server.log`，可能缺日志。必须保存实际启动日志路径与每档时间窗口。
- `logstat.py` 汇总整份 server.log，未按每档 raw 的测量窗口切分；warmup/前档的 compile、峰值会混入。`new>=8192` 后统一用8192倒推块时长，对16k块不成立；采样吞吐不能当成每个 batch 的 GPU 计时。
- job 文件复制了模板正文，如 `ladder_best140.sh` 仍缺最新模板的 precheck/smoke/diagnostics；只改模板不自动修复旧 job。
- 相同120编号已经经历v1/v2/v3，必须按旧运行源码/PATCHES_SIG/哈希恢复026，不能拿当前同名补丁当旧基线。

## 4. 对现状和已有解释的独立判断

1. **VERIFIED：闭环成立。** 但“闭环所以MTP必然降低N”不成立。MTP同时省服务时间、改变状态池占用，并在当前配置禁用140；净效应需要受控配对。可以暂缓组合，不能判方向死刑。
2. **VERIFIED：8.1–8.5k是实际未命中量/全档墙钟。** 分母包含decode、gap与末尾排空；不是纯prefill GPU产能。相近数字支持有效完成率接近，不能证明prefill执行效率相同或GPU绝无余量。
3. **INFERRED需降级：** 在飞prompt求和重复计算共享前缀、包括尚未算完的长prompt，不能等同物理KV驻留；`1-p10(tpot)/mean(tpot)`不能当已测prefill停顿份额；由公开N/TPOT/TPM不能识别第一名的源码方案或有意节流。
4. **当前实绩边界：** 026 N18四TTFT门过，但TPOT p95≈0.219失败；028约0.082通过TPOT但fast/overall/chain失败；028b与034也没有N18全门通过证据。不能把“能启动、12题通过”写成系统已经过关。
5. **只读实时状态：** 09-23 16:46:43 UTC开发机两卡0%、各4MiB；pod队列running/pending为空、034已failed。队列空不等于pod停止或GPU无任何进程，本轮未向引擎发请求。116/170v2未出现在已完成队列中。没有缺密钥，初次SSH瞬断重试后成功。
