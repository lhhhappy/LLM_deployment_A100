## 2. 机制上的防线（已实施）
1. 梯子模板默认开**正确性闸门**：开测前跑 12 题能力冒烟，低于 11/12 直接退出（exit 6）；可选 `NUMREF`，先和参考引擎做数值指纹比对，有 WRONG 就退出（exit 7）。
2. **数值指纹工具**：`verify/numcheck.py` + `numcheck_cmp.py`。长度覆盖桶尺寸和需补齐的尺寸，另有前缀命中续算、混合 batch、真实文本。先对照参考引擎，再允许性能测试。
3. **运行时监控**：梯子每档后台跑 `metrics_sampler.py`，每 10 秒记一次运行中/排队请求数、KV 占用、吞吐、缓存命中、投机接受长度，写入 `N*/metrics.jsonl`，供事后分析瓶颈，不再只看最终门。
4. 梯子不降级；首档失败即停，转入诊断（用户指示）。
5. 队列纪律：依赖探针结论的任务，等结论出来再入队。
6. 开发机验证必须写明它**没覆盖**哪些方面（拓扑、flag、结构），这些方面进 8 卡队列时要配上对应的正确性检查。

## 3. 当前对 170 错误的分析（待 029a–d 与 T52b 证实）
- 事实：BCG+scatter 为 0/12，eager+scatter 为 12/12，BCG 不带 scatter 为 12/12。
- 推断的机制：scatter 按本次 forward 的 token 总数把 token 分给各卡；BCG 把输入补齐到桶大小 B，被捕获的通信和 MoE/mHC 按 B 切分，而 eager 断点（KDA、DSA/indexer 桥）按真实 n 处理。n≠B 时，两边对"哪个 token 在哪张卡"的认识不一致，每层都错位。
- 预测：029b 中桶尺寸（512/1024/2048/4096）一致，其余长度 WRONG；029c 全部一致；029d 与 029a 只有噪声级差异。
