## 0. 先回答：我对这个部署的理解，是不是常与实验对不上？

是的，而且偏差有规律。把我每次上 8 卡前的预判和结果对一遍：

| # | 我的预判 | 实测结果 | 对/错 | 预判类型 |
|---|---|---|---|---|
| 1 | 114（indexer 行切分）会让长上下文 prefill 变快 | 180k 时每 token −33% | 对 | 单个 kernel |
| 2 | MTP 会降低 TPOT | tpot_p95 0.219→0.082 | 对 | 单个机制 |
| 3 | 每块约 150ms 的固定开销来自 launch/host | T51 实测：host 侧占 99% 的空闲 | 对 | 单个机制 |
| 4 | 120 v1 N6"全过" | harness 口径下 overall 5.29，没过 | 错 | 读指标 |
| 5 | chunk 16384 不影响显存 | 自动显存比例降到 0.646，KV 633k，崩溃 | 错 | 系统耦合 |
| 6 | v3 调度（小块 + interval）整体更好 | TPOT 过了，TTFT 全崩（027） | 错 | 系统耦合 |
| 7 | DCP 让容量 ×7.8 | 底包根本没分片；修好后约 ×4.4 | 错 | 没读源码就信了 |
| 8 | 025 崩溃是前缀命中寻址问题 | 是分配器高水位超过每卡行数 | 错 | 猜测 |
| 9 | BCG 能省约 100ms/块 | 8 卡上约省 35ms；028b 整体更差 | 半错 | 从替身外推到真机 |
| 10 | BCG+scatter 出错是因为补齐错位 | 捕获时没开 scatter | 错 | 猜测 |
| 11 | 028 = 026 + MTP | 实际改了 5 个变量 | 错 | 没做对照 |
| 12 | 026 与 028 的差距来自缓存丢失 | 两者缓存丢失几乎相同 | 错 | 猜测 |

**规律**：预判**单个 kernel 或单个机制的局部效果**时基本都对（1–3）；预判**整个系统在真实负载下的表现**时几乎都错（4–12）。

**根因**：我一直没有一个**定量的负载预算模型**，只凭机制做定性推理——"这个改动会让 X 变好"。可 N@SLO 是由整体排队决定的：prefill 需求、prefill 产能、decode 占用、KV 驻留，四者互相耦合。定性推理判断不了"变好 X 会不会让 Y 更糟"。而且我在最主要的工作区间从来没测过真实数据：

- **从没 profile 过 16k 大块 prefill（GPU 算力受限区间）的 kernel 构成。** T51 只测了 c=1024，那是 host 受限区间。可 N18 负载下，GPU 大部分时间都在跑大块 prefill，所以真正决定吞吐的 kernel 排名我们并不知道。
- **从没把负载本身量化过。** 每档要处理多少 prefill token、需求随时间怎么分布、有多少请求会整段丢缓存，直到今晚才第一次算出来（§2）。

还有一个猜测的来源：开发机替身（单卡 TP1、dummy 权重、8 层）。它适合测单个 kernel，但它的结论不能直接当成 8 卡真机的结论（#9、#10）。

### 0.1 误判来自哪里：我自己的理解，还是 research/？
重读 `research/` 后发现两类来源：
- **research 早有答案、我没用上**：
  - R7 的对手表显示，所有 N≥18 的选手 tpot_mean 都是 0.024–0.028，tpot_p95 从没超过门槛的 78%。而我们在 N18 是 0.083 / 0.219，**慢约 3 倍**。我这两天一直当"调度问题"处理，没拿自己的数字去和 R7 对照。
  - R18（缓存丢失与容量）、R5（DP 显存）、R8 §6（MoE kernel、EDF）里的方向，也没有在上 8 卡前逐条对照。
  - 这是我的问题：每次上下文压缩后没按要求重读 research，凭记忆和临场推理做决定。
- **research 本身的推断，放到我们身上不成立**：
  - R7 §5 写"名次来自延迟排序和缓存命中，不来自吞吐；D3 容量工作优先级低"。这个推断的前提是**大家的引擎效率相近**。
  - 可我们的 sm80 适配栈（tilelang DSA、Marlin W8A16 MoE、indexer shim、eager prefill）效率明显更低，这个前提不成立。我照搬了结论，却没检查前提。

### 0.2 算术核对：prefill 的算力利用率只有 20–30%
- 激活参数（来自模型配置）：MoE 9.5B（42 层 × (8+1) 个专家 × 3 × 4096 × 2048）+ KDA 注意力约 5.1B + DSA 约 1.3B + dense MLP 0.45B ≈ **16.4B**，即约 33 GFLOP/token。
- 再加 indexer（32 头 × 128 × P，11 层）和稀疏注意力：P≈95k 时每 token 共约 **45 GFLOP**。
- 8×A100 bf16 峰值 2.5 PFLOP/s ⇒ 理论下限约 18µs/token。实测 60–100µs/token ⇒ **MFU 约 20–30%**。做到 50% 的正常水平，prefill 就能快 2–3 倍。
- 这与"对手 TPOT 比我们低约 3 倍、总工作量却相同"一致：对手的 GPU 没有被 prefill 塞满。
- ⇒ **一级问题不是调度，而是引擎在 A100 上的 prefill 效率（MFU）。** 调度只能在 TTFT 和 TPOT 之间换，换不出算力。

## 1. 全部试验按结论归类

### 1.1 已被实测证实、可以依赖的
- **可用基线**：tier-1 补丁（000,101,105,106,110–113）能在 A100 上启动，冒烟 12/12。
- **026 是迄今 TTFT 最好的配置**：v2 调度（有排队时才把块限到 8192）、chunk 16384、mem 0.75、scatter、mamba 缓存 200、140 开、KV 132 万。
  - N18 下四道 TTFT 门两个口径全过：fast 2.44（10/23）、overall 4.41（18/27）、turn 11.66、chain 25.43。
  - **唯一不过的是 tpot_p95 0.219**（tpot_mean 0.083）。
- **025b**（不带 140，KV 633k）N10：TTFT 全过，tpot_p95 0.13 不过。
- **MTP**：12/12；N18 下 tpot_p95 0.082，tpot_mean 0.048–0.053。
- **114**：长上下文 prefill 每 token −20~33%，decode 不受影响。只在 028/028b（同时改了很多东西）里用过，**从没以 026 为基线单独测过**。
- **prefill 固定开销**：每块约 105–130ms，主要来自 host 侧的 eager 执行（2358 个 kernel × 约 104µs）。
- **170 v1**：BCG+scatter 输出错误；BCG 不带 scatter 正确。170 v2 已修，只在开发机 TP2 上验证过。
- **116**：DCP 修复，开发机 TP2 验证通过，8 卡未测。

### 1.2 被证实的负面结果（可以安心放下）
- **小块 + interval 的调度**（027、028c）：prefill 吞吐不够时，块切小会让 TTFT 全面崩溃。在当前产能下，这个结论成立。
- **chunk 4096 + BCG + MTP**（028b）：TTFT 比 028 更差。但它同时改了块大小和 BCG，**所以只能说明这个组合不行，不能说明 BCG 不行**。

### 1.3 可能被误杀、或从没真正测过的方向（重点）
| 方向 | 当时怎么被放下的 | 实际证据强度 | 该怎么处理 |
|---|---|---|---|
| **026 + MTP（其余不变）** | 当时假设"MTP 必须关 140 + fp32 SSM + 小 KV" | 这个约束**没测过**，是从 W22 的验证配置继承来的 | 先单独测 MTP 与 140 能否共存（冒烟 + 数值），再测 026+MTP |
| **026 + 114** | 没测过 | 单 kernel 收益已实测 | 最该先做的单变量试验 |
| **DCP（116）** | 025 崩溃后被搁置 | 崩溃根因已找到并修复；013b 实测 190k 冷 prefill −19%，64 头一次读 KV 效率更高 | 8 卡复测容量 + 速度 + 正确性 |
| **Prefill CP（`--attn-cp-size 8`）** | 012d/012g 启动即崩（ENGINE_DIED），从没排查 | 零证据，只是"启动失败" | 查日志；长 prefill 按序列切到 8 卡，可能是最大的吞吐杠杆 |
| **BCG 在大块下** | 028b 与小块混在一起测 | 8 卡上固定开销约 −35ms，数值正确（不带 scatter） | 用 026 的 16k 块单独加 BCG 测一次；预计收益小 |
| **scatter + BCG** | v1 出错 | v2 已在 TP2 修好 | 8 卡数值复测 |
| **MTP + chunk 16384** | 033 预检 KV 82 万 < 90 万，被拦下 | 90 万这条线是我拍的；026 的 KV 峰值 97% 是在 132 万下 | 不一定要拦；可用 mamba 缓存、KV dtype 等方式腾显存 |
| **cache 保留策略** | 从没做过 | 实测：一个 25 万 token 的链中请求整段丢缓存，要重算约 20s | 见 §2 |
| **MoE / indexer 大块 kernel** | 没 profile 过大块 | 未知 | 先 profile |

## 2. 一级问题：prefill 吞吐（实测 + 算术）

**负载预算**（026/028 的 N18 原始记录，实测）：
- 722 个请求在约 1200 秒墙钟里，实际 prefill 了 **1063 万 token**（026），平均需求约 **8.9k token/s**。
- 实测 prefill 产能：chunk 16384 下每 token 约 60–100µs（随前缀长度增长），即**约 10–16k token/s**。
- ⇒ N18 时 prefill 利用率大约 55–90%，已经接近饱和。排队论告诉我们，利用率接近 1 时尾延迟会爆炸。这正是 TTFT p95 和 chain_start 尾巴的来源。
- decode 能拿到的 GPU 时间就是剩下的那部分，所以 tpot_mean 0.083 ≈ 纯 decode 20ms + 等 prefill 约 60ms。
- **N26 的需求是 N18 的约 1.44 倍（约 12.8k token/s）。要让利用率回到约 65%，prefill 产能要提升到现在的约 1.5–2 倍。** 光调参做不到，这是 CalvinCao 做到而我们没做到的。

**需求侧的浪费**（实测，026）：
- 整体实际 prefill 量比冻结预期少 13%（跨会话前缀共享起了作用）。
- 但有**个别追加型链中请求整段丢了缓存**：prompt 25.2 万、cached=0、预期新 token 只有 1281、距上一条约 200ms。一条就是约 20 秒 GPU，同时拖垮 TTFT 和 TPOT。
- context_reset 多算了约 99 万 token。
- **推断**：026 的 KV 峰值是 97%，LRU 把马上就要用的长链前缀挤掉了。可以用 cache 保留或保护策略（例如给链尾前缀更高优先级），或用 DCP 增加容量来解决。

**产能侧的杠杆**（按证据强度排序）：
1. 114：长上下文每 token −20~33%（实测）
2. DCP+116：容量约 ×4.4（算术），190k 冷 prefill −19%（013b 实测，但那次跑的是未修复的 DCP，要重测）
3. Prefill CP：未知（从没跑起来过）
4. 大块下的 kernel 优化（MoE Marlin W8A16、indexer `_prefill`）：要先 profile
5. scatter −6~9%（实测）；BCG 在大块下收益小（推断）
6. MTP：减少 decode 占用的 GPU 时间，把时间还给 prefill（推断）；TPOT 直接改善（实测）

**二级问题：tpot_p95**。026 的块是 16k，每块约 1.6s 的停顿会被计入并发 decode 请求的 TPOT。MTP 已经证明能把它压到 0.1 以下（028，但 028 用的是 8k 块并限到 4096）。**026 的 16k 块 + MTP，tpot_p95 能不能过，还没测过。**

## 3. 测试方法本身的问题
- **一次改太多变量**（028/028b），得出的结论无法归因。
- **最主要的工作区间从没 profile 过**（大块、真机 TP8）。
- **梯子不降级是对的，但缺少"逐门诊断"的工具**：直到今晚才有 `cachecmp.py`、`prefill_waste.py` 和 `metrics.jsonl` 采样。
- **dev 集只是链前缀抽样**，官方说不能用它预测 N@SLO。今天两次提交（45979/45980）的线上成绩出来后，要用它校准 dev 集与线上的关系。
- **开发机替身**只适合看单个 kernel，不能用来预测系统行为。

- Prefill CP
