# 长程 s1-dev：生成设计与验收契约

2026-09-26 起为 v3（`source-event-longchain-v3`）。当前实现为 `longchain.py` + `longchain_events.py`：先冻结事件计划，再编译不可变历史快照；复用原 Renderer、数据布局和回放程序。正文以 s1-dev 为素材；每一步的负载（新增 token、等待、输出）照搬主办方同类公开请求，每条链对齐主办方冻结的三个总数（见下节）。不再读取 Phoenix。独立性指每条接收链的历史和依赖自足，不强制隔离 KV，也不要求每个文本片段唯一。

## v3：按主办方 token 结构对齐（2026-09-26）

目标是让本地实测接近线上：生成器对齐的是引擎感受到的量，正文语义不追求。依据全部来自主办方 dev-combined-v1 的冻结元数据与 722 份公开正文，核对方式写在括号里。

- **每条链三个精确总数**：`chains.jsonl` 的 `sum_glm_tokens`（prompt 总量）、`sum_uncached_expected`（新增总量）、`total_edges - append_only_edges`（改写历史的相邻转换数；链从会话中途开始时 `total_edges` 多计链首入边）。66 条正文全公开的链上，逐条请求求和与链级总数 66/66 相等；逐条 `edge_type` 还原的改写数与链级 66/66 相等。合成部分以"总数减去公开部分"为目标。
- **每步负载照搬同类公开请求**：同轮续跑用非链首 intra（388 条），新轮开头用非链首 turn_start（20 条），重建用全部 context_reset（23 条）；照搬该请求的 `uncached_expected`、`replay_gap_ms`（主办方的工具+思考封顶规则）、`max_output_i`。三者成组抽取，保留它们的真实关联。事件位置未观测，随机放置；次数按链的 phase 计数。
- **重建是追加**：公开的 23 条 context_reset 全部是纯追加（新增 504–4750，中位约 1.9k），所以计划中的重建按模板大小追加，只是阶段标签为 context_reset（计入链首门）。只有上下文超过 `--max-context-tokens` 时才做真正缩短历史的重建（`compact-rebuild`，保留约四分之一尾部）。
- **新轮收尾规则**（公开正文全部相邻请求实测）：新 human 消息到来时，刚结束那一轮带工具调用的 assistant 消息正文被清空（11/11；同一轮内从不清空，231/231），因此从该轮第一条被清空的消息起全部重算；运行时 reminder 移到新问题之后。
- **改写（历史被打断）**：按链的改写数安排，新轮开头优先，余量随机落在同轮续跑。实现为在较早的工具调用消息里多加一个 Read 调用（至多 1024 token）：之后的历史全部重算而上下文几乎不增长；分叉点取估计重算量最接近目标的位置。构建时跟踪实际改写：计划外的改写（有正文可清空的新轮、上下文超限重建）会取消后面一个计划中的续跑改写；计划中的改写即使目标已达到也做最小分叉。公开数据中 5/20 个新轮开头是另一条轨迹、在第一条 human 消息后即分叉。工具调用 ID 不进入渲染，改 ID 不会导致重算（实测）。
- **两个总量的分配**：上下文增长会带入之后每条请求，所以 prompt 总量限制同轮续跑和重建的增长幅度；剩余新增 token 交给改写步。缩放系数限于 [1/16, 16]；增长步长不超过公开样本最大值；改写至多重算第一条 human 消息之后的全部历史。改写次数与 prompt 总量优先，一条链的新增总量若超出"改写次数 × 可重算长度"，就如实偏少，不用更大的 Read 硬凑。
- **长度补足**：借来的工具块短于目标时，加一个并行 Read 调用，结果文本先取公开工具结果中的长文本，再取冻结源码树 `build/base_exact`（`--read-corpus`）的文本文件，按固定顺序往下读、不回头重复；清单记录语料哈希与读取位置，只有 token 数有意义。
- **已知偏差**：公开请求集中在链的前几步，模板带有"开头"特征；主办方少数链有压缩式改写（下一条 prompt 变短），v3 只在上下文超限时缩短上下文；5 份公开正文的会话没有可用的 Read 定义，这些链的新增与改写会偏少；新增总量可能偏少（见上）。偏差按链写入 `manifest.json` 的 `chain_summaries`（`synthesized_*` 对 `target_*`，目标为源链总数减公开部分），用 `workload_compare.py` 汇总。

v2 成品为 [`data/s1-dev-longchain/`](../../data/s1-dev-longchain/)，v3 通过验收后放在 `data/s1-dev-longchain-v3/`；规模与验收进度见 [`data/README.md`](../../data/README.md)。生成中间件只写 `cache/` 下的新目录，通过验收才成为成品。全量生成需数 GB 内存，在 GPU 开发机 `/sjtu/linhang/arena/runs/` 下运行，产物再经 `scripts/pod/ppush` 进 Pod。

三路审查已修复重建摘要被下一步删除、素材不足绕过压力重建、丢弃试选污染使用计数，以及重建收据和工具边界漏检。极短中间历史的摘要可能比原文更长，生成器会收紧同一次重建的尾部/摘录并重新真实渲染，仍不缩短则拒绝生成；调整写入来源账本。

### 生成与验收

在仓库根目录执行；输出目录必须不存在，避免覆盖冻结数据：

```bash
uv run --with-requirements scripts/longchain/requirements-longchain.txt python -B scripts/longchain/longchain.py build \
  --chains 311 --seed 20260924 --set s1-dev-longchain-v3 \
  --out cache/s1-dev-longchain-v3-build          # --read-corpus 默认 build/base_exact

python3 scripts/longchain/workload_compare.py --root dev=s1-dev/data/dev-combined-v1 \
  --root v3=cache/s1-dev-longchain-v3-build     # 四道门占比、各类新增 token、逐链三总数对比

uv run --with-requirements scripts/longchain/requirements-longchain.txt python -B scripts/longchain/longchain_replay.py \
  --root cache/s1-dev-longchain-build \
  --out evidence/longchain-design-20260924/full-acceptance --self-check
```

`--chains 24` 生成分层小集；311 链的源摘要规模为5,601次调用，原722条可见输入保留，其余4,879次由事件续接产生。换seed得到另一份共享素材的合成选择，不能当新增独立线上观测。`--max-context-tokens` 默认524288，部署较小上下文时须按真实上限另行生成和验收，不能发压时截断。

当前实现的明确边界：用户追问采用跨session原query加短衔接，Luna试制素材尚未接入；system/tools继承各源链家族，链内不新增版本切换；重建采用接收历史摘录而非语义摘要模型。下面各机制说明包含后续扩展契约，不能把尚未使用的可选操作视为本版已经覆盖。

## 目的与数据来源

构造可用原harness回放的长程合成开发集，检查部署在持续增长、等待、重建和混合竞争下的表现。原开发集继续独立承担A/B和回归；新集不能预测正式N@SLO。

**按task.md原理核对的结论**：跨session借query/片段并离线冻结，与该harness的固定轨迹回放方式兼容。[task.md](../../llm-challenge-arena-v1/task.md)第167–222行规定完整渲染prompt与逐请求`max_new_tokens + ignore_eos`，压测评分不读输出正文；第488行明确工具结果来自冻结记录、不执行工具。[s1_loadgen.py](../../s1-dev/harness/s1_loadgen.py)的`drive`逐次读取冻结prompt，没有把本次回答反馈到下一prompt。因此无需恢复A原故事或执行其真实工具，也无需对合成对话做逐题正确性打分。此结论只涉及自建诊断负载；官方能力评测仍独立保留。

用户要求review聚焦**负载真实性**：实际token长度/增量/输出预算、事件与间隔、历史稳定/重建、共享前缀、链长与竞争结构。只因话题跳转或措辞不精致不应阻断生成；格式损坏、未闭合工具引用或大段克隆导致的负载畸变才须修复。不能进一步推成“任意正文同分”：tokenization、MTP接受率、MoE路由和实际闭环交错仍可能受内容影响。冻结同一成品做A/B，并报告这些实测差异；不追求完整故事复原。

| 来源 | 用途 | 不据此宣称 |
|---|---|---|
| s1-dev完整请求正文 | system/tools、用户/assistant/工具文本及结构素材 | 缺失的真实请求已经恢复 |
| s1-dev源链摘要 | Bio/Sci链长、事件计数、输出和输入工作量的参考约束 | 等于正式隐藏集 |
| 正式A/B与原样本地校准 | 检查负载解释是否合理，识别分布敏感性 | 两点反演隐藏集或拟合固定换算系数 |

不加密后直接填充prompt；不靠循环复制同一个8k块扩成16k。可以组合不同s1-dev素材，也可以适度复用同一素材；生成位置、结构、来源和估计字段必须可追踪。

“允许mock正文”与“禁止mock测量”分开：低成本模型可生成主题变体、追问、回答、示例工具结果和摘要；不能让模型编造token计数、等待时间、cache miss、吞吐或评分。相邻调用的完整语义一致不作高成本验收项目；格式闭合、前缀稳定、长度与事件分布仍是硬要求。

模型产出的素材在生成前冻结：`source_material → model variant → accepted block`。一次生成、多次组合，减少逐请求LLM成本；复用受正文重复与跨session LCP审计约束。每块记录来源、模型、推理档、内容hash与GLM长度。不能让润色模型逐次重写整份历史，否则会破坏真实可复用前缀。

用户随后细化：Luna默认只扮演**离线受控user**，不整体重写轨迹。生成器先分配一个追问事件，选择可复用的后续assistant/工具素材，给Luna必要上下文及一种意图（澄清结果、补充约束、比较方案、要求总结、继续任务、调整范围），只收一条user消息。可以反向用已有后续材料约束提问，减少语义悬空。assistant/工具内容优先复用s1-dev；只有局部衔接缺失时才另行生成小片段。Luna不能创建额外事件或改历史。正式回放时不调用Luna，不根据被测模型本次回答动态生成追问；所有输入在测量前冻结，保证A/B同负载。

最新确认的素材策略有三种：原样复用、按有效消息/工具组边界组合、局部改写产生派生素材。模型也可以改写选定的回答/摘要/结果文本，user角色是低成本优先用法而非唯一允许角色。每次模型任务只处理一个明确片段或小素材包，不接管整条链。复用本身不违规：相同材料出现在不同历史后面，不等于能跨session命中；验收以最终token前缀关系与重复形态为准。无需为每个字都求唯一而付出模型成本。

## 1. 独立性的精确定义

每条生成链自足：其请求携带完整冻结输入，只引用本链先前事件或独立入场状态；没有依赖另一条生成链的消息、工具结果或完成时刻。逻辑session、request、tool call ID分配独立空间；同一链中的历史块保持不变。若从同一来源生成多个变体，来源关系必须可见，不能把它们当成独立的真实观测。

源session与回放chain不是同一单位。原开发集中136个(pack,session)对应311条回放链。第一版不新增跨链运行依赖；若将来源分支独立化，给生成实例独立session标识，并保留source_session/source_chain，不能假称恢复原父子并发。

原harness用N个worker逐链执行，前一响应完成后等待gap，之后发下一条；同一档共用cache_namespace，session ID作为请求头携带。**session ID不同不会使相同token前缀自动失去共享资格。** 不修改harness，不增加每session盐或强制隔离缓存。来源本来共享的system/tools前缀允许自然复用；生成器新增的大段克隆历史应被检出。

工具结果由数据冻结，回放不执行工具，也不把本次生成回答回填下一请求。输出不一致不会破坏后续轨迹；实际推理、排队、缓存保留与淘汰都由被测引擎发生。

## 2. 状态与不可变内容块

每个session维护以下状态：system/tools家族与版本、当前用户轮、按顺序排列的历史块、工具调用及返回映射、原始等待与回放等待、重建记录。正文块引入后只通过明确事件移除/重写；不在每次渲染时重新随机填充。

素材库将源请求历史去重为用户块、assistant块、完整工具调用/结果组、提醒块，以及有前后输入证据的重建转移。相同源块在多个快照出现只计一次素材，避免把快照重复当素材多样性。工具schema按语义结构比较；只有兼容的调用组才能移植。参数JSON、调用ID、结果ID、同一文件/实体引用的修改保持成组一致。

分配按接收session的事件、主题/任务类型、工具兼容性和长度需要选择素材。**跨源session借素材是正常生成路径，不只是同源素材耗尽后的回退。** 同源关系保留在来源账本，不作为硬性优先级。全局记录非共享正文块的来源、接收session与引入次数；素材不足时报告覆盖缺口，不自动退回大段重复、循环拼接或随机字符串。

### 跨session续接：A提供素材，B拥有新历史

用户最新确认的核心操作是：取A的query，原样使用或局部改写，放到B已有对话后面，作为B的一次新用户事件；随后续接兼容的回答/完整工具组，让B继续增长。不是把A的完整prompt接到B后面，也不是只把两个query合成一次请求。例：`B历史 → B轮结束 → 改写的A.query → 后续工具调用/返回 → 继续增长`。

- **接收端状态**：保留B的system/tools和已引入历史；A的system、会话头和全部旧历史不随query自动搬入。允许同领域任务切换，不要求逐句复原某一真实故事。
- **引入边界**：先结束/承接B当前工具组，再引入新user。query可单独借用；连续片段可整体借用，但必须切在完整消息/工具组边界。借入后生成实例有独立session/request/tool ID；所有前驱指向B。
- **局部适配**：把“上面那份文件”“刚才运行的任务”等A私有状态改成B已有对象，或把必要材料作为本轮新输入一起引入。必要时让Luna low只改这条问题/局部衔接；不重写B旧历史。无法适配的片段换素材，不要求为其搭真实工具环境。
- **身份与缓存**：每个session自足不等于素材必须唯一，也不等于物理KV隔离。B与其他session可以借同一query；历史分叉后相同尾部不直接构成长共享前缀。审核实际渲染LCP及整段克隆，不能靠随机ID/盐替代审核。
- **事件与计数**：借入一条query通常引入一个新用户事件，后续可有多次工具LLM调用；不能每补一个模型请求都塞一个user。合并A的两个query到B的一次追问，与拆成两轮是不同事件计划，分别计数。
- **时间与输出**：A.query不自带A的历史等待或当前输出预算。接收事件的gap、当前decode预算按预先冻结的联合计划分配，缺乏真实关联时明确估计；下一prompt内借用的assistant文字不等于本次实际decode长度。

来源字段至少包含`source_material_id/source_session_id/source_req_id`、`receiving_session_id`、事件ID、操作（原样/改写/组合）、实体和调用ID映射、引入位置及内容hash。同一素材可服务多个B实例，但不能将这些实例计为新增独立真实观测。每个实例沿自己的计划增长，重建后不会无意恢复已删除历史。

## 3. 事件操作与前后条件

| 事件 | 正文操作 | 时间/预算 | 必须检查 |
|---|---|---|---|
| 独立入场 | 使用源请求作为自足起始状态，保留完整system/tools与历史 | 入场是否带已有历史明确记录 | 起始长历史不伪装成从零开始；首请求走原chain规则 |
| 短工具续跑 | 追加完整assistant调用与小结果，可替换末尾提醒 | 从同类观测联合取等待和输出预算 | 原历史逐token保持；结果不能凭空引用外链call ID |
| 大工具返回 | 追加较大的文件/表格/检索材料，保留角色和工具组结构 | 与真实等待关系联合选择；慢工具不必大返回 | 新增量与总上下文分别测；不把多次返回简单重复成一个大块 |
| 用户追问 | 前一轮结束后引入一个明确的新用户事件，历史可继续保留 | 用户等待与工具等待分开记录 | 不将system-reminder或控制注入当真人追问；phase由该事件产生 |
| 长工具/子任务等待后恢复 | 等待前后的旧历史不变，再加入冻结结果 | 合并重叠工具区间；按原节奏规则转换 | 等待不修改prompt前部、不清缓存、不预设miss；返回量可大可小 |
| 历史重建 | 用摘要/清理后的历史替换旧历史的一部分；近期完整工具组按计划保留 | 与发生位置、前后长度、重建耗时一起建模 | 必须发生实质改写或缩短，不能只换标签；不能留下孤立tool结果 |
| 重建后恢复增长 | 在新历史基线上继续追加，不恢复已删除旧块 | 保留重建后的短期连续调用关系 | 历史版本持续一致；观察缓存重新建立，而非每轮再次重建 |
| system/tools版本变更 | 按有来源依据的版本事件更新定义，并调整后续兼容素材 | 原数据如何切链/分桶需单独核验 | hash变化位置与真实渲染对应；不每轮随机换system |
| 结束 | 保持最后请求与输出预算；worker按原harness补位 | 不加空等凑时长 | 长尾收尾时并发下降如实统计 |

这些是操作类型，不是各占固定百分比的独立抽签。长等待、大返回、用户追问和重建可以有联合关系；不能把若干边际分布独立随机后声称保留真实行为。

重建可以有两种不同结构：历史压缩为摘要并保留近期工具组；更早工具结果清理而保留其后消息。它们的首次分叉位置不同，LCP和新算量不同，不能都做成清空全部历史，也不能固定“每20轮压一次”。v3 的重建保留尾部，使重建后 prompt 接近所抄公开重建请求的长度。

## 4. 如何组成一条长链

先选择链长/起始上下文/提示词家族，再按主办方 phase 计数与改写数安排事件，最后编译正文快照。v3 的事件位置随机（重建尽量不放在首尾），另有上下文压力触发的强制重建；编译后验证实测token。若计划在很短历史上重建、移除内容不足或会打断工具组，则回到计划层重选，不仅修改phase使其通过评分。

链长参考源摘要的经验分布，分别保留Bio/Sci特点；查看按链和按请求加权的占比。源摘要311链/5601请求中31+的50链贡献3627请求，不能把公开722正文的短前缀当完整链长分布。具体候选规模不靠5150/341的均值反推。

原96链选择对应的源phase摘要为28 session_start、1569 intra、76 turn_start、45 context_reset；这只是明确的参考账。现成品28/1638/44/8说明缺失机制。下一版必须解释事件组成的偏差，但不通过随意增加标签来对齐摘要。fast比例由真实渲染及冻结规则产生，不单独设置目标命中率或目标fast比例。

长尾机制覆盖与经验混合使用同一生成模块、不同明确命名的配置；极端案例过采样不冒充线上频率。预先冻结配置，不能看某个部署分数后调整负载让它通过。

## 5. 时间、子代理与并发

原始工具等待采用时间区间并集，不能相加并行工具时长。用户思考单列。已知分解的原数据遵循`min(tool_union,300s)+min(net_think,10s)`；harness再执行每链累计gap 3600秒上限。v3 的新增事件照搬同类公开请求的 `replay_gap_ms`（已按该公式计算），`tool_union_ms/net_think_ms` 留空，不复制分解。

N是逻辑槽数；等待占槽，但该链此时没有在飞模型请求。其他槽继续调用或结束补位，形成真实缓存竞争。等待后不保证miss，立即返回也不保证全命中。不能以部署实测cache_read反过来修改数据或phase。

原harness表达的是自足顺序链，不能直接表达任意跨链DAG。子任务等待可由冻结结果和gap体现；若另行回放子代理LLM分支，必须先明确其如何计槽、与父链是否重复计入，不能简单加几条独立链来声称复现原并发。原s1-dev已存在的子代理来源链单独保留来源标识。

## 6. 防止人为缓存收益的检查

1. **依赖闭合**：所有新增消息、工具结果与实体引用属于本session；无跨session前驱引用。唯一ID检查只是基础，不能代替内容检查。
2. **链内历史一致**：追加时旧块完全相同；重建时有明确删除/替换账本；重建后旧块不会自动长回来。
3. **新增素材重复**：统计完整prompt重复、长消息块重复、整段工具组重复及每条链首次引入量。后续快照携带自己的历史不算新增重复；重复读取必须标成事件。
4. **跨session长前缀**：原GLM渲染后做token级LCP账本。分离source本来共享的system/tools与新增历史共享，检查是否生成了源中不存在的大群近乎相同会话。不能仅按sys_tools_hash判断共享深度。
5. **共享前缀竞争**：最终报告链首共同前缀长度、家族权重、多个长链交错时的不同历史规模。所有session共享一个模板、所有session完全随机化两种极端都不作为默认。
6. **预算与长度**：逐请求token和output预算、LCP新算量、phase、gap重算；不压输出、不在送引擎时截历史、不删除tools。
7. **评分完整性**：原harness全量自检；每请求恰好一次；同一冻结cohort比较部署；每档真实flush；同时报告四道TTFT、TPOT及TPM的原口径。

重复检查先与原s1-dev的同口径基线比较，不凭空设“所有跨session LCP必须为0”。若出现新制造的大段共享，修正素材分配；不往开头加随机盐掩盖重复。

## 7. 实现边界与交付

**8卡端无感知接入**：成品继续是原`requests.jsonl/chains.jsonl/bodies/*.jsonl.gz/samples/cohort.json`布局，原Renderer、runner、发压与评分照常读取，只切换root/set/cohort。内容来源记录放额外审计文件，不要求引擎理解synthetic事件或调用生成模型。离线改写/组合不是运行时改题；每档使用同一冻结输入、预算和gap，真实flush。可选[longchain_replay.py](longchain_replay.py)只在外层做完整性防护后调用原流程，不是第二套回放实现，也不要求现有8卡队列迁移。

原harness的self-check会跳过缺正文，其body cache只按数量判断可复用。因此交付先经独立checker全量token/ID/hash验收；原loadgen自检用`--no-body-cache`，原run_dev回放用新的输出目录，不能复用另一个成品的正文cache。评分显式指定本成品`--requests`或已有判分入口`--data-root`。这些防护同样适用于原dev。

保留：原数据读取、分层选链、Renderer/tokenizer、ID/body引用、工具配对、哈希/cohort冻结、独立校验器的通用检查。

已替换：追加式donor核心、按累计prompt反推每步增长的主导逻辑，以及依靠role=user猜事件的方式。重建必须有真正的状态变换；校验器也应独立验证这个变换，不能沿用“所有合成都必须追加”的旧假设。

当前内部流程：`source/profile → material bank → session event plan → immutable snapshots → original renderer → independent audit → frozen dataset`。网络采集与生成分开：生成只读取已经冻结的结构统计与s1-dev素材，不临时联网，不运行真实工具。

交付包括事件计划、逐请求来源/估计账本、跨session重复与前缀审计、原harness兼容产物和CPU完整验收。首次GPU回放只由执行层主会话排队；预期时长不能通过伪造测量或空等保证，正文可组合/局部生成。旧候选保持冻结，用于追溯，不继续叠加修补。

同pack、来源session不同的“user候选×接收源链”有69,899种候选配对。这只说明组合供应较大；尚未适配或验收，不能称69,899条可用链，更不能当独立样本量。重叠快照里的3,178次user消息出现、9,025次工具组出现已去重，不能用出现次数报素材容量。

**规模安排（实际进度见data/README）**：先做24–32链的分层小集，专门覆盖跨session续接、长链、长等待、重建与重建后增长；验收后主混合集以311链/约5,601次调用为首个规模目标，沿用源摘要的链长分布，再检查事件与联合分布偏差。数量并不受722条可见请求上限限制，也不需要为5,601次调用都请模型写一轮。按相同规格可另冻2–3个seed测合成选择敏感性，但共享素材，不是2–3倍独立线上证据。

从组合供应看，数千请求的合成集可行；一万或更多也没有组合数学上的障碍，但需先审核重复、兼容素材覆盖、上下文上限、磁盘及回放时间。上百调用长链通过多轮工具续跑和事件续接构造，不能将每条B统一延长或统一加追问。材料数无法保证有效多样性，无法保证2–3小时，也无法保证接近正式分数。大输出须配置并检查实际decode预算，不能只拼长历史回答。

## 9. Review与实现难点

跨session的query移植和局部改写本身容易；难点是保持B的不可变历史/依赖，以及在组合时不把user轮、工具续跑、gap、输出和重建的联合分布改坏。原读取、渲染、冻结与通用校验可复用；旧追加核心与“新增user即真人轮”的启发式需要事件计划取代。独立checker的“合成只能追加”规则也必须改成对真实重建的独立验证，不能只放宽标签。

1. **方案review**：核对来源、事件单位、时间转换、独立性定义及规模结论。主会话完成文档与素材数量自审，随后三个subagent审查并复核基础bug修复；事件核心也已经过三路bug审查；具体成品以真实Renderer验收记录为准。
2. **小集review**：预先分层抽24个接缝窗口，覆盖query单借、片段借用、大输入、长等待、重建、重建后增长；每类至少4个，可重叠，另查全部自动校验失败。审阅前后请求、来源和改写映射，不要求人工逐条读几千轮。
3. **全量CPU验收**：ID与工具依赖闭合、接收历史稳定、重建变换、token/LCP/预算、来源/哈希/cohort、分布与大段重复、原harness全量自检。把跨session引入的正文重复与后续正常历史携带分开计。
4. **独立实现复核与基线回放**：新生成核心/checker完成后再复核失败反例及成品；GPU阶段测真实缓存、MTP、实际输出和所有门。CPU通过不证明内容对MTP/MoE路由无影响，不证明线上分布已还原。

方案review不是向用户再索取批准的关口；在既有授权下推进。发现不一致就修复并记录，不能用review作为一直不生成数据的理由。

证据入口：[四类请求与来源审查](../../notes/codex-四类请求与造数建议.md)、[旧候选冻结](../../evidence/longchain-audit/frozen-candidate/README.md)。

311链/5601请求的完整扩展集已生成；它保持源摘要链长和phase计数，但位置与素材组合仍为合成。累计prompt393.887M（源485.059M）；缺失请求的源冻结新增预算18.936M，生成部分实际LCP新增5.109M。该静态差额不能等同GPU工作量差额，也不能忽略：本集能补充长程增长/重建/等待的机制覆盖，尚不代表已经恢复完整算量分布。
